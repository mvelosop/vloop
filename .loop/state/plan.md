### T2 — Build the run-record renderer, the marker splice and the metrics snapshot writer

`done` · depends on: T1

**Files:** `internal/closing/`, `internal/closing/closing_test.go`, `internal/cli/metrics_print.go`, `internal/metrics/`

`vloop brief close` (task 3) writes two artifacts: the brief's run record between generated markers and a frozen metrics/v1 snapshot. This task builds both as library code in a new package, `internal/closing`, before any command uses them. The marker splice is the invariant close relies on: everything outside the markers belongs to the operator and must survive byte for byte, which is what makes re-rendering safe. No command changes here.

**Acceptance**

- A new package `internal/closing` exports `PutRunRecord(doc, record string) string`. When doc holds a line `<!-- vloop:run-record:begin -->` and, after it, a line `<!-- vloop:run-record:end -->`, only the text between those two lines is replaced by record. Otherwise it returns doc, then a newline if doc lacks a final one, then the begin marker line, record and the end marker line, ending in a newline. Every byte outside the markers is preserved — trailing spaces and a missing final newline after the end marker included — and rendering the same record twice is a no-op.
- A renderer produces the record: `## Run record`, the line `Generated by vloop brief close on <YYYY-MM-DD>. Recompute with: vloop metrics <name>` (<name> the brief's name, e.g. `B20260101-0900-a.loop-brief`), the summary block in one fenced block, the `--by task` table in another, and one line per defect `- <id> — <kind>, <origin>, found by <found-by>: <summary>` — derived defects first by iteration, then recorded defects by id.
- The summary block and the table come from the same code `vloop metrics` prints with — moved out of internal/cli or exported from it — not from a second formatter. A copied format string for the summary or the table is the violation to look for.
- Derived defect ids are computed in one place: `<run id>/i<iteration>-gate` for a gate failure, `<run id>/i<iteration>-review-<n>` for a review finding, n counting from 1 within the iteration in the verdict's finding order (one `-review-1` when the verdict lists none). Task 5's export uses the same function.
- A snapshot writer saves a metrics/v1 document to `.vloop/state/metrics/<run id>.json`, 2-space indented with a trailing newline, creating the directories; the path it reports is repo-relative with `/`, and disk paths are built with `filepath`.
- Committed tests in internal/closing: `TestRunRecord…` (append, replace between existing markers, text after the markers byte-identical including no final newline, idempotent re-render, the rendered lines) and `TestSnapshot…` (path, indentation, trailing newline, validates against metrics/v1). They write only under t.TempDir().
- No command is added or changed; `vloop`'s output is unchanged.

### T3 — Add `vloop brief close`: findings, refusals, status lines, run record, snapshot and one commit

`done` · depends on: T2

**Files:** `internal/cli/close.go`, `internal/cli/close_test.go`, `internal/cli/brief.go`, `internal/brief/`, `internal/defect/defect.go`, `internal/runs/`, `README.md`

The command that replaces the operator's manual close of B1–B3, and the first vloop command that commits — so its refusals matter as much as its output. It refuses unless the operator states their findings, the tree is clean, HEAD is on a work branch and the plan is complete; then it records the findings as defects, snapshots the metrics, renders the run record (task 2's code), marks the brief consumed and commits exactly those files with the `Vloop-Brief:` trailer that release detection and `defect add --blame` rely on. `--abandon` and `--dry-run` are task 4's.

**Acceptance**

- `vloop brief close <brief> (--finding "<summary>"… | --no-findings)` takes a loop brief's name or path as `vloop metrics` does. Its refusals print one stderr line and nothing on stdout, and write, stage and commit nothing: neither or both findings flags → `vloop: say what you found before merge: --finding "<summary>" (repeatable) or --no-findings`, exit 2; no runs → `vloop: no runs for <name>`, 1; status consumed or abandoned → `vloop: <name> is already <status>`, 1; HEAD on the default branch (B3's rule) → `vloop: close on the brief's work branch, not <branch>`, 1; any uncommitted change, untracked files included → `vloop: commit or stash your changes first — close makes one commit of its own`, 1; the last run did not end `complete` → `vloop: the plan is not complete (<done>/<planned> done) — finish it, or pass --abandon "<reason>"`, 1.
- Each `--finding` becomes a defect file written by the same code `vloop defect add` uses — brief this brief, found-by operator, origin work, kind bug, severity medium, status open — not by a second writer.
- The metrics are computed exactly as `vloop metrics` computes them, with the brief's new status, and saved with task 2's snapshot writer; the snapshot equals `vloop metrics <brief> --json` run right after the close.
- The run record is written with task 2's `PutRunRecord` and renderer. The frontmatter `status` becomes `consumed`; a body line `**Status:** ready to plan` becomes `**Status:** consumed — closed <YYYY-MM-DD> as run <run id>. **Do not re-plan from this brief.**`, keeping whatever precedes `**Status:**` on that line (e.g. `- `). Nothing else in the brief changes.
- The commit holds exactly the defect files, the snapshot and the brief, staged by path — never `git add -A`, `-a` or a commit of whatever else is in the index — with the message `[vloop] close <run id>`, a blank line, and `Vloop-Brief: <name>`. It is one single-parent commit on the current branch. close never merges, pushes, fetches, checks out, or creates or moves any branch, tag or other ref. Git is run as the `git` command.
- Output, in order: the summary block as `vloop metrics` prints it (now `consumed · not merged`), `recorded <path>` per finding, `wrote <snapshot path>`, `updated <brief path>`, `committed <sha7> [vloop] close <run id>`, and last `squash-merge with the trailer: Vloop-Brief: <name>` — the brief's worked example, line for line.
- `--json` prints one document `{"brief","status","commit","files","trailer","metrics"}`: brief the name, status the new status, commit the new commit's sha (full, or at least 7 characters), files in the order written (defect files in flag order, then the snapshot, then the brief), trailer the whole `Vloop-Brief: <name>` line, and metrics the snapshot's metrics/v1 document.
- Committed tests `TestClose…` in internal/cli/close_test.go, on fixture repositories in t.TempDir() addressed with `git -C`: every refusal with a fixture where it applies and one where it must not, the re-render with a hand-written paragraph after the markers unchanged byte for byte, and the commit's files, message and trailer.
- README documents `vloop brief close`, `--finding` and `--no-findings`, so B1's README test passes, and stays under its 200-line cap: make room by moving detail to the guide, never by raising the cap.

### T4 — Add `--abandon "<reason>"` and `--dry-run` to `vloop brief close`

`done` · depends on: T3

**Files:** `internal/cli/close.go`, `internal/cli/close_flags_test.go`, `README.md`

Two variants of the close task 3 built. `--abandon` closes a brief whose plan did not complete, as `abandoned` — a status, not a deletion, so its runs and metrics stay and briefs that depend on it stay blocked. `--dry-run` lets the operator see exactly what a close would record, write and commit, while writing nothing. Both must keep every refusal task 3 established.

**Acceptance**

- `--abandon "<reason>"` lets close proceed whether or not the last run ended complete; it still requires `--finding` or `--no-findings`. The frontmatter status becomes `abandoned` and a body `**Status:** ready to plan` line becomes `**Status:** abandoned — <reason>`. The snapshot, run record and summary carry status `abandoned`; the commit is the same one commit, `[vloop] close <run id>` with the `Vloop-Brief:` trailer, holding the same kinds of file.
- After an abandon, `vloop brief close` refuses the brief as `already abandoned`, `vloop brief check` skips it, `vloop brief list` shows it with `-` and lists briefs depending on it as `blocked`, and `vloop metrics` reports it as `abandoned`.
- `--dry-run` applies every refusal first, with the same messages and exit codes. It then prints the summary block the real close would print (the new status, findings counted as operator defects), followed by `would record <path>` per finding, `would write <snapshot path>`, `would update <brief path>` and `would commit [vloop] close <run id>`, and nothing after. It writes no file, creates no directory, stages and commits nothing, and moves no ref.
- Committed tests `TestCloseAbandon…` and `TestCloseDryRun…` in internal/cli/close_flags_test.go, each with a fixture where the flag applies and one where a refusal still wins.
- README documents `--abandon` and `--dry-run` and stays under its 200-line cap.

### T5 — Add `vloop metrics export`: JSON Lines of briefs, tasks and defects with the repository's identity

`done` · depends on: T1, T2

**Files:** `internal/cli/export.go`, `internal/cli/export_test.go`, `internal/cli/metrics.go`, `internal/metrics/`, `internal/runs/`, `README.md`

Consolidating metrics across repositories only reads: each repository exports its own records, and anything bigger reads the export. The export carries numbers and titles, never code, and identifies the repository by its origin with any credentials stripped. Every record is `export/v1` (task 1), and the brief record is exactly `vloop metrics --json` without `by_task`, so the two can never disagree.

**Acceptance**

- `vloop metrics export [<brief>…]` prints JSON Lines on stdout — one record per line and nothing else — for the named briefs, or by default every brief with runs, in name order: the brief record, its tasks in plan order, then its derived defects by iteration, then its recorded defects by id. A named brief with no runs is `vloop: no runs for <name>`, exit 1.
- The brief record is the brief's metrics/v1 document, computed by the code `vloop metrics --json` uses, without `by_task`, with `schema: export/v1`, `type: brief` and `repo`.
- A task record carries brief, run_id, id, and title and status from the plan at the brief's last run commit, plus area, kind, attempts, churn, agent_ms, cost_usd and models with exactly the values of the matching `by_task` row.
- A defect record carries brief, run_id, id, task, origin, found_by, kind, severity, status, summary and derived. Derived ids come from task 2's function (`<run id>/i<iteration>-gate`, `<run id>/i<iteration>-review-<n>`); a derived defect's severity and status are null.
- `repo.remote` is origin's URL with any userinfo removed (`https://user:tok@example.com/acme/shop.git` → `https://example.com/acme/shop.git`, `ssh://git:pw@example.com:2222/acme/api.git` → `ssh://example.com:2222/acme/api.git`), or null without an origin; `repo.name` is the remote's last path segment without `.git`, else the repository directory's name. It is read with the `git` command; nothing touches the network.
- Nothing else leaves: no file contents, no absolute path, no environment, no credential, no field outside export/v1. Every line validates against export/v1, and the export writes nothing.
- Committed tests `TestExport…` in internal/cli/export_test.go: record order and fields, derived ids for a gate failure and for several review findings, and credential stripping with a fixture where it applies and one where it must not, plus no origin.
- README documents `vloop metrics export` and stays under its 200-line cap.

### T6 — Add `--workspace <file>` to `vloop metrics` and `vloop metrics export`

`done` · depends on: T5

**Files:** `internal/cli/workspace.go`, `internal/cli/workspace_test.go`, `internal/cli/metrics.go`, `internal/cli/export.go`, `internal/config/`, `README.md`

A workspace file lists clones of several repositories, lives in a repository of its own, and lets one command show all their metrics side by side or concatenate their exports — reading only, never writing into any of them. Each row and each record must be exactly what that repository reports on its own, so the workspace view adds a `repo` column and nothing else.

**Acceptance**

- A workspace file is TOML: `[[repo]]` tables with `path`, resolved relative to the workspace file's own directory (not the working directory), and an optional `name`. It is parsed with the TOML library already in go.mod.
- `vloop metrics --workspace <file>` prints the cross-brief table with a leading `repo` column: one row per brief per repository, repositories in file order, and every row after its `repo` cell equal to that repository's own `vloop metrics` row. It runs from any working directory, including one outside every git repository.
- `vloop metrics export --workspace <file>` concatenates each repository's `vloop metrics export`, in file order, with `repo.name` replaced wherever the file sets `name`; the metrics table uses that name in its `repo` column too.
- A listed path that does not exist or is not a git repository prints `vloop: workspace repo not found: <path as written>` on stderr, one line per such path; the other repositories are still reported and the command exits 1.
- `--workspace` together with `<brief>` arguments is a usage error: exit 2, one `vloop: ` line on stderr, nothing on stdout.
- --workspace reads only: nothing is written into any listed repository or beside the workspace file.
- Committed tests `TestWorkspace…` in internal/cli/workspace_test.go: two fixture repositories, the row equality, the name override, a missing path and a non-repository path, each with a counterpart where the rule must not fire.
- README documents `--workspace` and stays under its 200-line cap.
