### T1 — Build the run test harness: scratch repository, fake home, a stub claude scripted by prompt, and a smoke test

`done` · depends on: none

**Files:** `cmd/vloop/run_harness_test.go`

Every later task proves `vloop run` with Go end-to-end tests that run the real binary against a stub `claude` in a scratch repository, so the harness comes first and is shared. It replaces `.loop/tests/lib.sh`: a vloop-initialised git repository on `main`, a fake home that marks it trusted, and a stub that logs its arguments and plays a per-test script chosen by the prompt it receives. Later tasks must be able to plant any failure through the script alone (no proposal, no output, a non-zero exit, a git command, a cost), so they never need to edit the harness.

**Acceptance**

- cmd/vloop/run_harness_test.go provides helpers that create a scratch git repository on branch `main` with a git identity set in the repository's own config, initialised with the built binary's `vloop init`, holding a ready loop brief, all committed
- The helpers create a fake home whose `.claude.json` marks the scratch repository trusted (`projects[<path>].hasTrustDialogAccepted: true`), and every binary or stub invocation gets HOME, USERPROFILE and XDG_CONFIG_HOME pointing into temporary directories and GIT_CONFIG_GLOBAL/GIT_CONFIG_NOSYSTEM neutralised
- A stub `claude` is put first on PATH: it appends its full argv to a log the test can read, answers `--version` and `plugin list --json`, and for `-p` prompts `/vloop:plan <brief>`, `/vloop:work <id>` and `/vloop:review <id>` runs a per-test script that can write the plan, write files, write or omit `.vloop/tmp/proposal.json` and `.vloop/tmp/verdict.json`, run git commands, print the result JSON (with `total_cost_usd`, `duration_ms`, `num_turns`, `is_error`, `permission_denials` and `modelUsage` keyed by the model it was given) or print nothing, and exit with a chosen code
- The stub's script can vary by task and by attempt (for example: fail the first review of T1, pass the second) without editing the harness file
- The binary is the one TestMain builds once (`binPath`); the harness does not build another
- `TestRunHarness` exists in package main of cmd/vloop and passes: in a harness repository with the stub on PATH, `vloop doctor` exits 0 reporting 0 problems, and invoking the stub with `-p "/vloop:work T1" --model sonnet` performs its scripted action, prints JSON whose `modelUsage` is keyed `sonnet`, and is recorded in the argument log
- No test reads or writes this repository's `.loop/`, `.claude/`, `.vloop/`, its git history or the real home directory
- Where the stub cannot run on the host OS the harness skips with `t.Skip` naming the reason; it never passes vacuously on darwin or linux

### T2 — Add the six run.* budget keys to config, with VLOOP_RUN_* variables, validation and the config list update

- Committed tests in internal/config and internal/cli cover the defaults, the order, precedence, and each validation rule with a value that passes and one that fails

### T4 — Add `vloop run` with its flags and preflight, the work branch, the plan session, the plan checks and the plan commit

`done` · depends on: T1, T2, T3

This is where `vloop run` comes into existence: parse its flags and budgets, refuse on preflight problems, put the run on its work branch (R-2), run the plan session through T3's path, check the plan as the shell driver does, and commit it as `[vloop] plan <run id>`. `--plan-only` stops there, which is what lets this task be proven before iterations exist. The planning-side shell scenarios are ported here; 21 and 30 also exercise iterations, so they are ported in T5.

**Acceptance**

- `vloop run [<brief>] [--plan-only] [--replan] [--max-iterations N] [--cost-ceiling USD] [--max-attempts N] [--stall-limit N]` exists; each budget resolves flag > VLOOP_RUN_* > file > default through T2's keys
- Preflight runs doctor's checks and refuses (exit 1) on any problem before any branch, session or file change
- A brief path that does not exist is `vloop: brief not found: <path>`, exit 2 (scenario 29), with nothing changed: no session, no branch, no run folder, plan untouched; `--help` and an unknown flag leave the plan untouched too
- On the default branch `run` creates branch `<run id>` and switches to it before planning, printing `created and switched to branch <run id>` on stdout; if that branch exists it prints `vloop: branch <run id> exists — switch to it and re-run`, exit 1, changing nothing; on any other branch it runs there
- The plan session is `/vloop:plan <brief path>` through T3's session path; its record is `sessions/001-plan.json` (`iteration` 0, no `task`) in `.vloop/state/runs/<run id>/<YYYYMMDD-HHMMSS>/`
- The plan written by the session must be valid `state/v1` and pass every `vloop task validate` check; on top the driver applies the shell driver's checks — dangling references, the three gate-shape rules (re-serialised parse / source text, a file the task does not own, a decaying baseline) and the head-diff advisory, which warns naming the task but does not refuse. ### T5 — Run one iteration end to end: task choice, work, gates with timing and the env ids, review, the outcome, journal, plan.md, and the commit behind a HEAD check

**Files:** `internal/cli/run.go`, `internal/driver/`, `internal/driver/iterate.go`, `internal/driver/iterate_test.go`, `cmd/vloop/run_iterate_test.go`

This is the driver's core loop: pick the first ready task, start a work session, run every gate, review, apply the outcome, record it, commit once (R-1) — ending `complete` or `blocked` when nothing is left. Its records must be exactly what B3's metrics read (`iteration/v1`, `verdict/v1`, `[vloop] <task>: <outcome>` subjects) because T9's snapshot and summary are computed from them. **Acceptance**

- Each iteration takes the first pending task (plan order) whose depends_on are all done, starts `/vloop:work <id>`, then runs that task's gate and every done task's gate in the plan's shell from the repo root with `VLOOP_ACTIVE_TASK` = the iteration's task and `VLOOP_GATE_TASK` = the gate's task; sessions never see either variable

- Before every commit the driver checks HEAD is still on the run's branch; if not it halts with exit 9 and commits nothing (`TestRunHeadCheck`)
- The run ends `complete` (exit 0) when every task is done or `blocked` (exit 2) when tasks remain but none is ready, sets the plan status, and makes the closing commit `[vloop] run <run id>/<folder>: <status>`; the working tree is clean afterwards

### T6 — Handle gates across iterations: regressions, rewrites, blocked tasks whose gate passes, flaky gates and gate disputes

`done` · depends on: T5

**Files:** `internal/cli/run.go`, `internal/driver/`, `internal/driver/gates.go`, `internal/driver/gates_test.go`, `cmd/vloop/run_gates_test.go`

Gates are the regression net: every done task's gate re-runs each iteration, and the driver must tell apart a regression, a session rewriting the gate it is judged by, a work session that blocks while its gate passes, a flaky gate and a disputed one. Flaky gates and disputes are new in vloop: a flaky gate gets one immediate re-run and is recorded rather than charged; a disputed gate blocks for the operator, who keeps the judgement. The driver itself never edits a gate — reverting a session's rewrite of a gate file restores what HEAD holds; it does not touch `verify`.

**Acceptance**

- A done task whose gate fails during another task's iteration goes back to pending with attempts+1 and the run log line `GATE REGRESSION <id>` also names the iteration's task (scenarios 03, 41)
- A session that modifies a file its own task's verify names, that existed at HEAD from someone else, and that is not in the task's files has that file restored from HEAD before the gate runs, with `GATE REWRITE <task>` in the run log; creating such a file, a file in the task's files, and a retry editing its own earlier attempt's file are not reverted (scenario 33)
- A work session that reports blocked while its gate passes is recorded as blocked and its notes, the run log and the run-end report say the gate passes (scenario 39)
- A failing gate is run once more at once with nothing changed; if that passes the iteration continues as a pass, the record's gate is `{"exit": 0, "duration_ms": …, "flaky": true}`, the run log says `FLAKY GATE <task>`, and no attempt is charged; a gate that fails both runs is `gate_failed`; a gate that passes first time has no `flaky` key
- A proposal with `gate_dispute` blocks its task at once: status `blocked`, notes exactly `gate disputed: <reason> — <evidence>`, attempts unchanged, no review session; the run continues with other ready tasks and ends `blocked`, exit 2, if none remain
- The driver never edits, replaces or disables a task's `verify`, including on a dispute
- Ported tests `TestRun03GateRegression`, `TestRun33GateRewrite`, `TestRun39BlockedGatePasses`, `TestRun41RegressionNamesBoth` each assert everything their shell scenario asserts; `TestRunFlakyGate` and `TestRunGateDispute` each cover a fixture where the behaviour applies and one where it must not

### T7 — Halt the run: budgets with flag precedence, convergence, stall, session errors, repeat-blocked and moved refs

`done` · depends on: T5

**Files:** `internal/cli/run.go`, `internal/driver/`, `internal/driver/halt.go`, `internal/driver/halt_test.go`, `cmd/vloop/run_halt_test.go`

A run must always stop with the plan coherent and with one of R-3's exit codes, so the operator can tell what happened and whether re-running resumes. Budgets are per run and checked between iterations, which is what makes `--max-iterations` and `--cost-ceiling` halts resumable by raising the limit and re-running. The halts that want the operator first — not converging, session error, repeat blocked, refs moved — must commit nothing that a moved ref could misplace.

**Acceptance**

- Between iterations the driver checks, per run: iterations ≥ `run.max-iterations` → exit 4; spend ≥ `run.cost-ceiling` → exit 6; iterations per closed task > `run.convergence-max` once iterations ≥ `run.convergence-min` → exit 5; each budget resolved flag > VLOOP_RUN_* > file > default
- An iteration that closes nothing and charges no attempt adds to the no-progress streak; reaching `run.stall-limit` ends the run `stalled`, exit 3
- A session that fails to run (non-zero exit or `is_error`) halts with exit 7 and charges no attempt; a repeated block with nothing changed halts with exit 8 surfacing the first diagnosis (scenario 42)
- Refs and HEAD are snapshotted before every session and compared after; any difference halts with exit 9, the run log says `REFS MOVED <task|plan>` listing what moved, and nothing — iteration or closing commit — is committed
- Plan status is `stalled` for exit 3 and `halted` for 4–9; halts that commit write the closing commit `[vloop] run <run id>/<folder>: <status>`
- Re-running after exit 4 or 6 (with a higher limit) resumes the same plan without a new plan session, in a new run folder, and can complete

### T8 — Make the run safe and its records sound: containment, preflight refusals, the run lock, git identity, state tampering, the empty run, rendered views, telemetry and layout

`done` · depends on: T5

**Files:** `internal/cli/run.go`, `internal/driver/`, `internal/driver/safety.go`, `internal/driver/safety_test.go`, `cmd/vloop/run_safety_test.go`

A run writes only inside the repository (`.vloop/` and the tree sessions changed), refuses to start where it cannot be trusted, cannot be run twice in one working tree, and leaves records every later reader can rely on. These are the shell driver's safety and records scenarios; the port is what proves vloop kept them. Records matter twice: B3's metrics, T9's snapshot and the operator all read them, and a fabricated session record would be a lie in all three.

**Acceptance**

- Preflight refuses (exit 1) an untrusted workspace and a repository without git user.name/user.email before any session, branch, plan or commit; it warns, without refusing, about an active pre-commit hook (scenarios 18, 23)
- A run lock under `.vloop/tmp/` stops a second `vloop run` in the same working tree (exit 1, naming `git worktree add` as the alternative), clears a stale lock with a warning, is removed when the run ends, and is never committable (scenario 22)
- A session that modifies `.vloop/state/state.json` has it restored; the run log says `STATE TAMPERING <task>` and the iteration fails as `gate_failed` whatever the gate said (scenario 24)
- Nothing is written outside the repository; no tracked file holds an absolute path or the user name; `$HOME` in anything a session reported reaches committed records as `~`; `.vloop/tmp/` is never committed (scenario 10)
- A run with `--max-iterations 0` exits 4 with zero iterations and still prints its end-of-run report (scenario 13); `.vloop/state/plan.md` is what `vloop status --markdown` renders and re-rendering is deterministic, and the journal opens with the plan report, has one entry per iteration and closes with the run's ending (scenario 14)
- Every session record validates against `session/v1` and every `iterations.jsonl` line against `iteration/v1`; session files are name-sortable in run order, the plan session is iteration 0, work/review pair per iteration (scenario 15)
- Run folders are `.vloop/state/runs/<run id>/<YYYYMMDD-HHMMSS>/`; the journal is one per plan and a resumed run appends to it (scenario 20)
- A session that prints nothing gets no record and the run log says `SESSION RECORD MISSING <phase> <task|-> (iteration <n>)`; `vloop metrics` reports the missing record
- Ported tests `TestRun10Containment`, `TestRun13EmptyRunSignals`, `TestRun14RenderedViews`, `TestRun15TelemetryContract`, `TestRun18PreflightUntrusted`, `TestRun20ParallelSafeLayout`, `TestRun22RunLock`, `TestRun23GitIdentity`, `TestRun24StateTampering` each assert everything their shell scenario asserts, translated; `TestRunSessionRecordMissing` covers a silent session and a normal one
