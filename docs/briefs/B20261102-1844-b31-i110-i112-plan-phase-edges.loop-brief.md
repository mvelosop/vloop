## Executive summary

Three small gaps, each found by a run of the B26–B30 chain. B29 could not
start: B28's finished plan referenced two files B28 had moved, and the
preflight validates whatever plan is on disk, so the operator deleted it by
hand (#110). The plan commit stages the whole tree, so a file a plan or
gate-review session changes outside the plan's own files is committed with
the plan; only the fence stands in the way, and for Copilot its hook fails
open (#111). And `brief-review/v1` accepts any string as `brief`, while the
driver accepts only the brief's name, so the review-brief skill could say
"path", and its example agree, without any test noticing; Copilot followed
it in B29's acceptance and its report was rejected (#112).

**The goal:** a finished plan of another brief never blocks a run; a plan
or gate-review session's changes outside `.vloop/state/` and `.vloop/tmp/`
never reach the plan commit; and the schema rejects every `brief` the driver
rejects, so a skill example that drifts fails the existing skills test.

- **V1 — a finished plan does not block the next brief (#110).** `vloop
  run` naming another brief does not validate a complete `state/v2` plan;
  `vloop doctor` on its own reports one as a pass (`a complete plan of
  <brief> — the next brief's plan replaces it`). Resuming
  a plan, or any plan not complete, is validated as today.
- **V2 — the plan phase reverts what its sessions change elsewhere
  (#111).** After each plan session and each gate-review session, every
  path changed outside `.vloop/state/` and `.vloop/tmp/` is reverted and
  named in a warning, as the review and verify sessions' are.
- **V3 — `brief-review/v1`'s `brief` is a brief's name (#112).** The
  schema gains a pattern on `brief`, in place: no `/` or `\`, ending
  `.loop-brief`. No other report field is tightened: the audit found none
  the driver compares.

Unchanged: the fences and the Copilot hook; the clean-tree requirement at
start; `vloop doctor`'s other checks; every other schema, session, report
and exit code.

Three driver-and-schema fixes, each with its tests and the documentation

## Why this shape, and what was rejected

- **One brief for three issues.** Each is small, they touch disjoint
  files (the doctor, the plan phase, one schema), and every task leaves the
  checks green. *Rejected:* three briefs, three runs of plan, verify and
  close for about 200 lines.
- **#110: exempt only a complete plan of another brief.** The planner
  resets another brief's plan anyway (`the plan … was for … resetting and
  planning fresh`), so validating it protects nothing; `0a87d5a` did the
  same for a complete `state/v1` plan. A resume (no brief named, or the
  plan's own brief named) keeps the validation: its plan is the one the run
  goes on with. *Rejected:* exempting every complete plan, resume included
  — no gain, and a resumed plan's broken reference would surface later, in
  its own gates. *Rejected:* exempting any plan of another brief, whatever
  its status — an unfinished plan is work the operator may mean to resume,
  and the doctor's problem is how they learn it is broken.
- **`vloop doctor` on its own passes a complete plan.** It names no brief,
  so it cannot know what runs next; a complete plan is almost always a
  finished brief's. It passes with the plan's brief in the message, so the
  operator sees which. *Rejected:* keeping the problem in the bare doctor
  — that is what made B29's operator delete the plan by hand.
- **#111: revert and warn, per session (operator's decision).** The guard
  runs around each plan session and each gate-review session, as the review
  and verify sessions' guards do, rather than once before the commit:
  a change a plan session makes to a source file would otherwise be in the
  tree while the gates are checked on the base, and could make a gate fail
  or pass there for the wrong reason. Per session, the warning also names
  the session that made the change. *Rejected:* halting before the plan
  commit — the operator chose reverting, as the other sessions' guards do,
  and a halt would throw away a plan the gate review may have accepted.
  *Rejected:* one guard before the commit only — it cannot say which
  session changed a file, and it comes after the base gate checks.
- **What planning may write: `.vloop/state/` and `.vloop/tmp/`.** The same
  rule as the review's guard (`reviewMayWrite`): the driver writes its run
  folder and journal under `.vloop/state/`, the plan session the plan and
  gate folders, and `.vloop/tmp/` is never committed. *Rejected:* narrowing
  it to S-4's exact list (the plan and its gate folders) — a session that
  writes elsewhere under `.vloop/state/` is a state guard's job, which is
  out of scope here.
- **#112: tighten `brief-review/v1` in place (operator's decision).** B29
  set the rule that a published schema does not change. This is a stated
  exception, because no report the driver accepts today becomes invalid:
  `vloop brief review` takes only a `*.loop-brief.md` file
  (`internal/cli/brief_review.go`), and the driver accepts only `brief ==`
  that file's base name without `.md` (`internal/driver/briefreview.go`),
  which has no separator and ends `.loop-brief`. *Rejected:* publishing
  `brief-review/v2` — the churn of B30's `verify/v2` (skill, driver, docs,
  tests) for no change in what is accepted.
- **The audit of the other reports finds nothing to tighten.** The driver
  reads `verdict/v1`, `proposal/v1`, `gate-verdict/v2` and `verify/v2`, and
  compares none of their fields with the run: a verdict's or proposal's
  `task`, and a gate verdict's `tasks[].task`, are recorded or printed,
  never checked against the task the driver started. `brief-review/v1`'s
  `brief` is the only field compared. *Rejected:* adding patterns to those
  `task` fields — they would reject reports the driver accepts today, which
  is a `/v2` question for its own issue.

## Behaviour contract

### V1 — a finished plan does not block the next brief

- In `vloop run`'s preflight, a plan with `schema` `state/v2` and `status`
  `complete` is not validated when the run names a brief and that brief's
  path differs from the plan's `brief`. The `plan` check passes and prints
  nothing (the preflight prints only problems and its named warnings).
- In `vloop doctor`, run on its own, a complete `state/v2` plan is not
  validated either. The `plan` line is:

  ```
  ✓ plan a complete plan of <plan's brief> — the next brief's plan replaces it
  ```

  `<plan's brief>` is the plan's `brief` field as stored (a repo-relative
  path). `vloop doctor --json` carries the same message, result `pass`.
- **Validated as today:** a plan whose status is not `complete` (planning,
  running, blocked, any other); a complete plan when `vloop run` names no
  brief or names the plan's own brief (a resume); every `state/v1` plan,
  whose two cases stay as they are.
- `vloop task validate` is unchanged: it validates whatever plan is there.

### V2 — the plan phase reverts what its sessions change elsewhere

- Before each plan session (the first and each revision after a gate
  review) and each gate-review session, the driver snapshots the working
  tree as the review session's guard does, leaving out `.vloop/state/` and
  `.vloop/tmp/`. After the session, and before anything else reads the tree
  (the gates on the base, the verdict, the commit), it reverts every path
  changed since the snapshot: a tracked file is restored, a new file is
  removed, a deleted file is put back.
- Each reverted path is one warning, on stderr and in the run's `run.log`,
  in path order:

  ```
  vloop: the plan session changed <path> — reverted
  vloop: the gate-review session changed <path> — reverted
  ```

- A path the driver cannot revert halts the run, exit 1, before the plan
  commit, with `the plan session changed files the driver could not revert:
  <path>: <error>` (`gate-review` for that session), as the review's guard
  does. Not gated: there is no portable way to make a revert fail.
- Order after a session: the existing checks of moved refs and changed git
  configuration run first and still halt as today, reverting nothing. Then
  the revert runs, and only then is the session's ending judged as at the
  base: a plan session that timed out or exited non-zero, and a gate-review
  session that timed out, halt as today, after their stray changes are
  reverted (and warned), so the re-run does not meet the clean-tree
  refusal; a gate-review session's exit code is treated as at the base (its
  verdict is read). No new halt.
- Nothing else changes: the plan commit still stages the tree and leaves
  out `.vloop/tmp/`; a run whose sessions changed nothing outside those two
  folders prints exactly what it printed at the base.

### V3 — `brief-review/v1`'s `brief` is a brief's name

- `schemas/brief-review.v1.json`: `brief` becomes
  `{"type": "string", "pattern": "^[^/\\\\]*\\.loop-brief$"}` (in the
  file's JSON: no `/` or `\`, ending `.loop-brief`; `.loop-brief` alone
  passes, because a brief file named only .loop-brief.md passes the command's
  suffix check and the driver accepts that name).
  Nothing else in the schema changes; its title stays `brief-review/v1`.
- The driver's own check (`brief` equal to the brief's file name without
  `.md`) stays, and its refusal line is unchanged.
- The `brief-review/v1` cases of `internal/schema/schema_test.go` built
  from the two literals whose `brief` is `b` change it to `B1-x.loop-brief` (the contract changes what they
  pin), and gain the planted cases of the worked example.

### Decided here, because the cited documents leave it underdetermined

- The bare `vloop doctor` passes a complete plan (the issue asked for the
  pass; the brief says the bare doctor is where it shows).
- The message names the plan's `brief` field as stored, not its run id: the
  operator recognises the brief.
- The guard wraps each session, not the commit (see "Why this shape").
- The schema's pattern also rejects `\`, so a Windows path is caught the
  same way.

### Violations the review must rule on

- A test that pins today's behaviour changed for any reason other than the
  contract changing it: only the `brief-review/v1` cases of
  `internal/schema/schema_test.go` whose `brief` is `b` may change their
  values, and the callers of `runDoctor` and `runPreflight` only their
  arguments.
- A plan or gate-review session's change that reaches the plan commit, or
  is still in the tree when the gates are checked on the base.
- A complete plan of another brief validated, or a resumed plan not.

## Worked example

Gated with stub plan and gate-review sessions in fixture repositories, as
the base's run tests do (`cmd/vloop/`); the verify session cannot run
`vloop run`, so these lines are covered by the tests the plan writes there,
and the doctor and schema lines run as written.

**V1.** Fixture: a repository on a work branch whose committed plan is
`state/v2`, `status` `complete`, `brief`
docs/briefs/B20260101-0900-a.loop-brief.md (in the fixture), run id
`B20260101-0900-a` (a run id is the brief's name), `branch` the current branch, and whose T1
references docs/old.md, which a later commit removed; and a ready brief
docs/briefs/B20260101-0910-b.loop-brief.md. `<n>` is the count
`vloop task validate` prints on that fixture (the gate computes it).

```
vloop doctor
  -> ✓ plan a complete plan of docs/briefs/B20260101-0900-a.loop-brief.md — the next brief's plan replaces it
     (the line among the others; exit as the other checks decide)

     planning goes on; with the stubs the run completes            exit 0

vloop run docs/briefs/B20260101-0900-a.loop-brief.md
  ->   ✗ plan <n> problem(s) — run vloop task validate
     vloop: preflight failed — 1 problem(s), nothing has run         exit 1

vloop run
  -> the same two lines                                              exit 1
```

Planted: the same fixture with the plan's `status` `running`, then `vloop run
docs/briefs/B20260101-0910-b.loop-brief.md` → the same two lines, exit 1,
nothing ran.

**V2.** Fixture: a repository whose tracked files include `README.md`.
The stub plan session writes a valid plan with its gate folders, and also

  the two notes mark what V2 supersedes.
- Patterns on `verdict/v1`'s, `proposal/v1`'s or `gate-verdict/v2`'s `task`
  fields, or the driver checking them against the task it started.
- The bare `vloop doctor`'s other checks, and its wording for a plan that
  is not complete.
- The Copilot hook failing open (#82), and any fence change.
- The ready merge's stray `Vloop-Brief:` trailer on B30's ready commit.

## Constraints

- Go, at the version in `go.mod`; no new dependencies.
- Must keep building and passing on macOS, Linux and Windows.
- **Gates run on macOS's BSD tools**, and **no gate runs `claude`,
  `copilot`, `gh` or touches the network**: stub agents stand in, as in
  B16 and B24–B30.
- Tests build their fixtures in temporary directories and address them with
  `git -C`; sessions never move refs.
- **Gates follow the diff surface; a gate never runs the suite (P-8).**
- **No task may weaken a check to pass.** An earlier test changes only where
  it pins behaviour the contract changes (the `brief-review/v1` cases of
  `internal/schema/schema_test.go` built from the two literals whose
  `brief` is `b`), and only to the new behaviour; the existing callers of
  `runDoctor` and `runPreflight` (`internal/cli/doctor_copilot_test.go`,
  `internal/cli/doctor_second_review_test.go`) change only to pass the new
  parameter, with no brief, and keep every assertion; the work
  session names the contract item in its notes and the review cites it.
- **New tooling is proven by fixtures, including where it must fail**: every
  line of the worked example and each planted failure.
- Repo-relative paths everywhere. No absolute paths in any file or commit
  message.

## Shape

4 to 5 tasks, each verifiable by a single command. Order is load-bearing:

1. **V3 — the schema**: the pattern, the changed and planted schema cases,
   the real-data check over the kept brief reviews. Gated on
   `vloop schema validate` with the worked example's six reports and the
   schema and skills tests.
2. **V1 — the doctor and the preflight**: a complete plan of another brief
   passes; a resume and an unfinished plan are validated. Gated with the
   fixture and every V1 line, planted case included.
3. **V2 — the plan phase's guard**, around each plan and gate-review
   session. Gated with the stub sessions and every V2 line, planted cases
   included.
4. **Docs**: the configuration guide's sentence, the plan page's paragraph,
   the session page's two sentences and the fence audit's two notes, each
   literal as the contract gives it, wrapped in each file's own style. The
   gate searches each file with its lines joined and runs of whitespace
   collapsed to one space (for example `tr -s ' \n' '  '` before
   `grep -F`), so the wrapping is free and the words are not.
   Prose: if it fails review twice on wording, block it and the operator
   finishes it. Gated on a grep per sentence.
5. **Close:** every gate at once, and the worked example line for line.
