## Executive summary

A Copilot session is fenced by a `preToolUse` hook, `vloop fence hook`.
Copilot runs the call anyway when the hook prints anything but its JSON
answer, or outlives `timeoutSec` (documented, and probed in B22.3). The
hook always answers and is fast, but nothing behind it notices when a call
got through: the driver commits whatever the session did. And the hook's
program is the `vloop` binary, outside the repository, which no one has
checked a session cannot change.

**The goal:** a Copilot session that ran a call its fence denies, or during
which the hook's binary changed, halts the run before the driver uses
anything the session produced; and the hook gets four times its time.

- **F1 — the driver re-judges every call that ran.** After each Copilot
  session, every tool call the session started and Copilot did not deny is
  judged again by the session phase's fence, as the hook judges it. One
  denied call halts the run with exit 9.
- **F2 — the hook's binary is checked.** Its SHA-256 before the session and
  after; a change halts the run with exit 9.
- **F3 — `timeoutSec` 30 → 120.**
- **F4 — the docs:** every place that defines exit 9 (the domain's S-2
  and R-3, the session and run pages, the concepts guide's table, `vloop
  run`'s and `vloop brief review`'s help, the operate skill's halt table),
  the configuration guide's fence section, the fence audit, and B22.3's
  note.
- Unchanged: Claude sessions; the hook's own answers; every fence's rules;
  a session whose calls all pass.

## What it is

A check after the fact that makes the hook's fail-open visible: the fence
judge is deterministic, so a call it denies that nonetheless ran can only
have got past the hook. It turns a silent breach into a halt with the
calls named, at the point where `REFS MOVED` already halts.

## Why this shape, and what was rejected

Decided by the assistant on 2026-11-03 under the operator's delegation.
**Do not re-litigate these** — the planner inherits them.

- **Re-judge the calls, not match the hook's decisions.** Every call a
  Copilot session runs is in its JSON Lines (`tool.execution_start`), and
  the judge gives the same answer twice. Every call goes through the hook:
  in the 7 Copilot sessions the acceptance clones kept (B27–B32), all 140
  calls were judged by a `preToolUse` hook, none skipped it, so a call the
  judge denies that ran can only have got past the hook. Round 2 of this
  brief's review re-checked it: 132 of the calls ran, and the fence denies
  none of them, so F1 would have halted none of those runs.
  *Rejected:* having the hook log its decisions for the driver to match —
  the log would sit where a session that got past the hook could write it,
  and the payload carries no call id to match on.
- **Halt with exit 9, like a moved ref.** A breached fence is the same kind
  of event: something a session must never do happened, and only the
  operator can judge the damage.
  *Rejected:* failing only the session (an attempt charged) — the work tree
  may hold what the fence exists to prevent; a new exit code — 9 already
  means "a guard tripped; restore before resuming".
- **Hash the hook's binary.** Cheap, and answers B22.3's open question
  whatever a probe would find.
  *Rejected:* a one-off probe — it says nothing about the next session.
- **`timeoutSec` 120.** The hook answers in milliseconds; a timeout only
  ever lets the call run, so the limit only has to be far above any real
  stall.

## Behaviour contract

### F1 — the driver re-judges every call that ran

- After every Copilot session, of every phase (plan, gate-review, work,
  review, second-review, verify, review-brief), the driver reads the
  session's JSON Lines. A **call that ran** is a `tool.execution_start`
  whose `tool.execution_complete` of the same `data.toolCallId` does not
  carry `data.error.code` `denied`, or that has no completion.
- Each call that ran is judged by the session phase's fence judge (the same
  `fence.New(phase, root, home)` the hook builds, `second-review` judged as
  the hook judges it), with the tool, path and command read from
  `data.toolName` and `data.arguments` exactly as the hook reads them from
  its payload, and with the hook's own rule before the judge: a `bash` or
  `powershell` call with an empty command is denied (`the <tool> call has
  no command the hook can read`). `internal/fence` imports `internal/driver`, so the driver
  cannot import the judge: the re-judge lives where the import graph allows
  (the driver taking it as a function, say); the mechanics are the plan's.
  The check belongs to vloop's phases, not to `Runner.Run`:
  `tools/agent-eval`'s sessions are scored, not halted, and its tests stay
  unchanged.
- One or more denied: the driver prints, on stderr, one line per denied
  call, `vloop: <tool> <what> — <the judge's reason>`, `<what>` the call's
  path, or else the first line of its command cut to 200 characters (runes,
  `…` added when cut), or else nothing (and then `vloop: <tool> — <reason>`);
  then it halts with exit 9 and the message `FENCE BYPASSED <phase> — the
  session ran <n> call(s) its fence denies; nothing from it was used`. The
  per-call lines and the halt are warnings like `REFS MOVED`'s: masked
  (`$HOME` as `~`) and written to the run log too where the phase has one
  (`vloop brief review` has none: there, stderr only). F2 then F1 run as
  soon as the session ends, before the phase's own checks; when one halts,
  the phase still makes its restores as today (the driver's inputs; a
  review-brief session's brief) before exiting 9, and a restore that fails
  is reported after the halt's lines. So a call that got past the hook and
  also moved a ref is named first. The
  session's record is kept as for any session; the halt comes where `REFS
  MOVED` halts for that phase, before the phase uses the session's report
  or anything is committed. The work tree is left as the session left it,
  except what each phase already restores (a review-brief session's brief).
- No call denied: nothing changes, nothing is printed.

### F2 — the hook's binary is checked

- `Runner.Run` hands the phase the session's stdout whether or not it
  printed a result event, so a session killed at its timeout is re-judged
  too.
- Before each Copilot session the driver takes the SHA-256 of the binary the
  hook runs (the one `writeCopilotHooks` writes into the hooks file); after
  the session, again. A difference, or a binary gone, halts with exit 9 and
  `HOOK CHANGED <phase> — the binary the fence hook runs changed during the
  session: <path>; nothing from it was used`, `<path>` the binary's path as
  the hooks file names it, masked as F1's lines are, at the same point as
  F1. F2 is checked
  before F1.

### F3 — `timeoutSec`

The hooks file's `timeoutSec` is `120`, for every phase.

### Decided here, because the cited documents leave it underdetermined

- A call with no completion counts as having run: Copilot may be killed
  mid-call.
- The check runs whatever the session's exit: a timed-out or failed session
  may still have run calls.
- The hook's own `deny` answers need no check: they appear as `denied`
  completions.

### Violations the review must rule on

- A Claude session's handling changed.
- A fence's rules changed, or the re-judge using a judge other than the
  hook's.
- The halt placed after the session's output is used or anything is
  committed.
- A call that ran left unjudged because its tool is one the judge does not
  name (the judge already decides unknown tools).

## Worked example

With the stub `copilot` of `cmd/vloop`'s harness, `agent.work =
"copilot"`, a plan of one task. The stub today answers only review prompts
and emits no tool events: it gains, in test code, the prompts of every
phase (`/vloop:<phase>` with or without an argument) and the tool events a
test's copilot-script.sh asks for. The judge's
reasons are `vloop fence check`'s for the same call.

```
(these first three lines are one `cmd/vloop` test each)
the work session's JSON Lines: a bash call "git commit -m x" (toolCallId c1),
  completed without error
  -> stderr "vloop: bash git commit -m x — git commit -m x is denied by the work fence (Bash(git commit:*))",
     "FENCE BYPASSED work — the session ran 1 call(s) its fence denies; nothing from it was used",
     exit 9; no new commit on the branch
the same call completed with data.error.code "denied"
  -> no FENCE BYPASSED; the iteration goes on as today
a bash call "ls" only
  -> no FENCE BYPASSED; the iteration goes on as today
a driver test of the phases' shared after-session check, phase work: the
  hook's binary a copy of a file (not a running binary), which the test
  changes between the check's before and after
  -> the halt "HOOK CHANGED work — the binary the fence hook runs changed during the session: <the copy's path>; nothing from it was used",
     exit 9
a driver test: a stub Copilot session run through Runner.Run with a Timeout
  of 1 s, which prints a started bash call "git commit -m x" and sleeps;
  what Runner.Run returns, handed to the shared after-session check, phase work
  -> the FENCE BYPASSED work halt: a killed session is re-judged, and a call
     with no completion counts as run
the hooks file the driver writes, read by a new test           -> "timeoutSec": 120
agent.<phase> = "copilot", a session of that phase that runs a bash call "git push",
  for each of the seven phases, one test each:
  plan (vloop run)             -> "FENCE BYPASSED plan — …", exit 9, no plan commit
  gate-review (vloop run)      -> "FENCE BYPASSED gate-review — …", exit 9, no plan commit
  work (vloop run)             -> "FENCE BYPASSED work — …", exit 9, no new commit
  review (vloop run)           -> "FENCE BYPASSED review — …", exit 9, no new commit
  second-review (vloop run, run.second-review = "record")
                               -> "FENCE BYPASSED second-review — …", exit 9, no new commit
  verify (vloop run, the last task done)
                               -> "FENCE BYPASSED verify — …", exit 9, the verify report not used
  review-brief (vloop brief review)
                               -> "FENCE BYPASSED review-brief — …", exit 9, the brief restored
  each "…" is "the session ran 1 call(s) its fence denies; nothing from it was used",
  each preceded on stderr by "vloop: bash git push — git push is denied by the <fence> fence (Bash(git push:*))",
  <fence> the fence the phase uses (vloop fence check names it)
```

F2's line is a driver test because `vloop run` points the hook at its own
executable, which a test cannot change while it runs (on Linux, writing a
running binary fails).

## Out of scope

- The fence's compound commands (#83).
- Claude sessions, whose fence is Claude Code's own.
- Reverting what a bypassing session changed: the operator decides.
- A probe of the binary's writability beyond F2.

## Constraints

- Gates run on macOS's BSD tools: no empty alternatives in `grep -E`, no
  `sed -i` without a suffix, no `\+` or `\|` in basic regexes.
- Sessions never move refs.
- Tests build their fixtures in temporary directories and address them with
  `git -C`; Copilot is the harness's stub; no test runs a real `copilot`.
- The existing tests pass unchanged, except a test that pins the stub
  `copilot` refusing a prompt it now accepts: that test changes only to
  pin a prompt the stub still refuses. None pins `timeoutSec` today, so F3
  gains a test.
- A docs gate joins lines and collapses whitespace before it greps, so an
  edit wrapped in the file's style passes.
- Repo-relative paths everywhere.

## Shape

4–5 tasks; every configured check green after each.

1. **F1's re-judge**, with fixture JSON Lines: the calls that ran, judged.
2. **F1's halt in every phase, and F2.** Gated on the worked example's
   seven phase lines and the F2 line, each a named test.
3. **F3 and F4.**
4. **Close:** every gate at once, and the worked example line for line.
