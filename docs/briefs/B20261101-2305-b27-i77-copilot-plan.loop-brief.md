## Executive summary

Copilot can run work, review, second-review, verify and gate-review sessions,
fenced by `vloop fence hook`, but the plan session that splits a brief into
tasks and writes their gates is Claude's only: `agent.plan` accepts `claude`
alone, and the hook knows no `plan` phase.

**The goal:** an operator sets `agent.plan = "copilot"` and a Copilot model,
and every plan session of the run runs on the GitHub Copilot CLI, under the
plan fence, with the plan it writes checked exactly as a Claude plan is.

- **P1 — the hook judges plan sessions.** A `plan` phase for `vloop fence
  check` and `vloop fence hook`, with the review phase's rules, the plan
  fence's deny rules, and the plan's write rule: writes only to
  `.vloop/state/state.json`, under `.vloop/state/gates/` and under
  `.vloop/tmp/`; `rm` denied.
- **P2 — Copilot runs the plan session.** `agent.plan` accepts `copilot`; the
  session runs under the hook's `plan` phase; the run preflight and doctor
  check it as they check the other Copilot phases.
- **A1 — the docs and the acceptance kit.** The fence audit, the guide and the
  domain pages say what a Copilot plan session may do; the kit gains a plan
  run on the real CLI.

Unchanged: Claude sessions — their argv, fence and settings; Copilot work,
review, second-review, verify and gate-review sessions, their decisions and
argv; everything the driver does with a plan (its schema and shape checks, the
base gates, the gate review, the rounds, the plan commit); the driver's checks
stay the boundary (S-2).

## What it is

At the end, `agent.plan = "copilot"` is accepted, experimental, and each plan
session of a run (the first and the revision a failed round asks for) runs on
Copilot under a hook that lets it write the plan and its gates and nothing
else. Every agent key then accepts `copilot`. It is for operators who want the
plan written by a model of another family, with Claude's gate review and
reviews judging it.

## Why this shape, and what was rejected

Decided on 2026-11-01 under the operator's delegation. **Do not re-litigate
these** — the planner inherits them.

- **The plan phase has the review phase's rules with S-4's plan write rule**:
  `fence/plan.json`'s `Bash(…)` deny rules (the same rules as
  `fence/review.json` at the base), the adapter's whole deny list, `rm:*`
  included, and writes allowed exactly where the plan fence allows them:
  `.vloop/state/state.json`, under `.vloop/state/gates/`, under
  `.vloop/tmp/`. *Rejected:* dropping `rm:*` as in the work phase — the
  planner overwrites a gate's files with the file tools and needs no `rm`; a
  revision that leaves a stale fixture behind is what the gate review reads.
  *Rejected:* allowing all of `.vloop/state/` — the run folders, journals and
  metrics there are the driver's.
- **`sh <script>` stays denied**, as in every phase: the hook cannot judge a
  script it does not see. The plan skill runs a gate with
  `vloop task gate <id>`, which the hook allows. Judging scripts or shell
  syntax is issue #83.
- **The driver handles a Copilot plan as it handles a Claude one.** The one
  wording change: a plan session that exits non-zero names its agent,
  `planning session failed (copilot exited <n>) — see <run folder>`; a Claude
  session's line stays `(claude exited <n>)`. *Rejected:* falling back to
  Claude when a Copilot plan session fails — it hides the agent's failure, and
  the operator chose the agent.
- **Copilot plan is experimental**, like the other Copilot phases.
- **The acceptance model is `gpt-5.6-terra`**, on the URL shortener template's
  brief, as for B24–B26. The brief pins no model: the operator sets
  `model.plan`.
- **The binary never calls the network**; acceptance on the real CLI is the
  operator's, at close.

## Behaviour contract

### P1 — the `plan` phase of `vloop fence`

`vloop fence check` and `vloop fence hook` accept `--phase plan`, alongside
`review`, `second-review`, `work`, `verify` and `gate-review`. Everything B22
and B24–B26 pinned for those phases stays, byte for byte, including their
messages, except the unknown-phase message below. In `plan`, a call is decided
exactly as in `review`, with four differences:

- the deny rules are `fence/plan.json`'s `Bash(…)` rules, and the shell denial
  names that fence: `<command> is denied by the plan fence (Bash(<rule>))`;
- a write is allowed when its path, resolved against `--root`, is
  `.vloop/state/state.json`, or lies under `.vloop/state/gates/` or under
  `.vloop/tmp/` (the directories themselves are not writable targets); any
  other write:
  `write to <path> is not allowed in a plan session: only .vloop/state/state.json, .vloop/state/gates/ and .vloop/tmp/ may be written`;
- the tool denial names the phase: `tool <name> is not allowed in a plan session`;
- the skill hint names plan's skill: `skill <name> is not vloop's — use /vloop:plan`.

The deny-list stems are the review phase's, `rm:*` included:
`<command> is denied by the Copilot deny list (<stem>)`. Reads are judged as
in review.

An unknown phase: `unknown phase "<p>": want review, second-review, work, verify, gate-review or plan`,
exit 2 for `fence check`; the deny line and exit 2 for `fence hook`.
`vloop fence check --help` and `vloop fence hook --help` name `plan` among the
phases, in their usage, their `--phase` flag and their long help.
`docs/guide/commands.md`, generated from that help, is regenerated
(`go generate ./...`) in the same task, so `TestCommandsReferenceIsCurrent`
stays green.

### P2 — the Copilot plan session

- `agent.plan` accepts `claude` (default) and `copilot`, with
  `VLOOP_AGENT_PLAN` as today.
- A plan session on copilot runs `/vloop:plan <brief path>` exactly as a
  Copilot gate-review session runs `/vloop:gate-review` — the plugin by
  `--plugin-dir`, a fresh home under `.vloop/tmp/`, the guidelines as custom
  instructions, the whole deny list on the argv (`--deny-tool=shell(rm:*)`
  included), the JSON Lines parsed into the `session/v4` record
  (`phase: "plan"`, `agent: "copilot"`, credits, `cost_source`,
  `permission_denials`) — with one difference: the hooks file runs
  `vloop fence hook --phase plan`. P-6 resolves its model and effort as for
  any plan session.
- Everything the driver does around the plan session is unchanged, whatever
  the agent: the line `planning from <brief> using <model>`; a moved ref or
  git setting halts with exit 9; a timeout halts with exit 7; a plan that is
  missing, fails `state/v2` or the gate-shape checks halts with exit 1; the
  base gates, the gate review and the two rounds; the plan commit. The one
  change is the exit line above.
- `vloop run`, when `agent.plan` is `copilot`:
  - warns `  ! agent.plan is copilot: experimental (docs/guide/configuration.md)`;
  - refuses to start, exit 1, while `model.plan` is the default:
    `vloop: agent.plan is copilot but model.plan is the default "opus", a Claude alias: set model.plan to a Copilot model id`;
  - applies the Copilot checks the other phases have: `copilot` on PATH and
    runnable, a GitHub login reaching its sessions, and K1's refusal of a
    project skill named like one of vloop's.
  `vloop doctor` shows the same rows for `agent.plan`. Planning has no switch
  to turn it off, so the key is in use whenever it is `copilot`, also on a
  resume that will not plan, as B26 decided for the gate review.

### Decided here, because the cited documents leave it underdetermined

- **A path written after a `cd`** is resolved against `--root`, as in every
  phase: `cd .vloop/state/gates/T1 && echo x > f` is denied.
- **The operator's commands stay denied.** `vloop task verify`, `vloop task
  set` and `vloop task drop` are in `fence/plan.json`; the planner writes the
  plan file, it does not drive the CLI that amends one.
- **The write rule follows the plan fence, not S-4's wording alone.** S-4 says
  the plan session writes "the plan and its gate folders"; the fence allows
  exactly `.vloop/state/state.json`, `.vloop/state/gates/**` and
  `.vloop/tmp/**`, and the hook allows the same.
- **The fence files are not changed.**

### Violations the review must rule on

- A line of the worked example's tables that `fence check --phase plan`
  decides otherwise, or with another reason.
- Any change to the other phases' decisions or messages (bar the
  unknown-phase message), to a Copilot work, review, verify or gate-review
  session's argv, or to a Claude session's argv, fence or settings.
- A Copilot plan session started without the hooks file, with another phase
  in it, or without `--deny-tool=shell(rm:*)` on its argv.
- A Copilot plan handled differently from a Claude one by the driver, bar the
  exit line.
- A gate that runs `copilot` or touches the network.

## Worked example

`vloop fence check --phase plan --root . --tool bash "<command>"` in a fresh
`git init` repository, printing `allow` with exit 0 or `deny: <reason>` with
exit 1:

```
allow   vloop task gate T1
allow   vloop schema validate state/v2 .vloop/state/state.json
allow   mkdir -p .vloop/state/gates/T1
allow   printf '{}' > .vloop/state/state.json
allow   echo 'exit 1' > .vloop/state/gates/T1/gate.sh
allow   echo x > .vloop/tmp/p/out.txt
deny    echo x > .vloop/state/journals/a.md            -> deny: write to .vloop/state/journals/a.md is not allowed in a plan session: only .vloop/state/state.json, .vloop/state/gates/ and .vloop/tmp/ may be written
deny    echo x > src/app.go                            -> deny: write to src/app.go is not allowed in a plan session: only .vloop/state/state.json, .vloop/state/gates/ and .vloop/tmp/ may be written
deny    cd .vloop/state/gates/T1 && echo x > f         -> deny: write to f is not allowed in a plan session: only .vloop/state/state.json, .vloop/state/gates/ and .vloop/tmp/ may be written
deny    rm .vloop/state/gates/T1/old.sh                -> deny: rm .vloop/state/gates/T1/old.sh is denied by the Copilot deny list (rm:*)
deny    sh .vloop/state/gates/T1/gate.sh               -> deny: sh: runs a script or stdin, not a literal -c string
deny    vloop task drop T2                             -> deny: vloop task drop T2 is denied by the plan fence (Bash(vloop task drop:*))
deny    sh -c "git push origin main"                   -> deny: git push origin main is denied by the plan fence (Bash(git push:*))
deny    env gh pr list                                 -> deny: gh pr list is denied by the Copilot deny list (gh:*)
deny    echo $(date)                                   -> deny: command substitution cannot be judged
```

## Out of scope

- Copilot for the brief review (#94), and moving the brief skills into the
  plugin (#101).
- Judging scripts, `if`, `for`, `while`, `$(…)` or subshells (#83), or
  following `cd`.
- Judging the targets of `cp`, `mv`, `tee` or other commands that write
  without a redirection: what the audit already lists as neither.
- Comparing the hook's decisions with Copilot's tool calls (#82), or raising
  the hook's `timeoutSec`.
- Any change to `fence/plan.json`, the other fences, the plan skill, or Claude
  sessions.
- Reverting a file a plan session changed outside the files it may write: the
  plan commit stages the whole tree today, for any agent.
- A model-qualifying eval runner (#81); a replacement for `gpt-5.6-terra`
  (#84); Foundry (#80); other providers (#85).
- Dropping the experimental label.

## Constraints

- Go, at the version in `go.mod`; no new dependencies.
- Must keep building and passing on macOS, Linux and Windows; the path rules
  are pure functions tested on every OS.
- **Gates run on macOS's BSD tools**, and **no gate runs `copilot`, `gh` or
  touches the network**: a stub agent stands in, as in B19, B22 and B24–B26.
- Tests build their fixtures in temporary directories and address them with
  `git -C`; sessions never move refs.
- **Gates follow the diff surface; a gate never runs the suite (P-8).**
- **No task may weaken a check to pass.** An earlier test changes only where it
  pins behaviour the contract changes (here, the unknown-phase message,
  `agent.plan` accepting `copilot`, the Copilot adapter supporting the plan
  phase (`TestCopilotSupportsWorkReviewAndVerify`), the fence commands
  accepting `plan` (`TestUnknownPhase` and `TestFenceHookFailsClosed`'s
  `plan phase` case move to another unknown name), and the plan session's
  exit line), and only to the new behaviour; the
  work session names the contract item in its notes and the review cites it.
- **New tooling is proven by fixtures, including where it must fail**: every
  line of the worked example, the unchanged lines, each planted failure.
- Repo-relative paths everywhere. No absolute paths in any file or commit
  message.

   review twice on wording, block it and the operator finishes it.
5. **A1 — the acceptance kit.**
6. **Close:** every gate at once, and the worked example line for line.
