## Executive summary

`[[check]].run` and every gate run in the shell `shell` names, and left
unset that is the OS default: `sh` on macOS and Linux, `pwsh` on Windows
(`internal/config/config.go:60`, `defaultShell`). A repository worked on from
two OSs has no way to keep its checks and gates runnable on both. This
repository showed it: its check was `sh` syntax, so on Windows `vloop run`
refused to plan until #157 moved the check into `go run ./tools/check` and set
`shell = "pwsh"` by hand. Nothing stops the next gate from calling `grep`,
which Windows does not have.

**The goal:** a repository says which platforms its team works on; with more
than one, vloop makes pwsh the one shell everywhere, from the shared config
only, and refuses a gate that calls a tool some of those platforms do not have.

- **M1 — the platforms key.** A shared `platforms` list (`linux`, `macos`,
  `windows`); set only in `.vloop/config.toml`.
- **M2 — one shell for a mixed team.** With two or more platforms, `shell`
  must be `pwsh` in `.vloop/config.toml`; a local file or `VLOOP_SHELL` that
  sets it is an error; doctor and `vloop run` refuse otherwise.
- **M3 — portable gates.** With two or more platforms, the driver refuses a
  plan whose gates call a command from a fixed list of platform-specific
  tools; the plan and gate-review skills write and judge gates in pwsh cmdlets
  and the project's own toolchain.
- **M4 — doctor's other findings.** `gate shell` is a problem when pwsh is
  missing on a mixed team; a warning when a repository has `[[check]]`s and
  does not set `shell` in `.vloop/config.toml`; a warning for a check that calls a listed
  tool.
- **M5 — documents, and this repository as the first user.** A "Mixed teams"
  section in the configuration guide, the domain rule, the roadmap's inherited
  decision, and `platforms = ["macos", "windows"]` here.

Unchanged: every repository without `platforms`, or with one platform, behaves
as today, except M4's default-shell warning; plans keep their recorded shell
(P-5); the five shells and their invocation.

## What it is

A repository-level declaration of the OSs its team uses, and the rules that
follow from declaring more than one: pwsh, set once in the shared config, and
gates that use only pwsh commands and the project's toolchain, enforced when a
plan is accepted. It is for a team on Windows and macOS (or Linux) sharing one
repository, like the client and the operator who use this one.

## Why this shape, and what was rejected

Decided with the operator on 2026-11-25. **Do not re-litigate these** — the
planner inherits them.

- **When the OSs are mixed, everyone uses pwsh.** pwsh is the one shell native
  on Windows, macOS and Linux, and the plan already records its shell (P-5),
  so a plan made on one OS runs on another. *Rejected:* writing gates in `sh`
  and requiring Git Bash or WSL on Windows — a second toolchain on every
  Windows machine, and `sh` on Windows still lacks BSD and GNU tools in
  different ways; `powershell` (Windows PowerShell 5.1) — it exists only on
  Windows and has no `&&`.
- **Any two or more platforms require pwsh, `linux` and `macos` included.**
  BSD and GNU `grep`, `sed`, `date` and `mktemp` differ (a GNU-only pattern
  already stalled a run here), so a macOS and Linux team has the same problem
  in `sh`. One rule is simpler than a matrix. A team that does not want it
  leaves the key unset. *Rejected:* requiring pwsh only when `windows` is
  mixed with another platform — it leaves the BSD/GNU split unguarded.
- **The key is `platforms`, values `linux`, `macos`, `windows`.** `macos`, not
  Go's `darwin`, because people write it. *Rejected:* `os` — reads as a single
  value.
- **`platforms` and, with two or more, `shell` belong to the shared file.** They
  are facts about the repository's team, like `[[check]]` (B39), and a
  machine that overrides them writes gates the others cannot run. An override
  is an error, not ignored: a setting silently ignored surprises the person
  who set it. *Rejected:* ignoring the override with a warning.
- **Portability is enforced by a driver lint and taught by the skills.** The
  driver already refuses gate shapes that can never pass
  (`internal/driver/gateshape.go`); a command from a fixed list is one more,
  checked the same way, deterministic, and its list lives in one place. The
  plan skill is told what to write instead, and the gate review treats any
  other tool missing on a declared platform as `unpassable`. *Rejected:* the
  skills alone — a judgment the model can miss; running gates under a
  restricted `PATH` — the project's toolchain (`go`, `node`, `pnpm`) lives
  beside `grep` in the same directories, so no `PATH` separates them.
- **The default-shell finding is a warning.** Single-OS repositories, the
  common case, keep working on upgrade. *Rejected:* a problem — it would stop
  every existing repository with checks.
- **The plan does not record `platforms`.** The lint reads the config when the
  plan is accepted; the plan already records the shell, which is what governs
  its gates (P-5). *Rejected:* a new plan field — a schema change with no
  reader.

## Behaviour contract

### M1 — the platforms key

- **Key:** `platforms`, a list, valid entries `linux`, `macos`, `windows`. No
  default (empty). In `.vloop/config.toml`: `platforms = ["macos", "windows"]`;
  in `vloop config set`: `vloop config set platforms macos,windows`.
- **Invalid entry:** the existing list-key message,
  `vloop: invalid value "macos,beos" for platforms: want a comma-separated list of linux, macos, windows`,
  exit 2 from `config set`; exit 1 with the file path prefix when read from
  `.vloop/config.toml`.
- **The platforms are distinct entries:** `["macos", "macos"]` is one
  platform. Wherever vloop prints them in a message, they are deduplicated
  and sorted (`linux`, `macos`, `windows`) and joined with `, `.
- **Shared file only.** `platforms` in .vloop/config.local.toml is an error
  wherever the config is read, exit 1:
  `vloop: .vloop/config.local.toml: platforms belongs in .vloop/config.toml — the platforms are the repository's, not one machine's`.
  `VLOOP_PLATFORMS`, set and not empty, is the same error with its own name:
  `vloop: VLOOP_PLATFORMS: platforms belongs in .vloop/config.toml — the platforms are the repository's, not one machine's`.
  `vloop config set --local platforms …` is refused with that line too, exit
  2, and writes nothing.
- **A mixed team** is a repository whose `platforms` has two or more distinct
  entries. Every rule below that says "mixed" means this.

### M2 — one shell for a mixed team

- **Shared file only, when mixed.** `shell` in .vloop/config.local.toml, or
  `VLOOP_SHELL` set and not empty, is an error wherever the config is read,
  exit 1, whatever its value (`pwsh` included):
  `vloop: .vloop/config.local.toml: shell belongs in .vloop/config.toml while platforms lists macos, windows — the checks and the gates are written for one shell`
  (or `vloop: VLOOP_SHELL: shell belongs …`, the rest the same). `vloop config
  set --local shell …` is refused with the same line, exit 2, writes nothing.
  Without a mixed team, both overrides work as today.
- **Doctor row `platforms`,** right after `config.local` (after `config` when
  there is no `config.local` row):
  - no `platforms` set, or the `config` row is a problem: no row;
  - mixed, and `shell` not set in `.vloop/config.toml`: problem,
    `✗ platforms macos, windows need shell = "pwsh" in .vloop/config.toml; it is not set`;
  - mixed, and `shell` set there to anything but `pwsh`: problem,
    `✗ platforms macos, windows need shell = "pwsh" in .vloop/config.toml; it is "sh"`
    (the value it has);
  - otherwise, when this machine's OS is not in `platforms` (Go's `darwin` is
    `macos`; another OS is its Go name): warning,
    `! platforms this machine (linux) is not one of macos, windows`;
  - otherwise: `✓ platforms macos, windows` (a single platform prints alone:
    `✓ platforms windows`).
- **`vloop run`'s preflight** fails on the `platforms` problem (counted like
  any problem, nothing runs) and prints the `platforms` warning, both on
  stderr in the preflight's form, two spaces then the symbol.

### M3 — portable gates

- **The listed commands**, in this order wherever a test or a document lists
  them:
  `awk`, `basename`, `bash`, `cat`, `chmod`, `cmd`, `cmp`, `cp`, `cut`,
  `date`, `diff`, `dirname`, `env`, `fc`, `find`, `findstr`, `grep`, `head`,
  `ln`, `ls`, `mkdir`, `mktemp`, `mv`, `powershell`, `printf`, `readlink`,
  `rm`, `robocopy`, `sed`, `seq`, `sh`, `sleep`, `sort`, `stat`, `tail`,
  `tee`, `test`, `touch`, `tr`, `uniq`, `wc`, `which`, `xargs`, `xcopy`,
  `zsh`.
  Each is a native tool on some platforms only, or a pwsh alias on Windows
  that runs a different native tool elsewhere (`cat`, `ls`, `sort`, `cp`,
  `mv`, `rm`, `sleep`, `tee`, `diff`; `mkdir` is a pwsh function on Windows;
  `find` is Windows' `find.exe`). `echo`, `cd`, `pwd` and `where` are pwsh
  aliases on every platform and are not listed.
- **A command word** is the word in command position: the first word of the
  command, and the first word after `;`, `|`, `&&`, `||`, a newline, `{`,
  `(`, `$(` and the call operator `&`, each of these separators counted only
  outside single and double quotes. A word in command position that is wholly
  quoted (`& 'grep'`, `& "/usr/bin/GREP.exe"`) is a command word, its quotes
  removed; a quoted word anywhere else is data. A word that starts with `$`,
  `-`, `@`, `[` or a digit is not one. It matches a listed command when its last
  path element (after `/` or `\`), with a trailing `.exe` removed, equals it,
  ignoring case: `grep`, `GREP`, `/usr/bin/grep` and `grep.exe` all match;
  so do `& 'grep'` and `& "/usr/bin/GREP.exe"`; `Select-String -Pattern
  'grep'`, `go test -run TestGrep` and `node -e "require('fs')"` do not.
- **When mixed, at plan acceptance,** the driver refuses the plan for each
  task whose `verify` holds a listed command word, and for each `.ps1` file
  under the task's gate folder (`.vloop/state/gates/<task id>/`, at any depth)
  that holds one on any line, naming the first listed command found in
  each:
  `gate shape rejected: T2  calls wc, which is not on every platform in platforms (macos, windows); use a pwsh cmdlet or the project's own toolchain`
  and, for a file,
  `gate shape rejected: T1  .vloop/state/gates/T1/gate.ps1 calls grep, which is not on every platform in platforms (macos, windows); use a pwsh cmdlet or the project's own toolchain`.
  A refused plan is handled as the existing gate-shape refusals are. Without a
  mixed team, no gate is checked for this.
- **The plan skill,** in its "In the plan's shell" bullet: when `vloop config
  get platforms` lists two or more platforms, every gate is pwsh using pwsh
  cmdlets (`Select-String`, `Test-Path`, `Get-Content`, `Measure-Object`,
  `New-Item`, `Remove-Item`, `Join-Path`, `[System.IO.Path]::GetTempPath()`)
  and the project's own toolchain, never a listed command, and a gate script
  in the gate folder is a `.ps1` run with `pwsh -NoProfile -File <path>`; the
  BSD-tools advice stays for `sh` on macOS.
- **The gate-review skill,** in section 2: when `platforms` lists two or more
  platforms, a gate that calls a tool not present on every one of them is
  `unpassable`, even when it passes on the machine that reviews it.

### M4 — doctor's other findings

- **`gate shell` when mixed and no plan is in use:** pwsh missing from `PATH`
  is a problem, `✗ gate shell the configured shell "pwsh" is not on PATH`
  (today a warning). With a plan in use, the plan's recorded shell governs
  the row exactly as today (P-5), mixed or not. Without a mixed team the row
  is as today.
- **The default shell:** when `[[check]]` tables exist, `platforms` is not set,
  and `shell` is not set in `.vloop/config.toml`, the `checks` row warns:
  `! checks shell is not set in .vloop/config.toml, so each machine runs the checks in its own (pwsh here): set it there`,
  where the parenthesis holds the value `shell` resolves to on this machine,
  whatever its source: the OS default (`pwsh` on Windows, `sh` on macOS and
  Linux), the local file or `VLOOP_SHELL`. `vloop run` does not print it. With
  `platforms` set (one platform or more), there is no such warning.
- **A check that calls a listed command,** when mixed: one `checks` warning
  per such check, naming the first listed command in its `run`, as M3 finds
  command words:
  `! checks go calls grep, which is not on every platform in platforms (macos, windows)`.
  `vloop run` prints it.

### M5 — documents, and this repository

  `platforms` (execution: the shell rule and the gate lint, C-5).
- `docs/design-notes/vloop-roadmap.md`, "Decisions every brief in the series

- `README.md`: the Windows bullet names the "Mixed teams" section. The README

- `.vloop/config.toml` holds `platforms = ["macos", "windows"]`, beside the

  back.
- `docs/guide/commands.md` is regenerated (`go generate ./...`) if any
  command's help changes, as its test requires.

### Decided here, because the cited documents leave it underdetermined

- The shared-only errors apply to every command that reads the config, not
  only `vloop run`, as B39's local `[[check]]` refusal does.
- A plan already accepted keeps its shell (P-5); nothing re-checks its gates
  when `platforms` is set later. Its next plan is checked.
- `vloop task verify`, the operator's own replacement of a gate, is not linted.
- The lint reads `.ps1` files only: a gate script in another language is run
  by a listed command (`sh`, `bash`) or by the toolchain, which the `verify`
  check already sees.

### Violations the review must rule on

- A repository without `platforms` whose doctor, run or plan acceptance output
  changes, other than M4's default-shell warning.
- An override of `shell` honoured on a mixed team, or refused on one that is
  not.
- A listed command matched inside a quoted string, or a pwsh keyword
  (`if`, `foreach`, `exit`) reported as a command.
- The list of commands stated differently in two places (the code, the guide,
  the skills).
- A test this run adds that skips on Windows, or that runs a real `claude` or
  `copilot`.

## Worked example

In a fresh git repository in a temporary directory, with `vloop init` run and a
`[[check]]` whose `run` is `go version`:

```
$ vloop doctor          (shell not set, platforms not set)
! checks shell is not set in .vloop/config.toml, so each machine runs the checks in its own (pwsh here): set it there
                                         ((sh here) on macOS and Linux)   exit 0
$ VLOOP_SHELL=bash vloop doctor
! checks shell is not set in .vloop/config.toml, so each machine runs the checks in its own (bash here): set it there
$ vloop config set platforms windows,macos
$ vloop config get platforms
windows,macos                                                    exit 0
$ vloop doctor
✗ platforms macos, windows need shell = "pwsh" in .vloop/config.toml; it is not set   exit 1
$ vloop config set shell pwsh
$ vloop doctor
✓ platforms macos, windows                                       (on Windows or macOS)
! platforms this machine (linux) is not one of macos, windows    (on Linux)
$ VLOOP_SHELL=pwsh vloop config get shell
vloop: VLOOP_SHELL: shell belongs in .vloop/config.toml while platforms lists macos, windows — the checks and the gates are written for one shell   exit 1
$ vloop config set --local shell pwsh
vloop: .vloop/config.local.toml: shell belongs in .vloop/config.toml while platforms lists macos, windows — the checks and the gates are written for one shell   exit 2
$ vloop config set --local platforms linux
vloop: .vloop/config.local.toml: platforms belongs in .vloop/config.toml — the platforms are the repository's, not one machine's   exit 2
$ vloop config set platforms macos,beos
vloop: invalid value "macos,beos" for platforms: want a comma-separated list of linux, macos, windows   exit 2
```

`vloop config get platforms` prints the value as stored (`windows,macos`), as
every list key does today; only messages sort the platforms.

Plan acceptance with `platforms = ["macos", "windows"]` and `shell = "pwsh"`,
each `verify` in its own task of a test plan:

```
go test ./x; if ($LASTEXITCODE) { exit 1 }; (Get-Content out.txt | Measure-Object -Line).Lines     accepted
Select-String -Pattern 'grep' -Path a.txt                                                          accepted
node -e "require('fs')"                                                                             accepted
if (Test-Path a) { wc -l a }
  -> gate shape rejected: T4  calls wc, which is not on every platform in platforms (macos, windows); use a pwsh cmdlet or the project's own toolchain
go test ./x | /usr/bin/GREP.exe ok
  -> gate shape rejected: T5  calls grep, which is not on every platform in platforms (macos, windows); use a pwsh cmdlet or the project's own toolchain
& 'grep' -n ok a.txt
  -> gate shape rejected: T7  calls grep, which is not on every platform in platforms (macos, windows); use a pwsh cmdlet or the project's own toolchain
pwsh -NoProfile -File .vloop/state/gates/T6/gate.ps1     (gate.ps1's second line: $o = go test ./x | grep ok)
  -> gate shape rejected: T6  .vloop/state/gates/T6/gate.ps1 calls grep, which is not on every platform in platforms (macos, windows); use a pwsh cmdlet or the project's own toolchain
```

The same plan with `platforms` unset: every task accepted by this rule.

A check whose `run` is `go test ./... | grep ok`, mixed:
`! checks go calls grep, which is not on every platform in platforms (macos, windows)`.

**Real data:** with `platforms = ["macos", "windows"]`, the rule refuses all 8
gates of B39's plan (`git show 4c69adf0:.vloop/state/state.json`, every
`verify` `sh .vloop/state/gates/T<n>/gate.sh`) and accepts every gate of a
pwsh plan built only from `go` and cmdlets. A test reads B39's plan from that
commit with `git -C`, and the count it asserts is computed from that plan's
tasks, not written in.

**Lines no session can run:** every line above is covered by tests the plan
writes that run on Windows, macOS and Linux without stub agents: the config
and doctor lines through the CLI in-process with temporary repositories, the
plan lines through the gate-shape rule with test plans and gate folders, and
the preflight through `vloop run` refusing before any session starts.

## Out of scope

- Stub agents that run on Windows, so the end-to-end tests stop skipping
  there.
- Linting `vloop task verify` replacements, existing plans, or gate scripts
  other than `.ps1`.
- `vloop init` asking for or detecting `platforms`.
- Changing this repository's operator and architect skills under `.claude/`
  (their "gates run on macOS's BSD tools" lines): the operator's, at close.
- Running a gate under a restricted `PATH`, or detecting tools by probing
  each platform.
- Copilot model ids (#153) and testing a head build (#154).

## Constraints

- Go, as pinned in `go.mod`; no new dependency.
- **This run's gates run in pwsh on Windows** (this repository's `shell`), and
  are written as M3 requires of a mixed team: pwsh cmdlets and `go` only, no
  listed command, a gate-folder script a `.ps1` run with
  `pwsh -NoProfile -File`.
- **A test this run adds runs on Windows, macOS and Linux.** No POSIX stub
  script, no skip on Windows.
- **A gate judges from outside the task (P-8).** It never runs the suite, a
  check, or a test the task writes; the `go` check runs those. It drives a
  `vloop` it builds from the work tree into a temporary directory, or runs
  oracle Go tests the plan puts in the task's gate folder
  (`go test ./.vloop/state/gates/<task id>/ -v`, which may import the
  module's internal packages). A gate that runs Go tests checks the output
  holds a `--- PASS:` line for each, because a skipped test passes. Go files in
  a gate folder are gofmt-clean: the check's `gofmt -l .` reads `.vloop/`.
- Sessions never move refs. Tests build their repositories in temporary
  directories and address them with `git -C`; no test touches this
  repository's own `.vloop/` or `.gitignore`.
- Tests that need agents use stubs; none runs a real `claude` or `copilot`, and
  none depends on what is installed on the machine.
- **Gates follow the diff surface.** Each task gates on the packages it
  touches, never on `./...`; the `go` check (`go run ./tools/check`) runs the
  whole suite after every task.
- **No task may weaken a check to pass.** An earlier test changes only where it
  pins behaviour this contract changes (doctor's rows when `[[check]]`s exist
  and `shell` is unset), and only to the new behaviour.
- Repo-relative paths everywhere. No absolute paths in any file or commit
  message.

## Shape

6 to 8 tasks, each independently verifiable by a single command. Order is
load-bearing:
