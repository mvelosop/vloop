# Brief — vloop B9: the gate model

- **Starting point:** extends `main` at the v2.0 roadmap (`23f1afb`, PR #13),
  after the v1.0.0 release (`fc0b67a`, tag `v1.0.0`). The planner pins the base
  it plans from as the **base** every gate compares against — never `HEAD~n`.
- **Produced by:** the design act of 2026-10-03, from
  `docs/design-notes/vloop-v2.0-roadmap.md` → "B9 — the gate model", with the
  forks settled with the operator (intervention recorded with this brief).
- **Run by:** `vloop run` from the released v1.0.0 — never from a binary built
  from the tree it changes. This run therefore plans and gates under the **v1**
  model it replaces; see Constraints.

## What it is

Today a gate is a task's `verify` that usually runs the tests the task itself
wrote, guarded by a gate-file rule that cannot tell a judge from a product, and
the union of the gates is the only regression net. After this run a gate
**judges the brief's contract by exercising the product**, with a judge the
planner wrote and no task can reach; the driver runs every gate on the base and
an independent **gate review** session confirms each fails for the right reason
before any work starts; and the repository's own tests and health checks run as
named **checks**, scoped by path, after every iteration and once in full at the
end. The plan becomes `state/v2`: tasks lose `files`, the plan gains its checks.

The blind spot this closes: in B8 two of 18 gates could never pass (T12, T17),
two regressions passed every per-task gate (T5, T15) and surfaced only in the
one gate that ran the whole suite, and the gate-file rule froze a task's own
product. Each gate followed its task's diff surface, its judge was often the
task's own output, and nothing judged the gates before the work spent attempts
on them.

## Why this shape, and what was rejected

Decided with the operator on 2026-10-03. **Do not re-litigate these** — the
planner inherits them.

- **A gate judges a contract; a gate may be a test.** Its judge is the
  planner's: assertions in the verify command, or oracle tests and fixtures in
  the plan's gate folder, run by the product's own runner. A gate never judges
  by anything a task wrote, and never runs the repository's suite — that is a
  check's job. *Rejected:* "gates never run tests" — it bans the planner's
  oracle tests, which are exactly a contract exercised through the product (a
  component render, a browser round-trip); the defect was ownership, not the
  mechanism.
- **Gate fixtures live in `.vloop/state/gates/<task id>/`, protected like the
  plan.** The plan session writes them; no other session can; the operator
  amends them only through `vloop task verify`, which records the change.
  *Rejected:* gate fixtures writable by work sessions — a worker that "fixes"
  the judge's seed data passes the gate without doing the work; *rejected:*
  "committed is trusted" (exploring-claude's HEAD comparison) — it leaves no
  `gate_history`, so earlier failures stay blamed on the work.
  The work session's **own** test fixtures stay its own, unprotected, judged by
  the checks and the review.
- **Oracle tests run from a git-ignored scratch folder inside the product.** A
  runner only finds and builds tests inside the projects it knows, so a gate
  copies its oracle into a scratch folder named in config, which must be
  git-ignored; the driver empties it after every gate and checks that a gate
  changed nothing else in the tree. *Rejected:* pointing each runner at
  `.vloop/state/gates/` (toolchain by toolchain); leaving cleanup to each gate
  (a crashed gate's copy rides into the commit through `git add -A`).
- **The driver runs every gate on the base, and each must fail; whether it
  fails for the right reason is the gate review's.** The three base checks of
  the plan skill ("fails at a behavioural assertion, fixtures read back,
  matchers exercised") move from the planner to the gate review — a planner
  checking its own gates grades its own homework. *Rejected:* the driver
  judging the reason from exit codes or patterns; the planner keeping the duty.
- **The gate review is a fourth session kind, `gate-review`,** with its own
  model and effort keys, fence, skill and verdict. A failed review sends the
  plan back to the planner **once**, with the findings; a second failure blocks
  the run (exit 2) for the operator, whose amendment is the ruling. *Rejected:*
  always to the operator (every plan waits on a human); reusing `review` with
  another prompt (model, effort, fence and metrics mixed).
- **Checks are named and scoped by path, from config.** `[[check]]` entries in
  `.vloop/config.toml`, each with a `name`, `paths` globs and a `run` command.
  After an iteration the driver runs only the checks whose paths match what the
  iteration changed; at the plan's start every check must pass on the base; when
  the last task is done every check runs once more. *Rejected:* one command that
  always runs everything (a Playwright suite after an API-only change);
  scoping left wholly to the repository's tooling (nothing for repos without
  Turborepo or Nx — which can still use one check with `paths = ["**"]`).
- **Done tasks' gates keep re-running every iteration.** A check covers the
  repository's tests; only the re-run covers a contract an oracle judged, since
  the oracle is not in the suite. Gates that no longer run suites are cheap.
  *Rejected:* checks only; one re-run of every gate at the end.
- **A timed-out gate is not re-run.** The one immediate re-run stays for an
  ordinary failure. *Rejected:* keeping it — a timeout cost twice its limit.
- **vloop 2 does not resume a `state/v1` plan.** It reads v1 records for
  metrics and writes v2. *Rejected:* migrating a v1 plan in flight — its gates
  were never reviewed and its `files` meant something v2 no longer enforces.

## Behaviour contract

Messages below are exact where quoted; `<…>` marks a value. Every refusal is one
line on stderr starting with `vloop: `.

### G1 — the plan is `state/v2`

**Required.** schemas/state.v2.json is `state/v1` with these changes, and no
others:

- a task has **no `files`**;
- a task gains **`fixtures`**: the SHA-256 of its gate folder (below), or `""`
  when it has none — stamped by the driver, never written by a session;
- a `gate_history` entry gains **`fixtures`**: the task's `fixtures` before the
  amendment;
- the plan gains **`checks`**: `[{name, paths, run}]`, copied by the driver from
  config (G4);
- the plan gains **`gate_scratch`**: the scratch folders, copied from config
  (G3);
- the plan gains **`gate_review`**: `{rounds, verdict}` — rounds taken (0–2)
  and the last verdict, `PASS`, `FAIL` or `""` before the first;
- `task.model` and `task.effort` stay `{work, review}`.

vloop writes `state/v2` and validates with it (`vloop task validate`,
`vloop schema validate state/v2`). `vloop run` with a `state/v1` plan on disk
refuses before anything else: `vloop: .vloop/state/state.json is a state/v1
plan — finish it with vloop 1.x or re-plan the brief` (exit 1). `vloop status`
still reads a `state/v1` plan; metrics read v1 records as today.

### G2 — gate fixtures are the planner's

**Required.**

- The plan session may write `.vloop/state/gates/<task id>/**` beside
  `.vloop/state/state.json`; the plan fence allows exactly those, and the work,
  review and gate-review fences deny them. A folder for an id not in the plan
  refuses the plan.
- At acceptance the driver stamps each task's `fixtures`: the SHA-256 over the
  folder's files, sorted by path, each as `<path>\0<contents>\0` — so the value
  is the same on every OS.
- The plan hash (`VLOOP_PLAN_SHA256`) covers `state.json` and every gate
  folder; the driver keeps both in memory, restores what any session changed
  among them after the session, and `vloop task gate` refuses on a mismatch as
  it does today.
- `vloop run` resuming a plan whose gate folder no longer matches the task's
  `fixtures` refuses: `vloop: the gate fixtures of T<n> changed outside vloop
  task verify — record the change with vloop task verify T<n> --reason '<why>'`
  (exit 1).
- `vloop task verify <id> [<command>] --reason '<why>'` — the command is now
  optional. It appends a `gate_history` entry with the old `verify`, the old
  `fixtures`, the reason and `by: operator`, then takes the command (if given)
  and re-stamps `fixtures` from the folder as it now is. With neither a new
  command nor a changed folder it refuses: `vloop: nothing to record — T<n>'s
  gate and fixtures are unchanged` (exit 1). Every earlier gate failure on the
  task becomes `origin: plan`, as today (M-4).
- **Gone:** gate-file detection (`GATE REWRITE`, the restore from HEAD of files
  a verify names) and the plan-time rejection of a gate that reads a tracked
  file its task does not own. The other gate-shape rejections and warnings stay.

### G3 — oracle scratch, and a gate leaves the tree as it found it

**Required.**

- `run.gate-scratch`: a list of repo-relative folders, default empty. Each must
  be ignored by git; otherwise `vloop run` refuses before planning: `vloop: gate
  scratch <path> is not ignored by git — add it to .gitignore` (exit 1). The
  plan copies the list (G1).
- After every gate run — in `vloop run`, at acceptance (G5) and in `vloop task
  gate` — the driver removes everything inside each scratch folder.
- The driver snapshots the tree before each gate and compares after it,
  ignoring `.vloop/tmp/` and the scratch folders. A gate that changed anything
  has it restored and **fails**, its log ending `vloop: gate T<n> changed the
  tree — restored: <paths>`.

### G4 — checks

**Required.**

- `[[check]]` tables in `.vloop/config.toml`, each `name` (unique, `[a-z0-9-]+`),
  `paths` (non-empty list of repo-relative globs, the `metrics` glob syntax) and
  `run` (one command in the configured `shell`). `vloop config list` prints each
  as `check.<name>=<run> (paths: <globs>)`. No environment override.
- **No check configured:** `vloop run` refuses before planning: `vloop: no check
  configured — add a [[check]] to .vloop/config.toml` (exit 1). `vloop doctor`
  reports it as a problem.
- **On the base:** before the plan session, every check runs; one that fails
  refuses: `vloop: check <name> fails on the base — fix it before planning: <log
  path>` (exit 1), and no session runs. The driver copies the checks into the
  plan at acceptance and again on every resume; a resume that changed them says
  so in `run.log`.
- **After each iteration**, when every gate that ran passed: the driver runs, in
  config order, every check with a glob matching a path the iteration changed
  (tracked changes against HEAD, and untracked files). A failure ends the
  iteration as **`check_failed`**: no review, attempts+1, the note names the
  check and its log. A check is never re-run for flakiness: it owns its flakes,
  and its exit code is the truth.
- **The final pass:** when the last task becomes done, every check runs once.
  A failure ends the run: `vloop: check <name> failed in the final pass — see
  <log path>` (exit 2, plan `blocked`); resuming with every task done runs the
  final pass again.
- Logs as for gates: `checks/<name>.log` (latest) and
  `checks/<iteration>-<name>.fail.log` in the run folder; base and final-pass
  logs are `checks/base-<name>.log` and `checks/final-<name>.log`.
- Checks run in the plan's shell, from the repo root, under `run.gate-timeout`,
  with the refs and git guards of a gate (exit 9).

### G5 — acceptance runs every gate on the base

**Required.** After the plan session, and after the plan's schema and gate-shape
checks, the driver runs every task's gate on the base, in plan order, with the
scratch and tree rules of G3. Each must **fail** (non-zero exit, timeout
included). The logs are kept as `gates/base-T<n>.log`. A gate that passes, or
that changed the tree, is an acceptance problem: `gate T<n> passes on the base`
/ `gate T<n> changed the tree on the base`. Acceptance problems go back to the
planner as a round of G6, not to a halt; a plan that fails the schema still
halts as today.

### G6 — the gate review

**Required.**

- A session of kind **`gate-review`**, invoked as `/vloop:gate-review` with no
  task, after G5 and before the first iteration. Config keys
  `model.gate-review` (default `sonnet`) and `effort.gate-review`; no per-task
  override. Its fence reads the repo, runs `vloop task gate` and writes only
  `.vloop/tmp/**`.
- It reads the brief, the plan, the gate folders and the base logs, and writes
  .vloop/tmp/gate-verdict.json, schema **`gate-verdict/v1`**: `task` absent;
  `verdict` `PASS` or `FAIL`; `tasks`: one entry per task, `{task, verdict,
  findings: [{summary, kind}]}`; `notes`. Finding kinds: `wrong-reason` (fails
  on the base for a reason other than the missing behaviour), `not-contract`
  (judges how the code is written, or internals the brief does not name),
  `task-reach` (its judge is, or reads, something a task writes), `unpassable`
  (no correct implementation could pass it), `pins-unnamed` (pins a name the
  brief does not). The plan's verdict is `FAIL` when any task's is. A missing or
  invalid verdict is `FAIL`.
- **Rounds.** A round is G5 plus the review. When it fails, the plan session
  runs again with the acceptance problems or the verdict's findings, revises
  the plan and its gate folders, and a second round follows. A second failure
  ends the run: `vloop: the gate review failed the plan twice — see <verdict
  path>; amend the gates with vloop task verify, then re-run` (exit 2, plan
  `blocked`). The verdicts are kept as `reports/gate-review-<round>.json`.
- **Resuming** a plan blocked at the gate review repeats G5 only; the
  operator's amendments are the ruling, and the review does not run again.
- Its session record is `session/v2` with `phase: gate-review`, iteration 0,
  no task. schemas/session.v2.json is v1 with the phase added.

### G7 — the iteration

**Required.** The sequence becomes: work session → own gate and every done
task's gate (G3's rules; a timed-out gate is not re-run) → checks (G4) →
review → one commit. schemas/iteration.v2.json is v1 with:

- `outcome` gains `check_failed`;
- **`checks`**: `[{name, exit, duration_ms}]` for the checks that ran, `[]`
  when none did.

The review session is told the checks' results and log paths and does not
re-run the tests; it still judges whether the task shipped tests for what it
built, from the diff.

### G8 — metrics

**Required.** `metrics/v2` is v1 with: time gains `checks_ms` and
`gate_review_ms`; every per-phase object (cost, models, effort, missing
records) gains `gate-review`. A check failure is a derived defect `origin:
work`, `found-by: gate`, `kind: regression` — the export's catchers do not
change. Closed briefs' snapshots stay `metrics/v1`.

### G9 — init, upgrade, doctor

**Required.** `vloop init` writes one `[[check]]` per detected stack with
`paths` the stack's scope (`["**"]` when unscoped) — for `go`, `go test ./...
&& go vet ./...`; for the others, the stack's usual test command — and says
each is a starting point. `vloop upgrade` to 2.0 is a breaking jump (refused
without `--yes`, as today) and adds the same checks when none are configured,
showing them. `vloop doctor` reports no check as a problem and an un-ignored
scratch folder as a problem.

### G10 — the skills and their evals

**Required.**

- `/vloop:plan`: the rules of "Why this shape" for gates; the judge in the
  verify or the gate folder; oracle tests copied into a scratch folder and run
  by the product's runner; **UI oracles assert through roles and visible text,
  appearance goes to the acceptance criteria**; never judge by a task's output;
  never run the repository's suite. "What the gate does not outlive" keeps its
  point — the tests the work ships outlive the gate — without `files`; "The
  gates, together, are the regression net" is replaced by the checks; "Check
  every gate on the base — three ways" moves to `/vloop:gate-review`. A
  revision round reads the findings and revises; it does not start over.
- `/vloop:gate-review` (new): the three ways, the finding kinds, the verdict.
- `/vloop:review`: reads the checks' results instead of running tests.
- `/vloop:work`: the gate fixtures are not its to edit; a gate it believes
  wrong is a `gate_dispute`, as today.
- `plugin/evals/plan-checks-its-gates/` follows: the planner is no longer
  graded on running its gates on the base; it is graded on judges in the gate
  folder and no repository suite in any verify. A new eval suite for
  `/vloop:gate-review` with planted gates: one failing on a path typo, one
  judging by a file its task writes, one grepping source text, one that passes
  on the base, and one sound gate that must `PASS`.

### The domain, updated

`docs/domain/domain-model.md` changes, and nothing else in it:

- **P-3**: a task has no `files`; the plan has at least one check.
- **P-4** gains: "A gate's judge is the planner's — its verify and its gate
  folder — and no task writes it; it is checked on the base and by the gate
  review before any work. Replacing a gate or its fixtures records the old ones,
  a reason and who replaced them in `gate_history`."
- **P-7** (new): "A plan's checks are the repository's tests and health checks,
  named and scoped by path; they pass on the base, run after every iteration
  whose changes they match, and all run once when the last task is done."
- **S-4**: "…— the plan session also writes the plan and its gate folders."
- **R-3**: exit 2 also covers a plan the gate review failed twice and a final
  check pass that failed.
- The vocabulary gains **check**, **gate fixtures**, **gate review**,
  **gate scratch**; **gate** reads "a task's `verify` and its gate folder: the
  planner's judge of the task's contract".

`docs/domain/execution/task.md`, `plan.md`, `session.md`, `run.md` and
`docs/domain/measurement/metrics.md` describe the behaviour above where they
describe the same thing today; `docs/guide/concepts.md`, `configuration.md`,
`commands.md` (generated) and `metrics.md` follow.

### Decided here, because the cited documents leave it underdetermined

- The gate review has no per-task model override (`task.model` stays
  `{work, review}`): it judges the plan, not a task.
- A check-caught failure keeps `found-by: gate` so `defect/v1` and `export/v1`
  do not version; metrics count check failures separately.
- Acceptance problems from G5 and gate-review findings share the two rounds.
- "Changed by the iteration" includes untracked files, so a new file in a
  check's scope runs that check.
- `run.gate-scratch` is config, not a plan field the planner chooses: the
  folders must be git-ignored before the run, which only the operator can do.

### Violations the review must rule on

- A gate in this run's own plan, or in an eval fixture, whose judge is a file a
  task writes.
- Anything that lets a work, review or gate-review session write a gate folder,
  or lets a gate-folder change reach a gate without a `gate_history` entry.
- A check re-run for flakiness, or a timed-out gate re-run.
- A `state/v1` plan resumed, or a v1 record no longer readable by metrics.
- A message that differs from the one quoted here.
- Scope from B10 or B11: intervention fields, the README rewrite, exit-code
  remapping beyond R-3's additions, help-text rewording.

## Worked example

With the stub claude of the run tests, in a temp repo with a ready brief, the
`sh` shell, and config:

```toml
run.gate-scratch = ["web/.gate/"]      # in .gitignore
[[check]]
name = "api"
paths = ["api/**"]
run = "sh api/test.sh"
[[check]]
name = "web"
paths = ["web/**"]
run = "sh web/test.sh"
```

The stub planner writes T1 (changes api/) and T2 (changes web/, its gate
copies .vloop/state/gates/T2/oracle.sh into web/.gate/ and runs it).

```
vloop run <brief>                  (both checks pass on the base)
  -> plan accepted; gates/base-T1.log and base-T2.log exist; both gates failed
     gate review PASS (round 1); state.json: gate_review {rounds 1, verdict PASS}
     iteration 1, T1: checks [api]          (web did not run)
     iteration 2, T2: checks [web]; web/.gate/ empty after every gate
     final pass: api, web                                              exit 0

no [[check]]
  -> vloop: no check configured — add a [[check]] to .vloop/config.toml          exit 1
web/test.sh exits 1 on the base
  -> vloop: check web fails on the base — fix it before planning: <log path>     exit 1
     no session record exists
web/.gate/ not in .gitignore
  -> vloop: gate scratch web/.gate/ is not ignored by git — add it to .gitignore  exit 1
T1's gate `true` (passes on the base); the stub planner fixes it in round 2
  -> gate review rounds 2, verdict PASS; the run proceeds
stub gate reviewer returns FAIL twice
  -> vloop: the gate review failed the plan twice — see <verdict path>; amend the gates with vloop task verify, then re-run   exit 2
work session edits .vloop/state/gates/T2/oracle.sh
  -> restored after the session; T2's gate runs the planner's oracle
operator edits .vloop/state/gates/T2/oracle.sh by hand, vloop run
  -> vloop: the gate fixtures of T2 changed outside vloop task verify — record the change with vloop task verify T2 --reason '<why>'   exit 1
vloop task verify T2 --reason 'seed row'   (folder changed, no command)
  -> gate_history gains {verify, fixtures: <old sha>, reason, by: operator}; T2.fixtures re-stamped
vloop task verify T2 --reason 'again'      (nothing changed)
  -> vloop: nothing to record — T2's gate and fixtures are unchanged           exit 1
T2's gate writes web/leftover.txt
  -> T2's gate fails; its log ends: vloop: gate T2 changed the tree — restored: web/leftover.txt
T1's work breaks api/test.sh
  -> iteration outcome check_failed; checks [{name: api, exit: 1, …}]; no review
web/test.sh starts failing only after T2 is done, from a change T2's check did not see
  -> vloop: check web failed in the final pass — see <log path>                  exit 2
a gate that sleeps past the gate timeout
  -> runs once; no re-run
state.json is state/v1
  -> vloop: .vloop/state/state.json is a state/v1 plan — finish it with vloop 1.x or re-plan the brief   exit 1
```

**Real-data check.** On this repository, for every consumed brief (B1–B8),
`vloop metrics --json` by the new binary equals v1.0.0's output captured at
plan time once `schema` and the keys `metrics/v2` adds are removed. `vloop
status` reads B8's committed `state/v1` plan. This repository's own config gains
a `[[check]]` running the toolchain checks of `CLAUDE.md`, and it passes on the
base.

## Out of scope

- B10 (interventions with options and agreement) and B11 (the quality pass, the
  README rewrite, exit-code remapping, help text).
- The configurable merge strategy (horizon); containers or sandboxes for gates
  or checks; network isolation.
- Affected-test selection inside vloop beyond path globs (dependency graphs,
  Turborepo or Nx integration).
- Promoting a planner's oracle into the product's suite at close.
- Re-running the gate review on resume, or an operator override of its verdict
  other than amending the gates.
- Rewriting past records to v2; a `vloop migrate`.

## Constraints

- Go as pinned in `go.mod`; no new dependencies.
- Every task's gate builds for `windows` and `linux` as well as the host and
  runs `go vet ./...`. OS-specific code lives in build-tagged files; the
  fixtures digest, glob matching and path forms are pure functions tested on
  every OS.
- Gates run on macOS's BSD tools: no empty alternatives in `grep -E`, no
  `sed -i` without a suffix, no `\+` or `\|` in basic regexes, no `date -d`.
- Sessions never move refs. Tests build their repositories in temporary
  directories and address them with `git -C`.
- **This run is planned and gated by v1.0.0.** Its plan is `state/v1` with
  `files`, and no check runs. So: each gate runs **whole Go packages** it
  touches (`go test ./internal/driver/`), not a `-run` pattern alone, except in
  `cmd/vloop`, where a pattern is allowed; and the **close task's gate runs
  `go test ./...`**. B8's two regressions got through gates narrower than
  this.
- **No gate in this run judges by a file its own task writes.** Gates exercise
  the built binary or a package's tests the planner names in the verify; a
  task's new tests are checked by the review and the close.
- **No task may weaken a check to pass.** These earlier tests **must** change,
  and only as stated:
  - `internal/driver/gates_test.go` `TestGateFilesByToken` and
