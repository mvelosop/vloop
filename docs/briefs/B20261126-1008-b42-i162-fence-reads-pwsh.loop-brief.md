- **Produced by:** operator decision, 2026-11-26 (issue #162: read the common
  pwsh forms, steer the rest with the denial's text), widened by the
  operator's hands the same day after a probe of the work fence, on the
  recommended option: pwsh gets the judging sh already gets, no more.
- **Review:** `vloop brief review` (Copilot, mai-code-2), six rounds. 1: `ASK`,
  2 (the base; `fence check` needs no `vloop init`), settled. 2: `FIX`, 3 (W4's

## Executive summary

The fence judges a `bash` and a `powershell` tool call with the same POSIX
grammar (`internal/fence/judge.go`, `Decide`). For pwsh that fails both ways.
It refuses valid, harmless pwsh: B40's sessions were denied 13 times, 11 of
them `subshells and process substitution cannot be judged` for forms like
`(Get-Content README.md | Measure-Object -Line).Lines`, one
`command word $env:GOOS=linux starts with $ and cannot be judged`, and one
`command substitution cannot be judged` for a `$(…)`. And it
lets through what it would deny under sh: `vloop fence check --phase work
--tool powershell` answers `allow` to `pwsh -c 'git push'`,
`powershell -c 'git push'`, `cmd /c git push`, `iex 'git push'`,
`Invoke-Expression 'git push'`, `Start-Process git push`,
`Invoke-Command { git push }`, `ForEach-Object { git push }` and
`& {git push}`, where `bash -c 'git push'` and `eval "git push"` are denied.
The `bash` tool lets the three wrappers through too.

**The goal:** a pwsh command is judged at least as strictly as the same
command in sh, the pwsh forms sessions use most are read instead of refused,
and every refusal of pwsh syntax the fence cannot read says what to write
instead.

- **W1 — wrappers are judged.** `pwsh`/`powershell` with `-Command`/`-c` and
  `cmd` with `/c`/`/k` have their command string judged, as `sh -c` does;
  every other way they run code is refused. Both tools.
- **W2 — pwsh's eval is refused.** `Invoke-Expression`, `Invoke-Command`,
  `Start-Process`, `Start-Job`, `Start-ThreadJob` and their aliases, and a
  script block `{ … }`, are refused in a `powershell` call.
- **W3 — two pwsh forms are read.** `(<pipeline>).<Property>` and
  `$env:<NAME> = <literal>` are judged instead of refused.
- **W4 — unreadable pwsh syntax says what to write.** The refusals of pwsh
  syntax (parentheses, `$(…)`, a backtick, a script block) name the form the
  fence reads. A refused command or wrapper (W1, W2) keeps a plain reason, as
  `eval` does.

Unchanged: every `bash` tool judgement except W1's wrappers; the fence files
(`fence/*.json`) and their matching; the driver's checks after a session, which
stay the boundary (S-2).

## What it is

The fence's judge learns enough pwsh to hold pwsh calls to the bar sh calls
already meet: every wrapper that runs a string is looked through, every
dynamic-execution command is refused like `eval`, and the two forms that
cost B40 most of its denials are read. It is for every repository whose
sessions run pwsh: Copilot on Windows always does, and a mixed team (B40)
writes its gates in pwsh.

Why it got through: the fence was built and tested for POSIX sh (B22, B35);
the `powershell` tool was added to the same branch of `Decide` with no pwsh
cases beyond plain commands and redirections, and no test tries a pwsh
wrapper or cmdlet that runs code.

## Why this shape, and what was rejected

Decided on 2026-11-26. **Do not re-litigate these.**

- **Parity with sh, not a pwsh sandbox.** The fence is advisory and the
  driver is the boundary (S-2). Under sh the fence does not judge `cp`, `tee`
  or running a script file either; pwsh's file cmdlets (`Set-Content`, `Out-File`,
  `Remove-Item`, `New-Item`, …) and `& ./script.ps1` stay unjudged in the same
  way. *Rejected:* judging every pwsh file cmdlet's path as a write (a larger
  change with no sh counterpart; a later brief may do both shells together).
- **Wrappers are judged, not refused.** A session that runs
  `pwsh -NoProfile -Command "go test ./..."` gets its string judged, as
  `sh -c` does. *Rejected:* refusing `pwsh` and `powershell` outright
  (sessions and gates use them legitimately).
- **Script blocks are refused, not read.** A block's body is pwsh statements
  (`$_.Name`, comparisons, method calls) that the fence cannot judge, and
  reading them means a pwsh grammar. The simplified cmdlet forms
  (`Where-Object Name -like '*.go'`, `ForEach-Object -MemberName Name`,
  `Select-Object -ExpandProperty Name`) do the common jobs and are allowed
  today. *Rejected:* a pwsh parser (issue #162's third option; more than one
  brief, and the operator chose the common forms).
- **Exactly two pwsh forms are read** (W3): they are B40's denials. Any other
  parenthesis, `$(…)`, `@(…)`, `@{…}`, a backtick and a `[Type]::Method(…)`
  call stay refused. *Rejected:* reading member access on any expression, or
  method calls.
- **`cmd /c` is judged with the same splitter**, refusing `%` and `^`, which
  the fence cannot resolve. *Rejected:* refusing `cmd` outright (a session on
  Windows may need `cmd /c mklink`).

## Behaviour contract

All of it is observable through `vloop fence check --phase <phase> --root
<dir> --tool <bash|powershell> "<command>"`: `allow` exit 0, or
`deny: <reason>` exit 1. The hook prints the same reason after `vloop fence: `.
Matching is case-insensitive for pwsh command names, parameter names and
aliases, and a name may carry a path and `.exe`, as for sh today.

### W1 — wrappers, in both tools

- **`pwsh` and `powershell`.** Options before the command string may be
  `-NoProfile`, `-NonInteractive`, `-NoLogo` and `-ExecutionPolicy <value>`
  (also `-nop`, `-noni`, `-nol`, `-ep`). Then `-Command` or `-c`: the rest of
  the words, joined with one space, is the command string, judged as a
  `powershell` call at one more nesting level (the eight-level limit holds).
  Every word of it must be literal: a word that expands is
  `deny: the -Command string expands and cannot be judged`. A missing string is
  `deny: -Command has no command string`. Anything else (`-File`, `-f`, a
  script path, `-EncodedCommand`, `-e`, `-ec`, `-Command -`, no command, any
  other option) is
  `deny: pwsh: runs a script, stdin or an encoded command, not a literal -Command string`
  (`powershell: …` for powershell).
- **`cmd`.** `/c` or `/k` (case-insensitive; `/d`, `/q`, `/s` may come before
  it): the rest of the words, joined with one space, judged as a command line
  split at `&`, `&&`, `||` and `|`, each command matched as today. A `%` or a
  `^` anywhere in it is `deny: cmd: % and ^ cannot be judged`. Anything else
  is `deny: cmd: runs stdin or a batch file, not a literal /c string`.
- A command the wrapped string holds is judged exactly as it would be on its
  own: `pwsh -c 'git push'` is denied with git push's reason.

### W2 — pwsh's eval, in the `powershell` tool

- These command names, wherever a command name stands, are
  `deny: <name> is not allowed`, with the name as written:
  `Invoke-Expression`, `iex`, `Invoke-Command`, `icm`, `Start-Process`,
  `saps`, `start`, `Start-Job`, `sajb`, `Start-ThreadJob`, `Invoke-Item`, `ii`.
- Any `{` outside quotes in a `powershell` call (a script block, `@{`, or
  anywhere else) is
  `deny: script blocks cannot be judged — use Where-Object <Property> -like <value>, ForEach-Object -MemberName <Property> or Select-Object -ExpandProperty <Property>`.
- The `bash` tool keeps its `{ …; }` group reading (B35).

### W3 — two pwsh forms read, in the `powershell` tool

- **`(<pipeline>).<Property>`**, as a whole statement or as the first command
  of a pipeline: the inside of the parentheses is judged as a `powershell`
  call; the property path is one or more `.Name` (letters, digits, `_`), with
  nothing after it but the statement's end or `|`. `(…)` in any other place,
  a method call `.Name(…)`, or anything after the property path keeps the
  refusal, now worded for pwsh (W4).
- **`$env:<NAME> = <value>`** (with or without spaces around `=`), as a whole
  statement: `NAME` is letters, digits and `_`, not starting with a digit;
  `value` is one word that does not expand (single-quoted; double-quoted with
  no `$` and no backtick; or bare with none of `$ ( ) { } [ ] @` and no
  backtick). It is allowed, as a sh assignment is. Any other `$env:` statement
  keeps today's reason, `command word <word> starts with $ and cannot be
  judged`, `<word>` being the statement's first word as the splitter reads it.
- In the `bash` tool both forms keep today's refusals.

### W4 — pwsh denials say what to write, in the `powershell` tool

The pwsh-specific refusals read, exactly:

| what | reason |
|---|---|
| `(…)` not in W3's form, `@(…)` | `parentheses cannot be judged here — (<command>).<Property> is read; or pipe into Measure-Object or Select-Object -ExpandProperty` |
| `$(…)` | `command substitution cannot be judged — run the inner command on its own` |
| a backtick | `a backtick cannot be judged — write the command on one line, without escapes` |
| `@{…}` | the script-block reason of W2 |

The `bash` tool's reasons are unchanged.

### Decided here, because the cited documents leave it underdetermined

- **Where "pwsh" applies.** W2–W4 apply to the `powershell` tool, and to a
  string W1 hands over from `pwsh`/`powershell -Command` under either tool. A
  `bash` call keeps POSIX judging; `sh -c` inside a pwsh string is judged as
  sh, as today.
- **The audit and the guide.** `docs/guide/configuration.md`'s "The fence
  hook" gains the pwsh rules (one bullet), and `docs/design-notes/fence-audit.md`
  gains rows for W1 and W2. No skill changes: the denial reasons carry the
  guidance, so every agent sees it.
- **The help.** `vloop fence check`'s long help names the new wrappers
  (`… xargs, sh -c, pwsh and powershell -Command, and cmd /c, …`) and adds one
  sentence: in a `powershell` call, pwsh's eval-like commands and script
  blocks are refused. `docs/guide/commands.md` is regenerated from it.
- **The probe's other findings stay as they are**, by the parity decision:
  `Set-Content .git/config`, `Remove-Item -Recurse -Force .git`,
  `New-Item ~/.claude/x`, `& ./x.ps1`.

### Violations the review must rule on

- A `bash` tool judgement that changed, other than W1.
- A pwsh form allowed that this brief does not name, or a W2 name allowed
  anywhere a command name stands (after `|`, `;`, `&&`, inside a W1 string,
  inside W3's parentheses).
- A wrapper's string judged with a different phase or root than the call.
- An earlier fence test edited for anything but the new behaviour.

## Worked example

`vloop fence check --phase work --root <repo> --tool <tool> "<command>"`:

```
tool        command                                                       result
powershell  pwsh -c 'git push'                                            deny: git push is denied by the work fence (Bash(git push:*))
bash        pwsh -NoProfile -Command "git push origin main"               deny: git push origin main is denied by the work fence (Bash(git push:*))
powershell  pwsh -NoProfile -Command 'go test ./x'                        allow
powershell  pwsh -File x.ps1                                              deny: pwsh: runs a script, stdin or an encoded command, not a literal -Command string
powershell  powershell -EncodedCommand ZwBpAHQA                           deny: powershell: runs a script, stdin or an encoded command, not a literal -Command string
powershell  pwsh -c $x                                                    deny: the -Command string expands and cannot be judged
powershell  cmd /c git push                                               deny: git push is denied by the work fence (Bash(git push:*))
powershell  cmd /c echo %PATH%                                            deny: cmd: % and ^ cannot be judged
powershell  cmd                                                           deny: cmd: runs stdin or a batch file, not a literal /c string
powershell  iex 'git push'                                                deny: iex is not allowed
powershell  Get-Content a | Invoke-Expression                             deny: Invoke-Expression is not allowed
powershell  Start-Process git push                                        deny: Start-Process is not allowed
powershell  Get-ChildItem | ForEach-Object { $_.Name }                    deny: script blocks cannot be judged — use Where-Object <Property> -like <value>, ForEach-Object -MemberName <Property> or Select-Object -ExpandProperty <Property>
powershell  & {git push}                                                  deny: script blocks cannot be judged — use Where-Object <Property> -like <value>, ForEach-Object -MemberName <Property> or Select-Object -ExpandProperty <Property>
powershell  Get-ChildItem | ForEach-Object -MemberName Name               allow
powershell  (Get-Content README.md | Measure-Object -Line).Lines          allow
powershell  (git push).Length                                             deny: git push is denied by the work fence (Bash(git push:*))
powershell  (Get-Content a).Trim()                                        deny: parentheses cannot be judged here — (<command>).<Property> is read; or pipe into Measure-Object or Select-Object -ExpandProperty
powershell  $env:GOOS='linux'; go build ./...                             allow
powershell  $env:GOOS = "linux"; go vet ./...                             allow
powershell  $env:GOOS=$x; go build ./...                                  deny: command word $env:GOOS=$x starts with $ and cannot be judged
powershell  Write-Output "a`tb"                                           deny: a backtick cannot be judged — write the command on one line, without escapes
powershell  Write-Output "$(git push)"                                    deny: command substitution cannot be judged — run the inner command on its own
bash        (cat a).Count                                                 deny: subshells and process substitution cannot be judged
bash        eval "git push"                                               deny: eval is not allowed
bash        bash -c 'git push'                                            deny: git push is denied by the work fence (Bash(git push:*))
```

`<repo>` is any directory: `vloop fence check` needs no `vloop init` and runs
nothing. The eight-level limit
applies across wrappers: nine nested `pwsh -c` strings are
`deny: shell wrappers nest too deep to judge`.

## Out of scope

- Judging pwsh file cmdlets' paths as writes, or `tee`, `cp`, `mv`, `touch`
  under sh: both shells together, in a later brief if the operator wants it.
- A pwsh grammar: reading script blocks, method calls, `$(…)` or `@(…)`.
- pwsh's output encoding on Windows (#162 part 2), which is the next brief's.
- Any change to the fence files' rules, the hook's protocol, the backstop or
  the driver's checks.
- Skills: no skill text changes.

## Constraints

- Go, as pinned in `go.mod`; `go run ./tools/check` is the `[[check]]` and
  passes after every task.
- **This run is on Windows, and its sessions' shell tool is `powershell`.**
  The fence judges their own commands as it changes: a task that breaks the
  judge mid-task costs that task turns, not the run. The fence's unit tests
  run on every OS; most `cmd/vloop` end-to-end tests skip on Windows, so gate
  through `vloop fence check` on the built CLI or an oracle test in the
  task's gate folder that calls the judge, never through those end-to-end
  tests.
- **Gates follow the diff surface.** No gate runs the whole suite or the
  check (P-8).
- **No task may weaken a check to pass.** An earlier test changes only where
  it pins behaviour the contract changes, and only to the new behaviour.
- **Fail closed stays.** Every new path through the judge that cannot decide
  denies; no change makes an error an allow.
- Tests build their repositories in temporary directories and address them
  with `git -C`. Sessions never move refs. Repo-relative paths everywhere.
