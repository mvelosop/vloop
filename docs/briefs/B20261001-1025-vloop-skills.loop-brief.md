## What it is

The seventh slice of `vloop`: the plugin's skills. `vloop run` (B6) invokes
`/vloop:plan`, `/vloop:work` and `/vloop:review`; this brief writes them, ported
from the shell loop's `loop-plan`, `loop-work` and `loop-review` and adapted to
vloop's files, schemas and commands, with the duties B2–B6 added: assigning
`area` and `kind`, executing every gate against the base before handing over a
plan, disputing a gate that cannot pass, and writing the prose people read in
the configured language. It also writes `/vloop:operate`, the operator's
playbook as a skill, which records what the operator does — defects and
interventions — because the loop will run on every kind of project, and the
patterns only show in that data. Structural checks keep the skills consistent
with the schemas, the CLI and the fence; eval suites — the shell loop's reviewer
calibration among them — test their behaviour on demand; and a real `vloop run`
of a benchmark brief, at close, is the acceptance.

## Why this shape, and what was rejected

Decided with the operator on 2026-10-01. **Do not re-litigate these.**

- **Ported, not rewritten.** The shell skills' rules come from real runs — notes
  that spread habits, gate-shape rules, tamper rules — and survive the port
  unless vloop's contracts change them.
  *Rejected:* fresh skills from the domain docs and schemas — leaner, and they
  would drop lessons nobody would know to re-learn.
- **Structural gates plus eval suites.** Gates check, in Go, that the skills name
  only what exists and that their examples validate; eval suites
  (`claude plugin eval`) test behaviour and are run by the operator at close.
  *Rejected:* gates that run `claude` — every done task's gate re-runs every
  iteration, and sessions cannot run `claude`.
- **The prose people read follows the configured language** (C-4): the planner's
  task titles, goals, acceptance criteria and notes; the work session's summary
  and notes; the review's evidence, finding summaries and notes. Keys, enum
  values, ids, commit subjects and the driver's own messages stay English.
  *Rejected:* only notes and findings — a Spanish team would read English
  acceptance criteria in `plan.md`.
- **B7 is run by the shell loop**: it builds the skills `vloop run` needs. The
  first real `vloop run` is the **acceptance run** at B7's close (below); B8 is
  the first brief this repository runs with `vloop run`.
- **The design act stays upstream.** No skill writes briefs; `/vloop:operate`
  starts from a `ready` one.
- **Interventions become a vloop record, like defects.** `/vloop:operate`
  records them as they happen, and the export carries them with each
  repository's stacks, so patterns can be compared across project types.
  *Rejected:* leaving them as this repository's practice — the data is only
  useful across projects.
- **The reviewer calibration becomes the review's eval suite**: its nine planted
  defects, with an objective expected verdict and a measured baseline (9/9, then
  8/9 with case `06` not reproducing, about $3), are a better test of
  `/vloop:review` than new cases.

## Behaviour contract

### The skills

Each is `plugin/skills/<name>/SKILL.md`, with frontmatter `name` and
`description`; supporting files may sit beside it. The plugin is named `vloop`,
so the skills resolve as `/vloop:<name>`.

**`plan`** — invoked as `/vloop:plan <brief path>`. Reads the brief and its
binding references, and surveys the repository. Writes `.vloop/state/state.json`
as `state/v1`: `base` (HEAD's commit), `shell` (`vloop config get shell`),
`status: planning`, `iteration: 0`, timestamps, and the tasks — each with `id`,
`title`, `goal`, `kind`, `area` (one of `vloop config get areas` when that is
set; omitted when it is not), `files`, `references` (the brief's binding
references **distributed** to the tasks they bind, with their reasons; never a
document the brief does not cite), `depends_on`, `acceptance`, `verify` (a
command in the plan's shell), `status: pending`, `attempts: 0`, `notes: ""`.
`run_id`, `brief` and `branch` are the driver's to stamp. Before finishing it:

1. validates the plan: `vloop schema validate state/v1 .vloop/state/state.json`
   and `vloop task validate` both pass;
2. **checks every task's gate three ways**, in the plan's shell, on the
   **base** — the commit HEAD is at while it plans, before any task exists — and
   rewrites a gate that fails any of them before handing over the plan:
   - **it fails on the base**, at a behavioural assertion: a gate that passes
     before the work exists proves nothing;
   - **every fixture it builds is checked** with commands that already exist —
     the state a fixture edit leaves is read back, not assumed (B5 T8's TOML key
     appended after a table read back as `metrics.shell`);
   - **every matcher is exercised once** against the exact output the brief
     pins, so a pattern the host's tools reject or that can never match shows
     before the run (B2 T1's `(|/)`, which BSD `grep` rejects).

   What these cannot see is a gate that contradicts its own acceptance — B5 T6
   asserted a clean `git status` after requiring a tracked file to change. That
   stays the work session's to dispute (`gate_dispute`), which now blocks at once
   with no attempt charged.

**`work`** — invoked as `/vloop:work <task id>`. Reads its task with
`vloop task show <id> --json`, the brief, the task's references and notes. Does
exactly that task (S-3), runs its gate, and writes `.vloop/tmp/proposal.json` as
`proposal/v1`, validated with `vloop schema validate proposal/v1`. When the gate
cannot pass for a correct implementation, it reports `outcome: blocked` with a
`gate_dispute`: `reason` (what the gate gets wrong) and `evidence` (the clause,
and the output or fact that shows it). It never edits a gate, commits, sets a
status or moves a ref (S-2).

**`review`** — invoked as `/vloop:review <task id>`. Judges the task
independently: the working tree's change against the task's acceptance, the
brief and the references — not the proposal's summary (S-3). Writes
.vloop/tmp/verdict.json as `verdict/v1`, validated: one `criteria` entry per
acceptance line, verbatim, with `met` and `evidence`; `findings` with `summary`
and `kind` (`bug`, `spec-gap` when the brief is silent or ambiguous, `gate-gap`
when the gate passes on wrong behaviour); `verdict: FAIL` whenever a criterion is
unmet or a finding is a `bug`. When in doubt it fails: a verdict that passes work
it could not judge is the failure the loop exists to prevent.

**`operate`** — invoked by the operator in an interactive session. The
playbook of `.claude/skills/vloop-operator/SKILL.md`, made generic for any
repository and driven by the CLI. It **records defects (`vloop defect add`) and
interventions (`vloop intervention add`) as they happen** — everything the
operator does around a run besides testing. Its steps: `vloop doctor`; `vloop run` on a work branch;
on a halt, `vloop status`, the journal and the task's notes, with what each exit
code asks of the operator; a disputed gate resolved only with the operator's
approval, through `vloop task verify --reason`; verification — refs first, the
repository's own checks, `vloop metrics` read critically; closing with
`vloop brief close --finding …` or `--no-findings`; the squash-merge with the
printed trailer, keeping the branch, only on the operator's go-ahead. It starts
from a `ready` brief and never writes one. Repository-specific lessons of this
repo's playbook stay in this repo.

### Interventions — `vloop intervention add | list | set`

Interventions become a vloop record, the way defects are (B3):

- One file each: `.vloop/interventions/I<YYYYMMDD-HHMM>-<slug>.md`, frontmatter
  as `.vloop/interventions/README-interventions.md` defines it (`id`, `brief`,
  `phase`, `kind`, `automatable`, `by`, `occurred`, `recorded`, optional
  `backfilled`), then the summary and the **Trigger.**, **Done.** and **What
  would automate it.** sections. Schema `intervention/v1` (the frontmatter as
  JSON) joins `vloop schema list`.
- `vloop intervention add "<summary>" --phase <p> --kind <k> --automatable <a>
  --by <b> [--brief <name>] [--trigger <text>] [--done <text>] [--automation
  <text>]` writes the file and prints its path; invalid values are exit 2 with
  B1's invalid-value message.
- `vloop intervention list [--brief <name>] [--json]` prints `<phase>  <kind>
  <automatable>  <id>`, sorted by phase in lifecycle order, then kind, then id —
  the table `tools/interventions-index.sh` prints today.
  `vloop intervention set <id> <field> <value>` sets one field.
- Every record already in `.vloop/interventions/` validates against
  `intervention/v1` as it is.
- `vloop metrics export` gains `intervention` records, and every record's `repo`
  gains `stacks` (`metrics.stacks` as configured), so analysis across a
  workspace can group by project type.

### Language

Each session reads `vloop config get language` and writes, in that language,
the prose a person reads (as listed under "Why this shape"). Everything else is
English. The skills themselves are written in English.

### Structural checks (the gates)

Go tests over `plugin/`:

- every skill has `name` and `description` frontmatter, and `name` equals its
  folder;
- every `vloop <command>` a skill names exists in the command tree, with every
  flag it names;
- every schema a skill names is in `vloop schema list`, and every fenced `json`
  block carrying a `"schema"` field validates against that schema;
- every `.vloop/` path a skill names is one of the layout's (the domain model's
  "On disk");
- **skills and fence agree**: every vloop command the `plan`, `work` or `review`
  skill tells a session to run is allowed by the embedded fence, and none it
  names is one the fence denies;
- every eval case has a prompt.md with `max_turns` and `allowed_tools`
  frontmatter, and at least one `graders/*.md` with `type` and `weight`.

### Eval suites

Under `plugin/evals/<case>/`, in `claude plugin eval`'s format (a prompt.md plus
`graders/*.md`; a case that needs a repository plants it with a scaffold script,
as the calibration's `plant.sh` does).

- **The review calibration, ported**: the nine cases of the shell loop's reviewer
  calibration (`01-hollow-test` … `07b-provenance-weak-goal`), each planting a
  defective implementation that passes its gate and expecting `/vloop:review` to
  FAIL it with a finding that names the planted defect. The bar is the
  calibration's baseline: every case caught, with `06` allowed to miss as it does
  today.
- **The other skills**, at least:

| Case | What it shows |
| --- | --- |
| `plan-valid-state` | a plan for a small brief validates and every task has `kind` |
| `plan-checks-its-gates` | the planner rewrites a gate that passes on the base, and one whose fixture does not do what it assumes |
| `work-disputes-impossible-gate` | a work session facing an unsatisfiable gate writes `gate_dispute` instead of editing the gate |
| `language-es` | with `language = "es"`, a plan's titles and acceptance are Spanish and its keys English |

They are run by the operator at close: `claude plugin eval plugin
--max-cost-usd <run.cost-ceiling>` — the loop's own ceiling as the starting
limit, adjusted from what the runs cost. `vloop plugin path` does not extract
the evals: sessions never need them.

### Acceptance — the url-shortener benchmark (operator-run at close, not a gate)

The first real `vloop run`: `mvelosop/url-shortener-loop-sample` at `9a197a7`
(its brief `0001-url-shortener`, before the shell loop planned it), in a scratch
directory outside this repository:

1. remove the shell loop (loop/, `.claude/skills/loop-*`), keep the app's
   `.claude/settings.json` (it allows `npm`, `npx`, `node`);
2. `vloop init`; convert the brief to docs/briefs/B20260818-2100-url-shortener.loop-brief.md
   — frontmatter added, its content unchanged — and check it with `vloop brief
   check`;
3. `vloop run` with the B7 binary, real `claude`, default budgets.

It passes when the run ends `complete` (exit 0), every session and iteration
record validates, every task has a `kind`, the app's unit tests, e2e tests and
boot check pass when run by hand, and `vloop metrics` is recorded in this
brief's run record beside the shell loop's run of the same brief (10/10 tasks, 11
iterations, 1 review rejection, about $19.86). A failure is a finding, recorded
with `close --finding`, and decides whether B7 closes or gets a fix first.

### Decided here, because the cited documents leave it underdetermined

- The planner's three gate checks, on the plan's base; and that a gate
  contradicting its own acceptance is left to the work session's dispute.
- `export/v1` gains the `intervention` type and `repo.stacks` in place, not a
  `v2`: nothing consumes the export yet.
- The eval cost limit starts at `run.cost-ceiling`; this brief's run record
  records what the suites actually cost.
- `/vloop:operate` keeps the repository-specific lessons out; the generic ones
  (refs first, read metrics critically, merge only on the go-ahead) stay.
- Eval suites live in the plugin, are not extracted for sessions, and are run by
  the operator.
- The benchmark brief is converted with its content unchanged, so the comparison
  with the shell loop's run is like for like.

### Violations the review must rule on

- A skill that names a command, flag, schema, field or path that does not exist,
  or tells a session to do what the fence denies.
- A skill that lets a session commit, set a status, edit a gate or move a ref;
  or a planner that discovers references the brief does not cite.
- A rule of the shell skills dropped without a reason in the task notes.
- `/vloop:operate` merging, pushing or resolving a gate dispute without the
  operator's approval, or leaving out recording defects and interventions.
- An existing intervention record that fails `intervention/v1`, or an export that
  drops one.
- Running `claude` in a gate, or the acceptance run in this repository.

## Constraints

- Skills are Markdown; the checks are Go tests in this module. No new
  third-party modules without their reason in the task notes.
- Must build for `darwin`, `linux` and `windows`.
- **Gates run on macOS with its BSD tools**: no GNU-only syntax (no empty
  alternatives in `grep -E`, no `sed -i` without a suffix, no `\+` or `\|` in
  basic regexes, no `date -d`).
- **Every gate is checked by the planner before it hands over the plan**: it
  fails on the base at a behavioural assertion, every fixture it builds is read
  back with commands that already exist, and every matcher is exercised once
  against the output the brief pins — the duty this brief also writes into
  `/vloop:plan`.
- **Sessions must not move git refs, and cannot run `claude`**: the fence denies
  both. Gates never run `claude`; the eval suites and the acceptance run are the
  operator's.
- **Gates follow the diff surface**: each task gates on the packages it touches,
  plus `go vet ./...`, `gofmt -l .` and `go mod tidy -diff` printing nothing,
  and the linux, windows and host builds. Only the close runs `go test ./...`.
- A gate runs in under three minutes. Tests never read or write this
  repository's `.loop/`, `.vloop/state/`, git history or the real home directory.
- **No task may weaken a check to pass.** Required changes, and only these:
  `schema list` gains `intervention/v1`; `export/v1` gains the `intervention`
  type and `repo.stacks`; the generated command reference is regenerated; B1's
  README test passes with the README's skills and intervention lines added.
- **New checks are proven by fixtures**: each structural check has a fixture it
  rejects and the real plugin it accepts.
- Repo-relative paths everywhere. No absolute paths in any file or commit message.

## Shape

9 to 11 tasks, each independently verifiable by a single command. Order is
load-bearing:

1. **The structural checks**, with a rejecting fixture each; on the real plugin
   they may not pass yet.
2. **`/vloop:plan`**, ported: its contract, references distributed, `area` and
   `kind`, gates executed against the base, the language.
3. **`/vloop:work`**, ported: its contract, `gate_dispute`, the language.
4. **`/vloop:review`**, ported: its contract, findings with kinds, failing
   closed, the language.
5. **Interventions**: `intervention/v1`, `vloop intervention add|list|set`, the
   existing records validating, the export's `intervention` records and
   `repo.stacks`.
6. **`/vloop:operate`**: the generic playbook, driven by the CLI, recording
   defects and interventions.
7. **The eval suites** — the nine calibration cases ported, the four others —
   and `vloop plugin path` skipping the evals.
8. **Docs**: a skills section in the README (under its cap), `docs/guide/concepts.md`
   on the skills, `docs/guide/defects.md` gaining interventions,
   `docs/domain/execution/session.md` stating the skills as built, the
   regenerated command reference.
9. **Close**: every structural check on the real plugin, `claude plugin validate
   .` (run by the gate), `go test ./...`, `go vet ./...`, `gofmt -l .`,
   `go mod tidy -diff` and the three builds.

The acceptance run and the eval suites are the operator's, at close: they need a
real `claude`, which no gate may run.
