# Brief — vloop B24: Copilot for work sessions

- **Starting point:** extends `main` at `c19e390` (B22 merged). The planner
  pins that SHA as the **base** every gate compares against — never `HEAD~n`.
- **Produced by:** the design act of 2026-10-27: B22's acceptance and the hook
  probes (`docs/design-notes/copilot-cli-experiments.md` → B22.0 to B22.3), the
  work replays of the experiments ("Results — work"), and the operator's
  decisions below.

## Executive summary

Copilot can run review sessions, fenced by `vloop fence hook`, but the work
itself is Claude's only: `agent.work` accepts `claude` alone, and the hook
knows only the review fence, which allows no writes outside `.vloop/tmp/`.

**The goal:** an operator sets `agent.work = "copilot"` and a Copilot model, and
every task's work session runs on the GitHub Copilot CLI, under the same work
fence Claude's work sessions run under, with the driver's checks unchanged.

- **W1 — the hook judges work sessions.** A `work` phase for `vloop fence
  check` and `vloop fence hook`: the work fence's rules, writes anywhere in the
  repository except where S-4 forbids, and `rm` of a file allowed as Claude's
  work fence allows it.
- **W2 — Copilot runs work sessions.** `agent.work` accepts `copilot`; the
  session runs under the hook's `work` phase; the run preflight and doctor
  check it as they check Copilot review.
- **A1 — the docs and the acceptance kit.** The fence audit, the guide and the
  domain pages say what a Copilot work session may do; the kit gains a work
  run on the real CLI.

Unchanged: Claude sessions — their argv, fence and settings; Copilot review and
second-review sessions, their rules and argv; plan, gate review and verify run
on Claude only; the driver's checks stay the boundary (S-2).

## Why this shape, and what was rejected

Decided with the operator on 2026-10-27. **Do not re-litigate these** — the
planner inherits them.

- **The work phase uses the work fence, one rule set.** The hook judges a
  Copilot work session against `fence/work.json`, the file Claude's work
  sessions run under, as B22 made the review hook read `fence/review.json`.
  *Rejected:* a stricter Copilot-only rule set (legitimate work denied, turns
  spent on retries); a looser one.
- **`rm` of a file is allowed in work, as Claude's work fence allows it.**
  Copilot's `--deny-tool` matches a stem only, so `shell(rm:*)` would deny
  every `rm`; for work sessions it leaves the argv and the hook's stems, and
  the work fence's recursive `rm` rules deny the rest. Review and second review
  keep it.
- **Shell syntax the hook cannot judge stays denied.** `if`, `for`, `while`,
  `$(…)`, subshells: a deny, as in review. The acceptance on the real CLI
  counts these denials; judging them is issue #83, after this brief.
- **No hook-log backstop in this brief.** The driver's checks after the session
  are the boundary for Copilot work as for Claude work (S-2, S-4); comparing
  the hook's decisions with Copilot's tool calls is issue #82.
- **Copilot work is experimental**, like Copilot review: warned by doctor and
  the preflight, documented as such.
- **The acceptance model is `gpt-5.6-terra`**, the operator's choice, for a
  cross-family run. The brief pins no model: the operator sets `model.work`.
- **The binary never calls the network**; acceptance on the real CLI is the
  operator's, at close, as in B19 and B22.

## Behaviour contract

### W1 — the `work` phase of `vloop fence`

`vloop fence check` and `vloop fence hook` accept `--phase work`, alongside
`review` and `second-review`. Everything B22 pinned for the review phases
stays, byte for byte, including their messages. In `work`:

- **Shell** (`bash`, `powershell`): the same splitting, unwrapping and
  outright denials as in review (a backtick, `$(`, `<(`, `>(`, `eval`,
  `source`, `.`, an unterminated quote, a non-literal `-c` string, a command
  word starting with `$`, and the shell keywords). Each simple command is
  denied when it matches a `Bash(…)` deny rule of `fence/work.json`:
  `vloop fence: <command> is denied by the work fence (Bash(<rule>))`; or one
  of the adapter's deny-list stems for work sessions, which are the review
  stems without `rm:*`:
  `vloop fence: <command> is denied by the Copilot deny list (<stem>)`.
  A redirection to a file is a write, judged as below.
- **Writes** (`create`, `edit`, `apply_patch`, a redirection): every path
  resolved against `--root` as in review. Allowed anywhere under the root,
  except:
  - under `.git/`, or under `.vloop/` but not under `.vloop/tmp/` (S-4):
    `vloop fence: write to <path> is not allowed in a work session: nothing under .git/ or .vloop/ but .vloop/tmp/`
  - outside the root:
    `vloop fence: write to <path> is not allowed in a work session: it is outside the repository`
  `/dev/null` is allowed.
- **Reads**: as in review — denied under `~/.claude`, `~/.copilot` and
  `~/.config/gh`, allowed elsewhere.
- **Skills**: one of the embedded plugin's skills only; any other:
  `vloop fence: skill <name> is not vloop's — use /vloop:work`.
- **Everything else** (`web_fetch`, `task`, any name ending in `_subagent`,
  every name not listed): `vloop fence: tool <name> is not allowed in a work session`.
- An unknown phase: `unknown phase "<p>": want review, second-review or work`,
  exit 2 for `fence check`; the deny line and exit 2 for `fence hook`.

### W2 — Copilot work sessions

- `agent.work` accepts `claude` (default) and `copilot`, with
  `VLOOP_AGENT_WORK` as today. `agent.plan`, `agent.gate-review` and
  `agent.verify` still accept `claude` only.
- A work session on copilot runs `/vloop:work <task>` exactly as a Copilot
  review session runs `/vloop:review <task>` — the plugin by `--plugin-dir`, a
  fresh home under `.vloop/tmp/`, the guidelines as custom instructions, the
  JSON Lines parsed into the `session/v4` record (`agent: "copilot"`, credits,
  `cost_source`, `permission_denials`) — with these differences only: the hooks
  file runs `vloop fence hook --phase work`, and the argv's deny list omits
  `--deny-tool=shell(rm:*)`. P-6 resolves its model and effort as for any work
  session.
- Everything the driver does around a work session is unchanged, whatever the
  agent: the gate, the checks, the guards (a moved ref or git setting halts
  with exit 9; inputs restored), the proposal read from `.vloop/tmp/`, the
  review, the one commit.
- `vloop run`, when `agent.work` is `copilot`:
  - warns `  ! agent.work is copilot: experimental (docs/guide/configuration.md)`;
  - refuses to start, exit 1, while `model.work` is the default:
    `vloop: agent.work is copilot but model.work is the default "sonnet", a Claude alias: set model.work to a Copilot model id`;
  - applies the copilot checks Copilot review has: `copilot` on PATH and
    runnable, a GitHub login reaching its sessions, and K1's refusal of a
    project skill named like one of vloop's (the message naming `agent.work`
    where it names a key).
  `vloop doctor` shows the same rows for `agent.work`.

### A1 — the docs and the acceptance kit

- `docs/design-notes/fence-audit.md` gains the work fence: each rule of
  `fence/work.json` and each work deny-list stem, classified as for review
  (the driver after the session, the hook, or neither, with what covers the
  last).
- `docs/guide/configuration.md`: `agent.work` lists `copilot` (experimental);
  the Copilot section covers work sessions, what the hook allows them and that
  shell syntax it cannot judge is denied.
- `docs/domain/execution/session.md` and the glossary of
  `docs/domain/domain-model.md`: copilot runs work, review and second-review
  sessions; the hook serves the work phase with the work fence.
- `tools/copilot-acceptance/`: a script running the fixture brief
  (`greet.loop-brief.md`) in a scratch repository with `agent.work = copilot`
  and the model given, plan and review on Claude, and summarising each work
  session record (agent, model, credits, estimated cost, `session/v4`
  validity, its `permission_denials`) and each task's outcome; its README
  section.

### Decided here, because the cited documents leave it underdetermined

- **A path written after a `cd`** is resolved against `--root`, as in review:
  the hook does not follow `cd`. What it misses the driver's checks restore
  (S-2, S-4).
- **A script run by a command** (`node x.js`, `pnpm test`, `sh script.sh`
  stays denied as in review) is judged by its command line only, as Claude's
  fence judges it.
- **Package installs are allowed** (`pnpm add`, `npm install`): the work fence
  allows them for Claude; `pip install` stays denied as it is there.

### Violations the review must rule on

- A form in the worked example's deny column that `fence check --phase work`
  allows, or an allow line it denies.
- Any change to the review or second-review phases' decisions or messages, to
  a Copilot review session's argv, or to a Claude session's argv, fence or
  settings.
- A Copilot work session started without the hooks file, with the review
  phase in it, or with `shell(rm:*)` on its argv.
- `agent.plan`, `agent.gate-review` or `agent.verify` accepting `copilot`.
- A gate that runs `copilot` or touches the network.

## Worked example

`vloop fence check --phase work --root <repo> --tool bash "<command>"` in a
fixture repository:

```
allow   rm src/old.ts
allow   pnpm add nanoid
allow   git diff > .vloop/tmp/diff.txt
allow   echo ok > src/version.txt
allow   ls src > /dev/null
deny    rm -rf dist                          -> vloop fence: rm -rf dist is denied by the work fence (Bash(rm -rf:*))
deny    sh -c "git push origin main"         -> … denied by the work fence (Bash(git push:*))
deny    env gh pr list                       -> … denied by the Copilot deny list (gh:*)
deny    curl https://example.com             -> … denied by the work fence (Bash(curl:*))
deny    git commit -m x
deny    echo x > .vloop/state/state.json     -> vloop fence: write to .vloop/state/state.json is not allowed in a work session: nothing under .git/ or .vloop/ but .vloop/tmp/
deny    echo x > ../outside.txt              -> vloop fence: write to ../outside.txt is not allowed in a work session: it is outside the repository
deny    for f in a b; do echo $f; done
deny    echo $(date)
```

Every `deny` exits 1 and prints its reason; every `allow` exits 0.

The same `rm src/old.ts` with `--phase review`:
`deny: vloop fence: rm src/old.ts is denied by the Copilot deny list (rm:*)`,
exit 1 — unchanged.

Other tools (`--tool`, `--path`), phase `work`:

```
allow   create       src/links/links.service.ts
allow   edit         test/app.e2e-spec.ts
allow   create       .vloop/tmp/proposal.json
deny    create       .vloop/state/state.json
deny    edit         .git/config
deny    create       .vloop/config.toml
deny    create       /etc/hosts
allow   view         src/app.ts
deny    view         ~/.copilot/config.json
allow   skill        work
deny    skill        vloop-work       -> vloop fence: skill vloop-work is not vloop's — use /vloop:work
deny    web_fetch                     -> vloop fence: tool web_fetch is not allowed in a work session
```

An `apply_patch` payload in `work` with `*** Update File: src/app.ts`: allow;
with `*** Add File: .vloop/defects/D1.md`: deny. `vloop fence check --phase
plan`: `unknown phase "plan": want review, second-review or work`, exit 2.

A run with a stub `copilot` on PATH, `agent.work = copilot`,
`model.work = gpt-5.6-terra`, review on the stub Claude, a one-task plan whose
stub work session writes the task's file and a valid proposal:

```
vloop run
  ! agent.work is copilot: experimental (docs/guide/configuration.md)
  T1 done; one commit
  the work session's record: phase "work", agent "copilot", model "gpt-5.6-terra",
    session/v4 valid
  the stub's logged argv: --deny-tool=shell(git push:*) present,
    --deny-tool=shell(rm:*) absent; the hooks file in its home holds
    "fence hook --phase work"
```

Planted failures, each with the same stub:

```
model.work unset             -> vloop: agent.work is copilot but model.work is the default "sonnet", a Claude alias: set model.work to a Copilot model id     exit 1
.claude/skills/work/ present -> K1's refusal, naming .claude/skills/work                                                                                    exit 1
agent.plan = copilot         -> refused as today: agent.plan accepts claude only
stub work session moves HEAD -> the run halts, exit 9, as for a Claude work session
```

## Out of scope

- Copilot for plan, gate review or verify (#77, #78, #79).
- Judging `if`, `for`, `while`, `$(…)` or subshells (#83).
- Comparing the hook's decisions with Copilot's tool calls (#82), or raising
  the hook's `timeoutSec`.
- Any change to the review fence, the work fence's rules, or Claude sessions.
- A model-qualifying eval runner (#81); a replacement for `gpt-5.6-terra`
  (#84); Foundry (#80); other providers (#85).
- Dropping the experimental label.
- Reporting vloop defects upstream (B23).

## Constraints

- Go, at the version in `go.mod`; no new dependencies.
- Must keep building and passing on macOS, Linux and Windows; the path rules
  are pure functions tested on every OS.
- **Gates run on macOS's BSD tools**, and **no gate runs `copilot`, `gh` or
  touches the network**: a stub agent stands in, as in B19 and B22.
- Tests build fixtures in temporary directories and address them with
  `git -C`; sessions never move refs.
- **Gates follow the diff surface; a gate never runs the suite (P-8).**
- **No task may weaken a check to pass.** An earlier test changes only where it
  pins behaviour the contract changes, and only to the new behaviour; the work
  session names the contract item in its notes and the review cites it.
- **New tooling is proven by fixtures, including where it must fail**: every
  line of the worked example, the review phase's unchanged `rm` denial, each
  planted failure.
- Repo-relative paths everywhere. No absolute paths in any file or commit
  message.

## Acceptance on the real CLI, at close (the operator's)

The operator runs the URL shortener brief from `mvelosop/url-shortener-template`
with `agent.work = copilot` and `model.work = gpt-5.6-terra`, plan and review on
Claude, and the `app` check, and records in
`docs/design-notes/copilot-cli-experiments.md`: tasks done and first-pass, the
work sessions' credits and estimated cost, every hook denial with its reason
(how many were shell syntax the hook cannot judge, the measure for #83), and
the driver's halts or restorations, if any.

## Shape

4 to 6 tasks, each verifiable by a single command. Order is load-bearing:

1. **W1 — the judge's work phase**, through `vloop fence check`. Gated on the
   worked example's tables, and on the review phase's `rm` line unchanged.
2. **W1 and W2 — Copilot work sessions**: `fence hook --phase work`, the
   adapter supporting work, its argv and hooks file, `agent.work` accepting
   `copilot`. Gated with the stub agent's run.
3. **W2 — the preflight and doctor.** Gated on the warning and the planted
   failures.
4. **A1 — the audit, the guide and the domain pages.** Prose task: if it fails
   review twice on wording, block it and the operator finishes it.
5. **A1 — the acceptance kit.**
6. **Close:** every gate at once, and the worked example line for line.
