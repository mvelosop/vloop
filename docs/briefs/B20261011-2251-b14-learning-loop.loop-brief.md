# Brief — vloop B14: the learning loop

- **Starting point:** extends `main` after this design merges (`main` at
  `e504106`, B13 merged). The planner pins the base it plans from as the
  **base** every gate compares against — never `HEAD~n`.
- **Produced by:** the T1 triage, `docs/design-notes/vloop-t1-triage.md` → P3,
  P4 and P5, and the design act of 2026-10-11, with the forks settled with the
  operator (intervention recorded with this brief).
- **Run by:** `vloop run` from the released v0.9.0.

## Executive summary

A lesson about *this* repository has nowhere to live: it is not vloop's rule, so
it does not belong in a plugin skill, and a brief carries it only if the
architect remembers. The same spec gap — a must-change list missing the tests
that pin a list or a count — was recorded four times (`D20261004-1142`,
`D20261004-2304`, `D20261011-1455`, `D20261011-2239`). And the gate review
missed gate defects whose rule was already written. B14 gives lessons a home,
makes `vloop brief check` read it, and turns each gate-review miss into an eval
case.

**The goal:** a mistake recorded once becomes something the next run is told
about or checked for, instead of something the operator has to remember.

- **L1 — every session gets the repo's lessons.** A file of lessons,
  .vloop/repo-guidelines.md, is handed by `vloop run` to every session, so a
  lesson learned once reaches all later runs.
- **L2 — `init` creates that file.** New repositories start with an empty
  template, so the place for lessons exists from day one.
- **L3 — `brief check` catches the most repeated brief mistake.** The file
  lists which tests pin what; a brief that changes it without naming those
  tests gets a warning before the run, not a stalled task during it.
- **L4 — `brief check` asks where an external format comes from.** A brief
  that uses, say, an eval case without citing its definition gets a warning.
- **L5 — the gate review learns the two rules it missed.** A gate that needs a
  session to write under `.vloop/`, or a GNU-only pattern on macOS, is
  reported as `unpassable`.
- **L6 — the real misses become a test for the gate review.** Six gates that
  fooled it in past runs go into one eval case, to measure it from now on.
- **L7 — three broken eval cases are repaired.** They scored correct answers
  below 1, so they could not measure anything.
- **L8 — docs, and this repository's own lessons file.** The guide explains
  the file; you write this repository's copy at close from the text pinned
  below.
- **L9 — a rule must say why it exists, and the file has a budget.** Each
  guideline cites the defect or intervention it prevents, and `vloop doctor`
  warns past 20 rules or on a rule with no source: too many rules has hurt
  before, and a rule without a source cannot be pruned later.
- **L10 — the skills get word budgets.** A test fails when a plugin skill grows
  past its ceiling, so growth is a deliberate, recorded decision, not drift.
- **L11 — `vloop metrics` shows how much each session reads.** A new line per
  brief gives the words each session kind starts with (its skill, the
  guidelines, `CLAUDE.md`) and the rule count, back to B1, so the trend is
  visible.
- **L12 — closing a brief triggers the learning.** `vloop brief close` reports
  each defect with the rule that caught it, the rule that should have, or
  "untriaged", and the operate skill proposes what to do about each: without
  a trigger, lessons reach the file only when someone remembers.

Unchanged: no exit code, no schema version; `doctor` gains one line, the
metrics summary one line and one optional JSON field, a defect two optional
fields, and `brief close` a report. Pruning rules, and the
review skill's eval cases for statements that disagree, wait for B16.

## What it is

A repository using vloop gains .vloop/repo-guidelines.md: the lessons that
belong to it, handed to every loop session and read by `vloop brief check`,
which warns when a brief changes something a listed test pins without naming
that test, or names an external format without citing its source. The gate
review learns the two rules it missed, and the gates that fooled it become an
eval case, alongside the three eval cases repaired.

The blind spot: lessons were recorded as defects and interventions — evidence —
but never fed back as inputs. A defect said "the brief's must-change list
omitted X"; nothing made the next brief name X.

## Why this shape, and what was rejected

Decided with the operator on 2026-10-11 (the forks) and on 2026-10-08 (the
triage). **Do not re-litigate these** — the planner inherits them.

- **The driver hands the file to every session.** A rule in a skill is not a
  check: the gate review missed twice with its rule written down. *Rejected:*
  each skill reading the file when present (whether a session reads it is up
  to the session); the planner distributing it as a task reference (the gate
  review would not get it).
- **`--append-system-prompt-file`, the file's content, not a pointer to it.**
  The session has it without spending a turn, and an empty or missing file
  adds nothing. The flag is the one `claude --help` lists.
- **`brief check` reads two structured sections of the file.** A repository
  owns its list of pinning tests; vloop cannot guess them. *Rejected:* a
  generic heuristic ("adds a config key and has no must-change list"), which
  misses the list that is present but incomplete — every recorded case.
- **The `.vloop/` write rule goes to the gate review, not to `brief check`.**
  The triage proposed a `brief check` error; a wording match over the
  Behaviour contract, tried on B10–B13, flagged B12's and B13's contracts,
  which describe the driver's and the operator's writes. The gate review reads
  the gate, which is where the write happens.
- **The six misses go in one case.** One session reviews seven gates, as
  `gate-review-planted-gates` reviews five, at a seventh of the cost.
- **Provenance and a budget now, pruning later.** A rule that cites no
  defect or intervention cannot be judged when it is time to prune, and
  adding that later means guessing. The budget, 20 rules, is a warning: the
  operator decides what to retire. *Rejected:* a hard cap (blocks a lesson
  when it is most needed); pruning in this brief (it needs the eval runs B16
  sets up).
- **Words measure the skills; a test enforces their ceilings.** Skills are
  prose; a count of their rules needs every skill restructured. The skills are
  vloop's own, so a failing test, not a user-facing warning, makes growth a
  decision. **The metrics line shows the trend**, from git, back to B1.
- **Close is the trigger, and it reports rather than refuses.** Close is
  where defects are recorded, so the question "which rule caught this, or
  should have?" is asked there, every brief. Whether a defect deserves a rule
  is the operator's decision, so an untriaged defect is a hint, not a refusal.
  A prose guideline leaves no trace when it works, so for guidelines the
  report can show `missed`, never prove `fired`. *Rejected:* a separate
  triage command (one more step to forget); refusing to close (it would push
  rules in to get past the gate, the bloat this brief guards against).
- **The review skill's eval cases wait for B16**, which measures the review.
  *Rejected:* all of P4 here (a longer brief and a costlier acceptance run).

## Behaviour contract

Messages are exact where quoted; `<…>` marks a value.

### L1 — the guidelines file reaches every session

**Required.**
- When .vloop/repo-guidelines.md exists in the repository root (C-2) and is
  not empty, every session `vloop run` starts — plan, gate review, work and
  review — gets `--append-system-prompt-file .vloop/repo-guidelines.md` added
  to its `claude` arguments (sessions start in the repository root). The flag and its spelling are confirmed against
  `claude --help`; a task that finds it absent halts and says so.
- When the file is missing or empty, the arguments are exactly today's.
- The four skills (`plugin/skills/plan`, `gate-review`, `work`, `review`) each
  gain one short paragraph: the repository's guidelines may be appended to
  the session's instructions; the planner applies them to tasks and gates and
  cites them in `references` where a task needs one; the gate review reports a
  gate that contradicts one, under the kind it fits; the work session follows
  them; the review rules on a deviation as it would on the brief's
  constraints. A guideline never overrides the brief or a domain invariant.
- The session record is unchanged: no new field.

### L2 — `init` writes an empty one

**Required.**
- `vloop init` writes .vloop/repo-guidelines.md when it does not exist and
  prints `wrote .vloop/repo-guidelines.md`, right after the
  `wrote .vloop/install.json` line. An existing file is kept, untouched, and
  nothing is printed for it.
- The template is short: a title, one sentence saying the file holds this
  repository's lessons and every loop session receives it, the headings
  `## Pinning tests` and `## External formats`, each with one sentence and one
  commented-out example line in the format L3 and L4 read. Its prose follows
  `language` (C-4); the two headings are the same in every language, because
  `brief check` reads them.

### L3 — must-change lists and pinning tests

**Required.**
- `vloop brief check` reads the repository's .vloop/repo-guidelines.md when
  it exists; under `## Pinning tests`, each line of the form
  `` - when `<phrase>`: `<name>`, `<name>`… `` is a rule. Other lines are
  ignored.
- For each rule: when the brief's **Behaviour contract** section contains
  `<phrase>`, case-insensitively, and its **Constraints** section does not
  contain one or more of the names, it adds one warning:
  `must-change list: the contract mentions "<phrase>" but Constraints do not name <name>, <name> (.vloop/repo-guidelines.md)`,
  the names in the rule's order.
- Sections are found by the repository's heading set (B-3, B-4).
- A guidelines file that exists but has no such section, or no such lines,
  adds nothing. A malformed line is ignored.

### L4 — external formats

**Required.**
- Under `## External formats`, each line of the form
  `` - `<phrase>`: `<path>` `` is a rule. When the brief's **Behaviour
  contract** contains `<phrase>`, case-insensitively, and its **Binding
  references** do not cite `<path>`, it adds one warning:
  `external format: the contract mentions "<phrase>" but Binding references do not cite <path> (.vloop/repo-guidelines.md)`.

### L5 — the gate-review skill

**Required.** In `plugin/skills/gate-review/SKILL.md`:
- `unpassable` also names a gate that needs a session to write under `.vloop/`
  outside `.vloop/tmp/` (S-4), the plan session's own gate folders aside.
- Check 1 says the gate is run, and read, in the plan's `shell` with this
  host's tools: `sh` unless the config names another (P-5), and on macOS BSD
  `grep`, `sed`, `awk` and `date`. A pattern those tools reject is `unpassable`.
- No other kind or check changes.

### L6 — `gate-review-real-misses`

**Required.**
- A new case under plugin/evals/gate-review-real-misses/, in the format of
  `docs/guide/evals.md`, beside `gate-review-planted-gates` and built like it:
  a scaffold that writes a repository with a brief, a plan of seven tasks and
  their gates, and graders.
- Six tasks carry the six gates of the defects cited in Binding references,
  reduced to the defect's mechanism; one carries a sound gate.
- The plan's `shell` is `"sh"`.
- `scaffold.sh` exits non-zero unless, run on the host, each planted gate
  fails on the base for its recorded reason and the sound gate fails on the
  base at its behavioural assertion (check 1). The GNU-`grep` gate reproduces
  only with BSD `grep`: the case is for macOS hosts, and the evals README says
  so beside it.
- Graders: the verdict is `FAIL`; each defective gate is a finding of kind
  `unpassable`, as each recorded defect describes it; the sound gate is not a
  finding.
- The evals README's gate-review table, and `docs/guide/evals.md` where it
  lists cases, gain the case.

### L7 — the three eval defects

**Required.**
- `plan-checks-its-gates`: the grader that judges the planner's gate-folder
  fixtures reads the files under `.vloop/state/gates/` the session wrote, not
  the trace (`D20261004-1309`).
- `operate-proposes-options`: the scaffold puts the plan and the iterations on
  a work branch named for the run id, `main` untouched; the plan has at least
  three tasks, the first done, the second halted on a gate dispute
  (`D20261006-1028`). The graders score what the skill's step names: one to
  three real options, one recommended with its reason, no gate amended before
  the operator answers, no straw option (`D20261005-0757`).
- No other case changes.

### L8 — the docs

**Required.**
- `docs/guide/concepts.md` gains **`## Repository guidelines`**: what the file
  is, that `vloop run` hands it to every session, the two sections and their
  line formats, the two warnings, that a lesson there replaces a constraint
  repeated brief after brief, and `vloop defect set <id> fixed-by guideline`
  for a defect a guideline now prevents. The `.vloop/` layout list gains the
  file.
- `docs/domain/briefing/brief.md` lists the two warnings with the others.
- `docs/guide/commands.md` is regenerated if any help text changes.

### L9 — provenance and the rule budget

**Required.**
- A **rule** is a line of .vloop/repo-guidelines.md that starts with `- ` at
  the left margin, in any section, including `## Pinning tests` and
  `## External formats`. A line inside an HTML comment (`<!-- … -->`), as
  the template's examples are, is not one.
- A rule's **provenance** is one or more defect or intervention IDs in it: a
  token `D<8 digits>-<4 digits>` or `I<8 digits>-<4 digits>`, optionally
  followed by the rest of the ID. L3 and L4 read a rule's names and paths
  before a trailing parenthesis, so `` - when `config key`: `TestA` (D20261011-1455) ``
  is one rule whose name is `TestA`.
- `vloop doctor` gains a check, **`guidelines`**, printed right after
  `gate edits`:
  - no file: `- guidelines`;
  - within budget, every rule with provenance: `✓ guidelines <n> rule(s)`;
  - over 20 rules: a warning,
    `! guidelines <n> rules, over the budget of 20 — retire or merge some before adding more`;
  - rules without provenance: a warning,
    `! guidelines <k> rule(s) cite no defect or intervention: line <a>, line <b>`;
  - both: one warning line, the two messages joined by `; `.
- The budget is 20, not configurable. Both are warnings: no exit code changes.

### L10 — the skills' word budgets

**Required.**
- A test in this repository counts each plugin skill's words — the
  whitespace-separated words of the whole SKILL.md, frontmatter included — and
  fails when one exceeds its ceiling, naming the skill, its count and the
  ceiling.
- The ceilings: `plan` 4,100; `gate-review` 1,550; `work` 1,800; `review`
  1,650; `operate` 1,750. They live beside the test with one comment each,
  saying when and why the ceiling was last set.
- Raising a ceiling is an edit of that comment and number, which the review
  rules on like any change to a check.

### L11 — the metrics `instructions` line

**Required.**
- For each brief, `vloop metrics` computes, at the commit its delivered lines
  are measured to (M-2), the words each session kind starts with: its skill +
  .vloop/repo-guidelines.md + the root `CLAUDE.md`, each counted as L10 counts
  and 0 when absent. A kind's skill is `plugin/skills/<kind>/SKILL.md`, or,
  where that does not exist at the commit, the shell loop's
  `.claude/skills/loop-<kind>/SKILL.md` (plan, work and review); with neither,
  the kind is `n/a`. It also counts the guidelines file's rules (L9).
- The brief summary gains a line after `interventions`:
  ` instructions  plan <n> · gate review <n> · work <n> · review <n> words · guidelines <n> rules`,
  numbers with thousands separators as elsewhere, `n/a` for a missing kind.
- `--json` gains an optional object, `instructions`:
  `{"plan": n|null, "gate_review": n|null, "work": n|null, "review": n|null, "guidelines_rules": n}`.
  It is optional in metrics/v2, as `wall_ms` was in session records: no schema
  version changes. `brief close` freezes it with the rest.
- Computed from git (M-1); nothing is recorded during a run.

### L12 — the defect report at close

**Required.**
- A defect record gains two optional fields, set with `vloop defect set`:
  - `rule`: the rule that caught the defect, or should have, as
    `<where>: <which>`, where `<where>` is one of `guideline`, `brief-check`,
    `gate`, `gate-review`, `review`, `skill`; e.g. `guideline: D20261011-1455`
    (a guideline named by its provenance ID), `brief-check: must-change list`,
    `gate-review: unpassable`.
  - `rule-outcome`: `fired` (the rule caught it), `missed` (the rule existed
    and did not catch it), `absent` (no rule existed; one should), `none` (no
    rule is warranted; the reason goes in the defect's body).
  - `vloop defect set` refuses any other `rule-outcome` with exit 2, and a
    `rule` whose `<where>` is not in the list. defect/v1 gains the two
    properties as optional: no schema version changes, and records without
    them stay valid.
- `vloop brief close`, after recording the findings and before its
  `squash-merge with the trailer` line, which stays last, prints the brief's
  defects, every one recorded for the brief, one line each:
  ```
  defects of <run id>
    <id>  <kind>  <found-by>  <rule or —>  <rule-outcome or untriaged>[  recurs ×<n> (<id>, <id>)]
  ```
  then, when any is untriaged,
  `<n> untriaged: vloop defect set <id> rule '<where>: <which>' and rule-outcome fired|missed|absent|none`.
  With no defects it prints `defects of <run id>: none`.
- **recurs**: other defects, of any brief, with the same `rule`, listed by
  short ID (`D<stamp>`), oldest first, at most three, with the total count.
  An untriaged defect has no `rule`, so it never recurs.
- `--dry-run` prints the report as it would be; `--json` is unchanged. Close
  never refuses for an untriaged defect.
- `plugin/skills/operate/SKILL.md`'s close step gains the triage: for each
  untriaged defect, propose its `rule` and `rule-outcome` as options, as the
  skill proposes any decision, and record the operator's choice. For
  `absent`, draft the guideline line with its provenance, or the check; for a
  `gate-review` rule that `missed`, propose an eval case and the defect's
  `case:` (T1 P4). The skill stays within its L10 ceiling.

### Decided here, because the cited documents leave it underdetermined

- Phrases match as plain substrings, case-insensitively; names and paths as
  plain substrings. No regular expressions in the file.
- The file is read from the repository root, never from `HOME`.
- `fixed-by: guideline` is a value, not a schema change: `fixed-by` is free text.
- A guideline file larger than 16 KiB is still handed over whole; size is the
  repository's business.

### Violations the review must rule on

- Any session's arguments changing when there is no guidelines file.
- A warning that becomes a problem, or changes `brief check`'s exit code.
- A rule read from the whole brief rather than its named section (B-4).
- A case format, grader type or field not in `docs/guide/evals.md`.
- A session asked, by a gate or a task, to write under `.vloop/` outside
  `.vloop/tmp/` — including this repository's seed (S-4).
- A skill ceiling raised, or a skill trimmed, to make room, beyond what L10 sets.
- A close that refuses, or a report that writes anything, for an untriaged defect.
- Any skill changed beyond the paragraphs L1, L5 and L12 name; any eval case changed
  beyond L6 and L7.

  skill's eval cases for statements that disagree); **B17, `vloop release`**.
- A `brief check` rule for a session writing under `.vloop/`.
- `vloop upgrade` writing the guidelines file; `doctor` checking it.
- Reading guidelines from `HOME` or any global location.
- A new field in any schema; a new finding kind.
- Changing any eval case other than the three L6 and L7 name.
- Writing this repository's .vloop/repo-guidelines.md (the operator's, at close).
- **Pruning rules** (B16): running eval cases with and without a rule, counting

## Constraints

- Go as pinned in `go.mod`; no new dependencies. Every gate builds for
  `windows` and `linux` as well as the host.
- Gates run on macOS's BSD tools: no empty alternatives in `grep -E`, no
  `sed -i` without a suffix, no `\+` or `\|` in basic regexes, no `date -d`.
  A scratch directory is `mktemp -d "${TMPDIR:-/tmp}/gate.XXXXXX"`.
- Sessions never move refs and write nothing under `.vloop/` but `.vloop/tmp/`
  (S-4): no task's work, and no gate, may require a session to change this
  repository's records, config or state. Tests build their repositories in
  temporary directories, with a temporary `HOME`, and address them with
  `git -C`.
- **The gate model applies** (`plugin/skills/plan/SKILL.md`): each gate judges
  this brief's contract by running the built binary, a case's scaffold, or
  reading the changed document, with its judge in the verify or its gate
  folder; no gate runs the repository's tests — this repository's `[[check]]`
  does, after every iteration. A gate that greps a document checks the
  headings and the exact strings this brief pins, nothing looser. No gate runs
  `claude` or the eval suite.
- An eval case's format comes from `docs/guide/evals.md` and the cases beside
  it, never from memory; the repository's skill checks (run by `[[check]]`)
  must accept it.
- A prose task that fails review twice on wording, not on a gate, is blocked
  for the operator, who finishes it by hand.
- **No task may weaken a check to pass.** These earlier tests **must** change,
  and only as stated:
  - `TestInitWritesEverything` (`internal/cli/init_test.go`) — the new
    `wrote .vloop/repo-guidelines.md` line;
  - `TestWorkedExampleB5Session` (`cmd/vloop/b5_e2e_test.go`) — `init`'s
    output gains a line;
  - `TestSessionArgs` (`internal/driver/session_test.go`) — only if the
    function it calls gains a parameter; the arguments it pins, with no
    guidelines file, do not change;
  - the skill and eval structure tests in `internal/cli/skills_test.go` only
    where they count or list cases;
  - `TestDoctorWorkedExampleText` (`internal/cli/doctor_test.go`),
    `TestWorkedExampleB5Session`, `TestWorkedExampleB11`
    (`cmd/vloop/b20261005_e2e_test.go`) and `TestWorkedExampleB13`
    (`cmd/vloop/b13_e2e_test.go`) — only by the new `guidelines` line and, where
    pinned, the warning count, in the doctor output they pin;
  - tests that pin the metrics brief summary line by line
    (`internal/metrics/print_test.go`, `internal/cli/metrics_test.go`,
    `cmd/vloop/b3_e2e_test.go`, `cmd/vloop/b4_e2e_test.go`) — only by the
    `instructions` line;
  - `TestCloseCommitsFindingsSnapshotAndBrief` (`internal/cli/close_test.go`)
    and B4's worked-example test (`cmd/vloop/b4_e2e_test.go`) — only by the
    report's lines before the trailer, where they pin the output in full;
  - `docs/guide/commands.md`'s staleness test (regenerate, as always;
    `defect set`'s help lists the two new fields).
- Repo-relative paths everywhere. No absolute paths in any file or commit
  message.
