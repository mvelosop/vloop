# Brief — vloop B43: pwsh gates and checks in UTF-8

- **Starting point:** extends `main` as it stands when the run starts, with
  this brief's ready commit on the run branch. The planner pins that SHA as
  the **base** every gate compares against — never `HEAD~n`.
- **Produced by:** operator decision, 2026-11-26 (issue #162, part 2: vloop
  sets UTF-8 when it starts pwsh, and the guide documents it), the remaining
  forks settled by the operator's hands on the recommended options.
- **Review:** `vloop brief review` (Copilot, mai-code-2), seven rounds; every
  finding fixed but one, overridden by the operator's hands. Fixed: the gate
  uses `-Quiet` as a condition (a non-matching `Select-String` exits 0); the
  gates cover all three encodings, their preambles, stdin and `powershell`;
  `vloop task gate`'s real output and exit 1; the count of assertions.
  Overridden: the reviewer, in its own Copilot shell, could not reproduce the
  code page 437 defect. The operator measured it twice on the run's machine,
  the second time through `state.RunGate` from the driver's console (see
  U1); a Copilot shell's console is not on code page 437, which is why
  sessions must not take their own shell as proof.
- **Run environment:** planned and run on Windows, in pwsh, every session on
  GitHub Copilot (`.vloop/config.local.toml`). See Constraints.

## Executive summary

On Windows, pwsh decodes a native program's output that it pipes or captures
with `[Console]::OutputEncoding`, which defaults to the OEM code page (437 on
the machine that ran B40), not UTF-8; it writes its own output to a pipe with
the same encoding. vloop's tools all write UTF-8. So in a pwsh gate,
`git log -1 --format=%s | Select-String -SimpleMatch 'café' -Quiet` is false for a commit whose
subject is `café`, and what the gate prints reaches vloop's gate log as code
page 437 bytes: B40's run tab showed `—` as `ΓÇö` and `·` as `┬╖`. A mixed team
(B40) writes every gate in pwsh, so this now meets every Windows member.

**The goal:** a gate or check that vloop runs in `pwsh` or `powershell` reads
native output as UTF-8 and writes UTF-8, on every OS.

- **U1 — vloop starts pwsh in UTF-8.** Every gate and check vloop runs in
  `pwsh` or `powershell` runs with UTF-8 input and output encodings set before
  its command, without a byte-order mark, printing nothing of its own.
- **U2 — the guide says so,** and gives the one line a person adds to their
  own pwsh profile for their terminal.

Unchanged: the command text a plan or config records and shows; the exit code
a gate or check returns; `sh`, `bash` and `cmd` gates; how sessions' own pwsh
commands run (the agent starts those, not vloop).

## What it is

One change where vloop builds the command line of a pwsh gate
(`internal/state/gate.go`, `GateCommand`, which every gate runner and the
checks use), plus a guide paragraph. It is for every repository whose gates
or checks run in pwsh, which a mixed team's always do.

## Why this shape, and what was rejected

Decided on 2026-11-26. **Do not re-litigate these.**

- **vloop sets the encodings, in the command it starts.** The setup runs
  inside the same pwsh process, before the recorded command, so the plan's
  shell still governs (P-5) and nothing about the machine changes.
  *Rejected:* documenting it only (every Windows gate author would have to
  remember it, and a gate that forgets fails only on Windows); changing the
  machine's code page or the user's profile (global state).
- **On every OS.** pwsh on macOS and Linux already uses UTF-8; setting it
  there too keeps one code path and makes the same gate behave the same way
  everywhere. *Rejected:* Windows only (two code paths, one of them untested
  on the other OS).
- **Both directions, no BOM.** `[Console]::OutputEncoding` (what pwsh decodes
  from native programs and writes to its own stdout),
  `[Console]::InputEncoding`, and `$OutputEncoding` (what pwsh sends to a
  native program's stdin) are all UTF-8 without a byte-order mark.
  *Rejected:* `[System.Text.Encoding]::UTF8`, which carries a BOM that pwsh
  can emit before the first output byte.

## Behaviour contract

### U1 — UTF-8 in pwsh gates and checks

**Defect.** `GateArgs` starts `pwsh`/`powershell` with `-NoProfile
-NonInteractive -Command <command>` and nothing else, so on Windows the
encodings are the console's code page.

**Required.** For `pwsh` and `powershell`, the process vloop starts sets
`[Console]::OutputEncoding`, `[Console]::InputEncoding` and `$OutputEncoding`
to UTF-8 without a BOM before the command runs, then runs the command exactly
as recorded. This holds for every caller of `GateCommand`: a task's gate run
by the driver or by `vloop task gate`, the gates run at plan acceptance, the
`[[check]]` runs, and `tools/release`'s shell commands.

- The setup prints nothing to stdout or stderr, and never changes the exit
  code: a gate that exits 3 still exits 3, a gate that exits 0 still exits 0.
- It works with no console attached (vloop starts gates with their output
  redirected); if setting an encoding fails, the command still runs and its
  exit code still stands.
- What vloop shows or records as the gate's command (`vloop task show`, the
  plan, the gate log's header, the journal) is the recorded command, without
  the setup.
- `sh`, `bash` and `cmd` gates are started exactly as today.

**The defect depends on the console vloop inherits.** pwsh takes its
encodings from the console code page of the process that starts vloop. The
operator measured it on this machine on 2026-11-26 through vloop's own gate
runner (`state.RunGate`, output redirected to a buffer, as the driver runs
gates), started from the console this run's driver runs in (`chcp`:
`Active code page: 437`); the `-Quiet` gate below exited 1 in both shells:

| shell | `Write-Output 'café'` bytes | Output / Input code page | `$OutputEncoding` | git's `café` read as |
|---|---|---|---|---|
| pwsh 7.7 | `63 61 66 82 0d 0a` | 437 / 437 | 65001 | `caf├⌐` |
| powershell 5.1 | `63 61 66 82 0d 0a` | 437 / 437 | 20127 | `caf├⌐` |

A console already on code page 65001 shows no defect, so a session's own
shell may see none: sessions must not take that as proof either way. The
gates run in the driver, in the run's console, where the table holds.

**Gate.** Tests through the gate runner (`GateCommand`), each for `pwsh` and,
on Windows, `powershell`; together they fail before the fix from a code page
437 console and pass after it on any console. A non-matching
`Select-String` alone still exits 0, so the tests use `-Quiet` as a
condition:

- **Reading native output:** in a temporary git repository whose last
  commit's subject is `café`, the gate
  `if (-not (git log -1 --format=%s | Select-String -SimpleMatch 'café' -Quiet)) { exit 1 }`
  exits 0.
- **Writing its own output:** the gate `Write-Output 'café'` gives vloop the
  bytes `63 61 66 c3 a9` followed by the line end (`0d 0a` or `0a`), with no
  `ef bb bf` before them.
- **The three encodings, without a BOM:** the gate
  `if ([Console]::OutputEncoding.CodePage -ne 65001 -or [Console]::InputEncoding.CodePage -ne 65001 -or $OutputEncoding.CodePage -ne 65001 -or [Console]::OutputEncoding.GetPreamble().Length -ne 0 -or [Console]::InputEncoding.GetPreamble().Length -ne 0 -or $OutputEncoding.GetPreamble().Length -ne 0) { exit 1 }`
  exits 0.
- **To a native program's stdin:** the gate
  `if (('café' | git hash-object --stdin) -ne '<hash>') { exit 1 }` exits 0,
  where `<hash>` is what `git hash-object --stdin` prints for the bytes
  `63 61 66 c3 a9` followed by the line end pwsh appends (`0d 0a` on Windows,
  `0a` elsewhere), computed by the test from those bytes, not hardcoded.
- A gate `exit 3` returns 3 from the gate runner and prints nothing; an `sh` gate is started with
  the same arguments as before.

### U2 — the guide

`docs/guide/configuration.md`'s "Mixed teams" gains a paragraph: vloop runs
pwsh gates and checks with UTF-8 input and output, so they read native tools'
output correctly on Windows; a person's own pwsh terminal does not, and the
line `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()` in their
pwsh profile makes `vloop run … | Tee-Object` and similar pipes show vloop's
output correctly.

### Decided here, because the cited documents leave it underdetermined

- **Where the setup lives** is the implementer's: a prefix in the `-Command`
  string, or another pwsh mechanism, as long as the contract above holds.
- **The literal `café`** is the gate's fixture; the test builds the commit in
  a temporary repository with `git -C`.

### Violations the review must rule on

- A recorded or shown gate command that includes the setup.
- A changed exit code, or output the setup adds, in any shell.
- A change to `sh`, `bash` or `cmd` invocation.
- An earlier test edited for anything but the new behaviour (a test that pins
  pwsh's exact argument list may change to the new list).

## Worked example

In a temporary git repository whose last commit's subject is `café`, with
`shell = "pwsh"` in `.vloop/config.toml` and a plan whose task T1 has the
gate `if (-not (git log -1 --format=%s | Select-String -SimpleMatch 'café' -Quiet)) { exit 1 }`,
T2's gate `Write-Output 'café'` and T3's gate `exit 3`:

```
vloop task gate T1                 (Windows, console code page 437)
  -> gate T1: pass (<duration>)                                   exit 0

vloop task gate T2
  -> café
     gate T2: pass (<duration>)                                   exit 0
     (the gate's own output bytes: 63 61 66 c3 a9, then the line end)

vloop task gate T3
  -> gate T3: fail (exit 3, <duration>)                           exit 1
     (vloop task gate exits 1 for any failing gate)

vloop task show T1
  -> verify  if (-not (git log -1 --format=%s | Select-String -SimpleMatch 'café' -Quiet)) { exit 1 }   (that line)
```

Before the fix, on Windows, T1 exits 1 (pwsh decodes `café` as `caf├⌐`) and
T2's bytes are `63 61 66 82`.

## Acceptance, at close (the operator's)

On Windows, the operator runs the worked example's three lines by hand with
the built CLI in a scratch repository, from a pwsh terminal whose console
code page is 437 (`chcp` prints `Active code page: 437`). The verify session's
fence denies `vloop init`.

## Out of scope

- The sessions' own shell commands (the agent starts them) and the fence
  (B42).
- `cmd` gates and their code page.
- Changing anything on the machine: code pages, profiles, the registry.
- vloop's own console output, which is already UTF-8.

## Constraints

- Go, as pinned in `go.mod`; `go run ./tools/check` is the `[[check]]` and
  passes after every task.
- **This run is on Windows, the only OS where the defect shows.** Most
  `cmd/vloop` end-to-end tests skip on Windows; gate through the built CLI or
  an oracle test in the task's gate folder that calls the gate runner, never
  through those end-to-end tests. New tests run on every OS; on macOS and
  Linux they pass before the fix too, which is expected.
- **Gates follow the diff surface.** No gate runs the whole suite or the
  check (P-8).
- **No task may weaken a check to pass.** An earlier test changes only where
  it pins behaviour the contract changes, and only to the new behaviour.
- Tests build their repositories in temporary directories and address them
  with `git -C`. Sessions never move refs. Repo-relative paths everywhere.
