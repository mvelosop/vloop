## Executive summary

Bringing vloop up to date takes three steps, and only the last is a vloop
command: `go install github.com/mvelosop/vloop/cmd/vloop@latest` by hand,
`claude plugin update vloop@vloop` and `copilot plugin update vloop@vloop` by
hand, then `vloop upgrade` in each repository. Doctor already warns when the
plugin and the binary disagree, and tells the operator to run the agent's
command.

**The goal:** one command, `vloop self-update`, brings the binary and every
installed vloop plugin up to date, and says what to run next.

- **S1 — the binary.** `vloop self-update` finds the latest release with the
  Go toolchain and installs it with `go install` when it is newer than the
  running binary; `--check` only reports; `--version <v>` installs that
  version. It refuses, with a reason and the command to run instead, when it
  cannot do it safely.
- **S2 — the plugins.** It then updates the vloop plugin of each agent CLI on
  PATH that lists it from where it runs (for `claude`, after refreshing the
  marketplace, as the release notes say), and reports each.
- **S3 — the pointers.** `vloop upgrade`'s help, doctor's two plugin-version
  warnings and the guide name `vloop self-update`.

Unchanged: `vloop upgrade` (the repository), doctor's other rows, and every
command that runs offline today stays offline: only `self-update` uses the
network.

## What it is

A new top-level command for whoever installed vloop with `go install`, which
is how the README installs it. It does the two machine-wide steps of an update
and points to the per-repository one.

## Why this shape, and what was rejected

Decided with the operator: the name, on 2026-11-01 (issue #98). The rest on
2026-11-26. **Do not re-litigate these.**

- **`vloop self-update` for the binary and the plugins; `vloop upgrade` keeps
  its meaning** (the repository). *Rejected* (issue #98): `vloop upgrade` for
  the binary with the repository refresh renamed; one command doing all
  three, which needs a re-exec and hides which step failed.
- **The Go toolchain is the channel.** The latest release is what
  `go list -m -json github.com/mvelosop/vloop@latest` reports, run outside
  any module; the install is `go install
  github.com/mvelosop/vloop/cmd/vloop@<version>`. *Rejected:* the GitHub API
  or downloading release assets (a second channel the README does not use,
  and credentials or rate limits).
- **Only forward, unless asked.** Without `--version`, it installs only a
  version newer than the running one by semver; a pre-release user whose
  build is newer than the latest release is told so and nothing is installed.
  `--version <v>` installs exactly `<v>`, older or a pre-release.
  *Rejected:* always installing `@latest` (it would downgrade
  `v0.15.0-rc.4` to `v0.14.0`).
- **Refuse rather than guess.** No `go` on PATH, a binary built from a
  checkout (no module version), or a running binary that is not where
  `go install` writes are refusals with the command to run instead.
  *Rejected:* installing anyway (the new binary would land where PATH does
  not find it, and the operator would keep running the old one).
- **No network in doctor or `vloop upgrade`.** They point to `vloop
  self-update` in their text; they do not check for a newer release.
  *Rejected:* a latest-release row in doctor (doctor runs offline and fast,
  and runs as `vloop run`'s preflight).
- **A plugin failure is reported, not fatal.** The binary step is the one
  that matters; a plugin update that fails prints its reason and the command
  to retry, and the command still exits 0. *Rejected:* exit 1 on a plugin
  failure after the binary was replaced (the operator would think nothing
  happened).

## Behaviour contract

`vloop self-update [--check] [--version <v>]`, runnable anywhere (it needs no
repository). Every message below is exact; `<path>` is printed with the home
directory as `~`. "Current" is the running binary's module version
(`v0.15.0-rc.4`); versions are compared by semver.

### S1 — the binary

In order:

1. **No Go:** `go` not on PATH:
   `vloop: self-update needs go on PATH — install the release by hand: go install github.com/mvelosop/vloop/cmd/vloop@latest`, exit 1.
2. **A checkout build:** no module version (built from a checkout, `(devel)`):
   `vloop: this vloop was built from a checkout, not installed from a release — build it again from the checkout, or go install github.com/mvelosop/vloop/cmd/vloop@latest`, exit 1.
3. **The target.** With `--version <v>`, `<v>` (it must start with `v` and be
   valid semver, else `vloop: --version <v> is not a version like v0.15.0`,
   exit 2). Otherwise the latest release from `go list -m -json
   github.com/mvelosop/vloop@latest`, run in a temporary directory; if that
   fails: `vloop: cannot find the latest release: <go's first line of
   error>`, exit 1.
4. **`--check`** prints two lines and exits 0, installing nothing:
   ```
   current  v0.14.0
   latest   v0.15.0 — vloop self-update installs it
   ```
   or `latest   v0.15.0 — up to date` when the target is not newer than
   current. With `--version <v>` the second line is
   `target   <v> — vloop self-update --version <v> installs it`, or
   `target   <v> — already running` when `<v>` equals current.
5. **Nothing to install** (no `--version`, and the target is not newer):
   `vloop v0.15.0-rc.4 is up to date (latest release v0.14.0)`; go on to S2.
6. **Where it installs.** The install directory is `go env GOBIN`, else
   `$(go env GOPATH)/bin`. If `go env` fails or both are empty:
   `vloop: cannot find where go install writes: <reason>`, exit 1, nothing
   installed; `<reason>` is `go env`'s last line of error output when it
   fails, else `GOBIN and GOPATH are empty`. Step 6 runs only when an install
   is about to happen (step 7): never for `--check` or when nothing is to be
   installed. If the running binary is not exactly `<dir>/vloop` (`vloop.exe`
   on Windows), comparing resolved paths, case-insensitively on Windows:
   `vloop: this vloop runs from <path>, but go install writes to <dir> — update it the way you installed it, or put <dir> first on PATH`, exit 1, nothing installed.
7. **Install:** prints `installing vloop <target> (from <current>)…`, runs
   `go install github.com/mvelosop/vloop/cmd/vloop@<target>`, and on success
   prints `installed vloop <target> at <dir>`. On failure:
   `vloop: go install failed: <go's last line of error>`, exit 1; the running
   binary is left in place and still runs.
   - **On Windows** the running `vloop.exe` cannot be overwritten. It is moved
     aside to `vloop.exe.old` in the same directory before the install, and
     moved back if the install fails. A `vloop.exe.old` left by an earlier
     update is removed first; if it cannot be removed:
     `vloop: cannot remove <old> (<reason>) — delete it and run vloop self-update again`,
     exit 1, nothing installed. `<old>` is the path of `vloop.exe.old`.
     If moving `vloop.exe` aside fails:
     `vloop: cannot move <exe> aside (<reason>) — nothing was installed`, exit 1.
     If the install fails and moving it back fails too:
     `vloop: go install failed: <go's last line of error>; and <old> could not be moved back to <exe> (<reason>) — rename it back by hand`,
     exit 1. `<exe>` is the running binary's path.

### S2 — the plugins

After S1 (installed or up to date), for `claude` then `copilot`, each only
when on PATH:

- **Finding the plugin** is doctor's rule, reused: `<agent> plugin list
  --json` run from the current directory; for `claude`, doctor's `plugin` row
  rule exactly: an entry whose `id` starts with `vloop@`, with a version, and
  whose scope is `user` or empty, or any other scope whose project path
  matches the directory self-update runs in; for
  `copilot`, an entry whose `name` is `vloop`.
- **The update commands.** For `claude`, one per entry found:
  `claude plugin update vloop@vloop --scope <scope>` (`user` for an empty
  scope). `claude plugin update --help` printed, on 2026-11-26:
  `Usage: claude plugin update [options] <plugin>` and
  `-s, --scope <scope>  Installation scope: user, project, local, managed`. For
  `copilot`, one: `copilot plugin update vloop@vloop`. Another repository's
  project or local installation is updated by running `vloop self-update`
  there.
- For `claude`, `claude plugin marketplace update vloop` runs first (as
  `tools/release` tells a person to); if it fails, it prints
  `! plugin claude: claude plugin marketplace update vloop failed: <its last line of output> — run it by hand`
  and the update is not run.
- Found: run each update and print `plugin <agent>: updated` (for claude,
  `plugin claude (<scope>): updated`) on exit 0, else
  `! plugin <agent>: <the command> failed: <its last line of output> — run it by hand`
  (for claude, `! plugin claude (<scope>): …`).
- Not found: `plugin <agent>: not installed`.
- The list fails or is not JSON:
  `! plugin <agent>: cannot read <agent> plugin list --json: <reason> — run <agent> plugin update vloop@vloop by hand`.
- The agent is not on PATH: nothing is printed for it.

With `--version`, whatever the version, before S2 it prints
`! with --version, the plugins still update to their latest release, which may differ from vloop <target>`
(nothing in `--json`); no latest-release lookup is made for it. A plugin failure never changes the exit code. Then, when S1 installed a new
binary or any plugin was updated, one last line:
`next: vloop upgrade in each repository that uses vloop, and vloop self-update there for a plugin installed for that repository`.
Exit 0.

### `--json`

With the global `--json`, stdout carries exactly one JSON document and none of
the lines above; refusals stay one `vloop: ` line on stderr with the same exit
code, and no document. The document:

```
{"schema":"self-update/v1","current":"v0.14.0","target":"v0.15.0","newer":true,"installed":true,
 "dir":"<dir>","plugins":[{"agent":"claude","result":"updated","message":""}]}
```

`schema` is `self-update/v1`, an embedded JSON Schema (schemas/self-update.v1.json at the repository root, where every embedded schema lives) the document validates against.
`newer` says whether the target is newer than current; `installed` whether
this run installed it (always `false` with `--check`, which also leaves
`plugins` empty); `dir` is the install directory (`~` for the home) when the
run reached step 6, else empty; `result`
is `updated`, `not installed` or `failed`; for `failed`, `message` is exactly
the `<its last line of output>` or `<reason>` of the human line (the tool's
line alone, no prefix), and for the others it is empty. A claude entry also
has `"scope"` when it stands for an installation found; a claude entry for
`not installed` or for a list or marketplace failure has none. An agent not on PATH has no entry.

### S3 — the pointers

- `vloop upgrade --help` gains, in its long help: `To update the vloop binary
  and its plugins, run vloop self-update first.`
- Doctor's two plugin-version warnings end
  `… — vloop run is unaffected; vloop self-update updates the binary and the plugin`,
  replacing `claude plugin update vloop@vloop updates the plugin, or update the binary if it is the one behind`
  (and its copilot counterpart).
- `docs/guide/concepts.md`, where it explains `go install` and `vloop
  upgrade`, gains a paragraph on `vloop self-update` with S1's refusals in a
  sentence; `docs/guide/commands.md` is regenerated.
- `go run ./tools/release publish`'s last two lines become one:
  `then: vloop self-update, and vloop upgrade in each repository`.

### Decided here, because the cited documents leave it underdetermined

- **Paths outside the repository.** C-2 makes every path vloop prints
  relative to the repository root, with `/`. `self-update` needs no
  repository and prints the install directory and the binary's path, which
  are outside any repository: it prints them with `/` and the home directory
  as `~` (`~/go/bin`). This run adds that exception to C-2's line in
  `docs/domain/domain-model.md` and to `docs/domain/platform/platform-context.md`.

- **Tests fake `go`, `claude` and `copilot`** with small Go programs the test
  builds into a temporary directory put first on PATH, so the tests run on
  Windows too; no test reaches the network or the real tools.
- **Semver comparison** uses `golang.org/x/mod/semver`, already a dependency.
- **`--check` with `--version`** compares the running version with `<v>`.

### Violations the review must rule on
- A new network call, or a new call to `go`, `claude` or `copilot`, from any
  command but `self-update` (doctor's existing plugin-list calls stay).
- An install without `--version` that is not strictly newer than current.
- A test that calls the real `go install`, the real agents or the network.
- A changed message anywhere but S3's two doctor warnings and `upgrade`'s help.

## Worked example

With fakes on PATH (a fake `go` that reports `v0.15.0` as latest and installs
by writing a binary into its GOBIN; a fake `claude` whose plugin list has
`vloop@vloop`; no `copilot`), and the binary under test reporting module
version `v0.14.0`, run from its GOBIN:

```
vloop self-update --check
  -> current  v0.14.0
     latest   v0.15.0 — vloop self-update installs it              exit 0

vloop self-update
  -> installing vloop v0.15.0 (from v0.14.0)…
     installed vloop v0.15.0 at <GOBIN>
     plugin claude (user): updated
     next: vloop upgrade in each repository that uses vloop, and vloop self-update there for a plugin installed for that repository   exit 0

the same, the binary reporting v0.15.0-rc.4 and latest v0.14.0
  -> vloop v0.15.0-rc.4 is up to date (latest release v0.14.0)
     plugin claude (user): updated
     next: vloop upgrade in each repository that uses vloop, and vloop self-update there for a plugin installed for that repository   exit 0

vloop self-update --version v0.15.0-rc.5     (binary at v0.15.0-rc.4)
  -> installing vloop v0.15.0-rc.5 (from v0.15.0-rc.4)…
     installed vloop v0.15.0-rc.5 at <GOBIN>
     ! with --version, the plugins still update to their latest release, which may differ from vloop v0.15.0-rc.5
     plugin claude (user): updated
     next: vloop upgrade in each repository that uses vloop, and vloop self-update there for a plugin installed for that repository   exit 0

vloop self-update --version 0.15
  -> vloop: --version 0.15 is not a version like v0.15.0             exit 2

no go on PATH
  -> vloop: self-update needs go on PATH — install the release by hand: go install github.com/mvelosop/vloop/cmd/vloop@latest   exit 1

a checkout build
  -> vloop: this vloop was built from a checkout, not installed from a release — build it again from the checkout, or go install github.com/mvelosop/vloop/cmd/vloop@latest   exit 1

the binary run from a directory that is not GOBIN
  -> vloop: this vloop runs from <path>, but go install writes to <GOBIN> — update it the way you installed it, or put <GOBIN> first on PATH   exit 1

a fake claude whose plugin update exits 1 printing "network down"
  -> ! plugin claude (user): claude plugin update vloop@vloop --scope user failed: network down — run it by hand   (and exit 0)

a fake go install that fails printing "no matching versions"
  -> vloop: go install failed: no matching versions                   exit 1
     (on Windows, vloop.exe is back in place and runs)
```

## Acceptance, at close (the operator's)

No released binary has `self-update` until the next release, so at close the
operator checks, on the real machine, the build from the work branch:
`go build -o <tmp>/vloop.exe ./cmd/vloop`, then `<tmp>/vloop.exe self-update`
prints S1 step 2's checkout refusal, exit 1. The real-network path (a released binary, the real `go list` and `go
install`, the real agents) is checked by the operator at the next release,
with `vloop self-update --check` and `vloop self-update`, as part of
`tools/release publish`'s proof.

## Out of scope

- Any other install channel (Homebrew, Scoop, release downloads).
- A latest-release check in doctor, `vloop upgrade` or `vloop run`.
- Running `vloop upgrade` from `self-update`, or re-executing the new binary.
- Updating the agents themselves (`claude update`, Copilot's own update).
- The repository declaration of the plugin in `.claude/settings.json`, which
  `vloop upgrade` keeps.

## Constraints

- Go, as pinned in `go.mod`; `go run ./tools/check` is the `[[check]]` and
  passes after every task. No new dependency.
- **This run is on Windows.** The fakes are Go programs, never shell
  scripts, so every new test runs on Windows; gate through the built CLI or
  an oracle in the task's gate folder, never through the `cmd/vloop`
  end-to-end tests that skip on Windows.
- **No test touches the network or the real `go install`, `claude` or
  `copilot`.**
- **Gates follow the diff surface.** No gate runs the whole suite or the
  check (P-8).
- **No task may weaken a check to pass.** An earlier test changes only where
  it pins behaviour the contract changes, and only to the new behaviour.
- Tests build their repositories and fakes in temporary directories. Sessions
  never move refs. Repo-relative paths everywhere.
