# Brief — vloop B17: the release tool

- **Starting point:** extends `main` after this design merges (`main` at
  `374f7ef`, B16 merged, v0.11.0 released and installed). The planner pins the
  base it plans from as the **base** every gate compares against — never
  `HEAD~n`.
- **Produced by:** the roadmap's B17 row
  (`docs/design-notes/vloop-roadmap-b12-b17.md`), the T1 triage's P7, and the
  design act of 2026-10-15, with the forks settled with the operator.
- **Run by:** `vloop run` from the latest released vloop (0.11.0): the first run
  with a verify session.

## Executive summary

vloop has been released seven times by hand. Each time the same steps were
recorded (bump five files, PR, merge, tag, build, publish, check the public
install, upgrade), with the same note: a release command would do it. v0.11.0
also showed a gap: a public `go install …@v0.11.0` wrote `"commit":"unknown"`
to `.vloop/install.json`.

**The goal:** releasing vloop is two commands around the operator's merge, and
every install, public ones included, says exactly which release it is.

- **V1 — one version source.** The binary reads its version from the plugin's
  `plugin.json`; a bump is one line, and no test pins the version.
- **I1 — a public install is identified.** `.vloop/install.json` records the
  module version (`v0.11.0`) when the binary carries one.
- **N1 — release notes from the merged briefs.** The tool lists the briefs
  merged since the last tag, with their titles and descriptions, and the other
  code changes.
- **P1 — `prepare` opens the release PR** after checking that `main` is ready to
  release and the version is valid.
- **P2 — `publish` tags and publishes the merged release** and proves that
  `go install …@<version>` from the public proxy installs it.
- **D1 — the docs and this repository's playbook** describe the tool.

Unchanged: the merge stays the operator's; users' `vloop` gains no command;
`vloop upgrade`, the marketplace and the plugin's content work as today.

## What it is

A Go program in this repository, `go run ./tools/release`, with three
subcommands: `notes`, `prepare` and `publish`. `prepare` checks, bumps the
version on a release branch and opens the PR; the operator squash-merges it;
`publish` finds the merged release commit, tags it, pushes the tag, creates the
GitHub release and checks the public install. Each step it has already done is
skipped when run again, so a `publish` interrupted while the proxy catches up is
finished by running it again.

"Release" here is a **version release** of vloop: a tag and its publication. It
is not M-5's release of a brief (its merge).

## Why this shape, and what was rejected

Decided with the operator on 2026-10-15. **Do not re-litigate these** — the
planner inherits them.

- **A repository-owned tool**, not a `vloop` subcommand: every step (the
  module path, `plugin.json`, the proxy) is about releasing vloop itself, and a
  user's `vloop` would carry a command that works only here. *Rejected:*
  `vloop release`, as the roadmap row named it.
- **`plugin.json` is the one version source.** `vloop version` already reads
  the plugin's version from it; the binary's own version follows, so the two
  cannot disagree. *Rejected:* keeping the five edits and automating them.
- **Prepare, then publish.** The merge stays the operator's (T1); the two
  outward steps around it are the tool's. *Rejected:* checks only (the
  ceremony stays manual); one command that also merges.
- **Notes from the merged briefs**, found by their `Vloop-Brief:` trailers;
  the operator can edit the release afterwards. *Rejected:* notes written by
  hand per release.
- **The upgrade stays the operator's**: installing and `vloop upgrade` happen
  in each repository, interactively, after publish.

## Behaviour contract

Messages are exact where quoted; `<…>` marks a value. The tool's refusals are
one stderr line starting `release: `; exit codes are `0` done, `1` refused or
failed, `2` usage. A **version** is `vX.Y.Z` or `vX.Y.Z-<pre>` (semver); the
plugin's version is the same without the `v`.

### V1 — one version source

**Required.**
- The binary's version is the `version` of the embedded
  `plugin/.claude-plugin/plugin.json`. `cmd/vloop/main.go` holds no version
  literal; `-X main.commit=<sha>` still stamps the commit.
- `vloop version` and `vloop version --json` print exactly what they print
  today for the same build.
- No test pins a version literal: the tests that compared `0.11.0` read the
  embedded `plugin.json`.

### I1 — a public install is identified

**Required.**
- `vloop init` and `vloop upgrade` write `"module": "<module version>"` into
  `.vloop/install.json`, after `commit`, when the binary carries a module
  version (as `vloop version` prints it); they leave it out otherwise.
- `schemas/install.v1.json` gains `module` as an optional string; no schema
  version changes, and a stamp without it stays valid.

### N1 — `go run ./tools/release notes <from> <to>`

**Required.**
- Prints Markdown for the commits after `<from>` up to and including `<to>`
  (tags or revisions), on stdout, exit 0:
  ```
  ## Briefs

  - **<title>** — <description>

  ## Other changes

  - <subject>
  ```
- A brief is named by a commit's `Vloop-Brief: <name>` trailer; one line per
  brief, oldest first. `<title>` is the brief's first heading with a leading
  `Brief — ` and `vloop ` removed (`B16: the verification phase`), else the
  brief's name; `<description>` is its frontmatter `description`, both read at
  `<to>`.
- **Other changes** are the commits without the trailer whose changes touch a
  file outside `docs/`, `.vloop/` and `CLAUDE.md`, and whose subject does not
  start `Release v`, oldest first. A section with no lines is left out; with
  neither, the output is `No changes.`.

### P1 — `go run ./tools/release prepare <version>`

**Required.** It checks, in this order, refusing before anything is written:
- `<version>` is a version, else exit 2:
  `release: <version> is not a version: vX.Y.Z or vX.Y.Z-<pre>`;
- its major version fits the module path in `go.mod`:
  `release: <version> needs the module path to end in /v<major>, and github.com/mvelosop/vloop does not`;
- `go.mod` does not retract it: `release: <version> is retracted in go.mod`;
- it is after the highest existing version tag:
  `release: <version> is not after the latest release <tag>`;
- no tag `<version>` exists locally or on `origin`:
  `release: tag <version> already exists`;
- the current branch is `main`, the tree is clean, and `main` is `origin/main`
  after a fetch: `release: prepare runs on main, not <branch>`,
  `release: the working tree is not clean`,
  `release: main is not origin/main — pull or push first`;
- every `[[check]]` of `.vloop/config.toml` passes, then
  `claude plugin validate plugin`: `release: check <name> failed`, its output
  on stderr; `release: claude plugin validate plugin failed`.

Then it creates `release/<version>`, sets `plugin.json`'s version, commits
`Release <version>`, pushes the branch, opens a PR titled `Release <version>`
with N1's notes from the latest version tag to `main` as its body, and prints:
```
prepared release/<version>: <PR url>
squash-merge it, then: go run ./tools/release publish <version>
```
`--dry-run` makes every check and prints what it would do, writing nothing.

### P2 — `go run ./tools/release publish <version>`

**Required.**
- It fetches `origin` and finds the **release commit**: the newest commit on
  `origin/main` whose subject starts `Release <version>` and whose
  `plugin.json` holds the version. None:
  `release: no release commit for <version> on origin/main — merge the release PR first`.
- **Tag.** It creates the annotated tag `<version>` on the release commit,
  message `<version>: <brief titles joined by "; ">` (`<version>` alone without
  briefs), and pushes it. A tag already on that commit is kept; one elsewhere
  refuses: `release: tag <version> points at <sha>, not the release commit <sha>`.
- **GitHub release.** `gh release create <version> --verify-tag`, titled
  `<version>`, with N1's notes from the previous version tag to the tag;
  `--prerelease` for a version with a `-<pre>` suffix. An existing release is
  kept.
- **Public install.** Until `go list -m <module>@<version>` succeeds through the
  module proxy, it retries every 30 seconds up to `--wait` (default `10m`):
  `release: the module proxy does not serve <version> after <wait>`. Then
  `go install <module>/cmd/vloop@<version>` into a temporary `GOBIN`, and that
  binary's `vloop version --json` must report the version and module:
  `release: go install …@<version> reports version <v>, module <m>`.
- Each step already done prints `<step>: already done` and is skipped; a fully
  done release re-runs only the public-install check.
- On success it prints:
  ```
  published <version>: <release url>
  install: go install github.com/mvelosop/vloop/cmd/vloop@<version>
  then, in each repository: vloop upgrade
  and for the plugin: claude plugin marketplace update vloop && claude plugin update vloop@vloop
  ```
- `--dry-run` makes the checks it can without writing and prints each step.

### D1 — docs and playbook

**Required.**
- `docs/guide/concepts.md`, "The stamped release build": the version comes from
  `plugin.json`; the stamped build sets the commit only; the release steps are
  `prepare`, the operator's merge, `publish`, then install and upgrade.
- `.claude/skills/vloop-operator/SKILL.md` gains the release as a short step
  that runs the tool and records the release intervention.
- `tools/release` has a README of its own, under 300 words.
- `docs/guide/commands.md` is regenerated if any help text changed.

### Decided here, because the cited documents leave it underdetermined

- The tool is `package main` under `tools/release`, in this module; it may use
  this module's internal packages.
- It runs `git`, `gh`, `go` and `claude` from `PATH`; its tests put stubs
  there and use a local bare repository as `origin`, so no test reaches the
  network.
- Pre-release versions sort before their release (`v0.12.0-rc.1` <
  `v0.12.0`), as semver says.

### Violations the review must rule on

- The tool merging, or pushing to `main`.
- A refusal that wrote, committed, tagged or pushed anything.
- A version literal left in `cmd/vloop/main.go` or in a test.
- A test that reaches the network or the real `origin`.
- A `vloop` subcommand added for releasing.

## Worked example

In a temporary clone of a fixture repository whose `origin` is a local bare
repository, with stub `gh`, `go` and `claude` on `PATH`, latest tag `v0.11.0`,
`go.mod` retracting `v1.0.0`:

```
go run ./tools/release prepare 0.12.0
  -> release: 0.12.0 is not a version: vX.Y.Z or vX.Y.Z-<pre>                 exit 2
go run ./tools/release prepare v2.0.0
  -> release: v2.0.0 needs the module path to end in /v2, and github.com/mvelosop/vloop does not   exit 1
go run ./tools/release prepare v1.0.0
  -> release: v1.0.0 is retracted in go.mod                                     exit 1
go run ./tools/release prepare v0.11.0
  -> release: v0.11.0 is not after the latest release v0.11.0                   exit 1
on a branch other than main
  -> release: prepare runs on main, not <branch>                                exit 1
go run ./tools/release prepare v0.12.0
  -> prepared release/v0.12.0: <stub PR url>
     squash-merge it, then: go run ./tools/release publish v0.12.0              exit 0
     origin has release/v0.12.0, one commit "Release v0.12.0" changing only plugin.json's version

go run ./tools/release publish v0.12.0      (before the merge)
  -> release: no release commit for v0.12.0 on origin/main — merge the release PR first   exit 1
the release branch squash-merged into origin/main as "Release v0.12.0 (#n)"
go run ./tools/release publish v0.12.0
  -> published v0.12.0: <stub release url> … the four lines              exit 0
     tag v0.12.0 on the release commit, annotated; the stub gh saw "release create v0.12.0 --verify-tag"
the same again
  -> tag: already done · release: already done · published v0.12.0 …    exit 0
the stub go install reporting 0.11.0
  -> release: go install …@v0.12.0 reports version 0.11.0, module v0.11.0      exit 1

a binary whose build info carries module v0.12.0 and no VCS stamp, then vloop upgrade
  -> .vloop/install.json has "commit":"unknown","module":"v0.12.0"
vloop version                     -> unchanged from today for the same build
```

Planted failures, each in a scratch copy of the tree:

```
a version literal put back in cmd/vloop/main.go       -> V1's gate fails
publish made to tag before finding the release commit -> P2's gate fails
a test that runs the real gh                          -> the review's violation
```

**Real-data check**, on a clone of this repository:

- `go run ./tools/release notes v0.10.0 v0.11.0` lists B16 alone under Briefs;
  `notes v0.9.0 v0.10.0` lists B13, B14 and B15. Both outputs in the task
  notes; the operator compares them with `git log`.
- `go run ./tools/release prepare v0.12.0 --dry-run` on a clean, current `main`
  passes every check but the checks' run time, and writes nothing.

## Out of scope

- Merging the release PR, installing the release, `vloop upgrade` and the
  marketplace update: the operator's.
- Release binaries or archives attached to the GitHub release; changelog files.
- A `vloop` subcommand; releasing any repository other than vloop.
- Changing `vloop upgrade`'s behaviour beyond I1, or the plugin's content.
- Re-tagging or editing past releases.

## Constraints

- Go as pinned in `go.mod`; no new dependencies. Every gate builds for
  `windows` and `linux` as well as the host.
- Gates run on macOS's BSD tools: no empty alternatives in `grep -E`, no
  `sed -i` without a suffix, no `\+` or `\|` in basic regexes, no `date -d`, no
  `\*` through `awk -v`. A scratch directory is
  `mktemp -d "${TMPDIR:-/tmp}/gate.XXXXXX"`.
- Sessions never move refs and write nothing under `.vloop/` but .vloop/tmp/
  (S-4): no task's work, and no gate, may require a session to change this
  repository's records, config or state. Tests build their repositories in
  temporary directories, with a temporary `HOME`, and address them with
  `git -C`. No session or gate runs the tool against this repository's real
  `origin`, or reaches the network.
- **The gate model applies** (`plugin/skills/plan/SKILL.md`): each gate judges
  this brief's contract by running the built binary or tool, or reading the
  changed document or code, with its judge in the verify or its gate folder;
  no gate runs the repository's tests — this repository's `[[check]]` does,
  after every iteration.
- **No task may weaken a check to pass. An earlier test changes only where it
  pins behaviour this contract changes, and only to the new behaviour**, the
  task's notes naming the item for each.
- Repo-relative paths everywhere. No absolute paths in any file or commit
  message.

## Shape

7 to 9 tasks, each independently verifiable by a single command. Order is
load-bearing:

1. **V1, one version source.**
2. **I1, `module` in the install stamp.**
3. **N1, `notes`**, with the real-data check.
4. **P1's checks**, refusing before anything is written.
5. **P1, the release branch and PR.**
6. **P2, tag and GitHub release.**
7. **P2, the public-install check and the re-run.**
8. **D1, the docs and the playbook.**
9. **Close:** the worked example line for line, and the real-data check.
